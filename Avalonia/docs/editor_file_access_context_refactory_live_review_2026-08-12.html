主题 当前代码事实 对新草案的影响
Provider 注册 Core 中只有一个 FumenVisualEditorProvider 同时注册为 IEditorProvider 与 IFumenVisualEditorProvider；Desktop/Browser 尚无各自的 Fumen Provider 注册。 按平台拆分可行，但必须定义 Core 共享服务与平台入口的注册边界，避免同时注册出两个相同文件类型 Provider。
职责现状 Provider 的 TryNew/TryOpen 目前只转发；文件夹选择、书签恢复、项目扫描和加载仍在 FumenVisualEditorViewModel.ProjectIO.cs。 草案提出把交互与平台逻辑移回 Provider，方向与现状相反，需要明确 ViewModel 接收上下文后的最小职责。
现有加载不变量 EditorProjectDataUtils.TryLoadFromFileAsync 接收一个项目根目录，并通过 EditorProjectPathResolver.TryResolveDependency 在该根目录内解析谱面和音频。 当前实现是严格单根模型；草案中的 Desktop 多目录兼容不能直接套用现有解析器。
运行时所有权 EditorProjectDataModel 当前持有并释放 ProjectRoot、 ProjectFile、FumenFile、AudioFile 等句柄。 若新增 EditorFileAccessContext 也持有这些对象，必须确定唯一所有者和转移时点，否则容易双重释放或泄漏。
最近记录 当前 Fumen 最近记录数据只有“一个文件夹书签 + 一个工程根相对定位符”；有效性检查也只恢复这一目录。 它只能重建单根工作区，无法自动表达 Desktop 工程、谱面、音频分别位于不同目录的情况。
Fast Open Core 的 Fast Open 注册已关闭；遗留流程可从单独谱面和用户补选音频构造 EditorProjectDataModel，但不一定存在 .nyagekiProj 文件。 Q8 已确认 Fast Open 初始允许 ProjectFile 为空；首次由用户触发完整保存时再选择工程文件， 保存成功后将新句柄纳入当前运行时上下文。
与既有设计的关系 docs/fumen-visual-editor-project-folder-io-design.md 已确认 D1：用户授权的项目文件夹是全部项目 I/O 的唯一权限边界。新草案的 Desktop 行为允许三个主文件分散在不同文件夹，因此这是一次明确的设计变更，不能只视为类名重构。

Q1. Desktop 是否正式支持“多授权根工作区”？

已确认

为什么必须先决定

新草案同时写了两个目前不能自然共存的不变量：ProjectDirectory 是项目主目录；Desktop 又可忽略 .nyagekiProj、谱面和音频位于不同文件夹。若只增加一个 List<ISimpleDirectory> AdditionDirectories，调用方仍然不知道每个文件由哪个目录授权、哪些路径允许保存、 最近记录应恢复几个权限，以及谁负责释放重复目录句柄。

不先明确会出现的直接歧义
  • ProjectDirectory 究竟是权限边界、工程文件父目录、默认保存目录，还是仅用于 UI 显示？
  • 工程中的绝对路径在 Desktop 上是继续保留、转为相对路径，还是保存时被重写？
  • 谱面和音频位于外部目录时，Save 是否可以原地覆盖，Save As 又能选择哪些目录？
  • 最近记录只有一个目录书签时，应用重启后无法恢复多目录工作区；只保存本地路径又无法证明权限和可写性。
  • AdditionDirectories 与文件没有角色绑定，无法可靠去重和安排反向释放顺序。

方案 A：所有平台保持单根

Desktop 打开旧工程时，如果谱面或音频在项目根外，也先复制到项目内再加载。这样完全延续既有 D1，Browser 与 Desktop 使用同一种上下文和最近记录格式。

优点模型最简单；现有路径解析、保存边界和“一个目录书签”最近记录可以复用；项目天然可搬运。
代价改变原 Desktop 行为；打开旧工程可能产生副本并重写引用；不能原地编辑散落在外部目录的资源。

方案 B：Browser 单根，Desktop 显式多根

Browser 新建与打开继续形成便携单根工作区；Desktop 的旧工程和 Fast Open 可形成兼容多根工作区。 “多根”必须成为上下文的显式模式，每个文件都要绑定自己的授权根，而不是仅把目录放入一个无类型列表。 

public enum EditorWorkspaceKind
{
    PortableSingleRoot,
    DesktopLegacyMultiRoot
}

public enum EditorFileRole
{
    Project,
    Fumen,
    Audio
}

public sealed record EditorFileBinding(
    EditorFileRole Role,
    ISimpleFile File,
    ISimpleDirectory AuthorizationRoot);

public sealed class EditorFileAccessContext : IAsyncDisposable
{
    public required EditorWorkspaceKind WorkspaceKind { get; init; }
    public required ISimpleDirectory ProjectDirectory { get; init; }
    public required IReadOnlyList<EditorFileBinding> Files { get; init; }
}

上述代码只是表达本题推荐的不变量，不是最终 API：后续还要单独决定 Fast Open 时 Project 绑定是否可缺省、目录/文件句柄由谁拥有，以及是否需要专门的保存策略对象。

优点保留 Desktop 原行为；Browser 仍维持可移植和权限受限模型；平台差异在 Provider 构造上下文时显式化。
代价最近记录、路径语义、保存边界和资源所有权都必须支持两种模式；测试矩阵明显扩大。

方案 C：Desktop 直接使用任意本地路径

把 ProjectDirectory 只当工程文件父目录，谱面和音频继续按绝对字符串路径访问； AdditionDirectories 仅作辅助信息。

优点最接近旧 Desktop 代码，短期改动量看似较小。
风险绕过新文件能力模型；ViewModel/加载器重新依赖 System.IO；上下文不能证明权限和所有权；Browser 与 Desktop 的核心加载路径再次分叉。
回答前的审核建议：选择方案 B，并把它定义成受约束的兼容模式。

这最符合草案明确提出的 Desktop 兼容目标，同时不会把“任意本地路径”泄漏回 ViewModel。Provider 负责把平台来源转换成完整、已验证的文件绑定； ViewModel 只消费绑定好的文件句柄。Browser 永远只产生 PortableSingleRoot；Desktop 只有打开旧工程或 Fast Open 时才可产生 DesktopLegacyMultiRoot，新建项目仍优先产生单根工作区。

推荐流程

Browser 新建/打开
  -> 选择项目根
  -> 外部谱面/音频复制到 autoImport
  -> 验证所有主文件属于项目根
  -> PortableSingleRoot

Desktop 新建
  -> 与 Browser 共用导入流程
  -> PortableSingleRoot

  -> 分别取得并验证工程、谱面、音频文件能力
  -> 为每个文件记录授权根
  -> DesktopLegacyMultiRoot

两种模式
  -> EditorContext
  -> FumenVisualEditorViewModel.Load(EditorContext)
  -> ViewModel 不再自行弹 Picker 或解析任意系统路径

回答后的修正 上面的初步建议错误地准备把 WorkspaceKind 和每个文件的 AuthorizationRoot 暴露给核心项目。用户明确指出，这些信息只属于平台构造过程。新结论保留“平台可以采用单根或多根来源”的自由， 但核心契约不描述来源拓扑，也不因 Desktop/Browser 产生两套加载算法。
用户回答：

EditorFileAccessContext 只由平台项目构造。对于核心项目，它只负责提供合适的可读写目录， 以及角色明确、可读写的谱面、音频和项目文件上下文。核心项目不关心这些对象如何从单目录、多目录、书签、 本地路径或复制导入流程中产生，只关心如何读取和使用所需文件内容。

审核归纳：
  • 构造责任属于平台 Provider。 Browser/Desktop Provider 负责文件选择、目录授权、外部文件复制、 路径解析、文件存在性检查，以及交付前所需的可读写能力验证。
  • 核心只依赖能力，不依赖来源。 Core 中的 ViewModel 和加载服务通过 ISimpleDirectory/ISimpleFile 读取或写入，不分支判断 Desktop、Browser、单根或多根， 也不把 LocalPath 当作正常加载前提。
  • Desktop 多目录仍可存在，但被封装。 原草案允许 Desktop 的工程、谱面和音频位于不同目录； 平台可在内部组合这些能力，但不应把 WorkspaceKind、授权根映射或书签结构泄漏进核心领域模型。
  • 文件角色必须直接可见。 核心不应从 AdditionDirectories 中猜测哪个文件是谱面、音频或工程； 三个主文件应由明确命名的属性提供。附加目录只有在核心确实需要按目录发现资源时才有意义，不能承担隐式主文件解析职责。
  • “已验证”是交付前置条件，不是永不失败保证。 平台在构造时应尽可能确认文件存在且支持预期读写； 交付后仍可能发生权限撤销、文件被外部删除、磁盘已满或写入异常，核心必须把这些视为正常 I/O 失败并正确呈现， 不能假定句柄永久有效。
  • 既有设计需要标明被修订的范围。 旧文档 D1 的“单一项目根是全部 I/O 边界”继续适用于 Browser 和便携项目流程，但不能再作为 Core 加载器必须了解的全局不变量；Desktop Provider 可以交付来自多个位置的已绑定文件能力。
最终决策 D1：

Q2. 新建时没有已有谱面，可写的 FumenFile 应在何时绑定？

已确认

触发原因

Q4. “谱面文件名”和“保存格式”如何组合成最终文件名？

已确认

为什么必须定义

Setup 同时提供文件名输入框和保存格式选择器。如果二者都允许携带扩展名，就会出现 master.ogkr.nyageki、输入扩展名与选择格式不一致，以及 Provider 不知道应信任哪一个值的问题。 Core 的序列化器按最终文件名后缀选择，因此该规则会直接决定实际写出的谱面格式。 

用户输入：master.ogkr
选择格式：Nyageki (*.nyageki)

可能结果：
  A. master.ogkr.nyageki
  B. master.nyageki
  C. master.ogkr，但实际选择 OGKR 序列化器
  D. 拒绝输入并要求修正

若没有固定规则，各平台很容易产生不同结果。

方案 A：输入名称主体，格式唯一决定扩展名

输入框表示叶级文件名的名称主体，不包含格式扩展名。格式下拉框选择一个具体可写扩展名，Provider 组合出最终名称， 并在表单中实时显示只读预览。 

名称：master
格式：Ongeki Fumen (*.ogkr)
预览：master.ogkr

名称：master.v2
格式：Nyageki (*.nyageki)
预览：master.v2.nyageki

建议的表单验证如下：

  • 去除输入首尾空白后不能为空，也不能是 . 或 ..。
  • 不得包含目录分隔符；这里只接受直接子文件名，不接受相对路径。
  • 若输入以任一已注册谱面扩展名结尾，则显示“文件名无需填写扩展名”，不静默猜测或改写。
  • 平台继续检查其文件系统禁止的字符或保留名称。
  • 最终名称通过所选具体扩展名构造，并再次用 IFumenParserManager.GetSerializer(finalFileName) 验证。

方案 B：输入完整文件名，格式只作为默认建议

用户可以直接输入 master.ogkr；格式选择器只在没有扩展名时补全，或用于初始默认值。 当二者冲突时还需另定“扩展名优先”还是“下拉框优先”。

优点熟悉传统保存对话框的用户可以直接输入完整名称。
风险同一信息有两个来源；冲突规则复杂；很容易使 UI 所示格式与实际序列化器不一致。

方案 C：允许完整名称，并自动替换扩展名

用户输入 master.ogkr 后选择 Nyageki，Provider 自动改为 master.nyageki。 这种体验表面方便，但如果名称末尾本来就是业务名称的一部分，静默替换可能令人意外；新增格式后识别规则也会变化。

推荐答案：方案 A，文件名输入只表示名称主体，保存格式唯一决定扩展名。

这是最清晰、可测试的单一事实来源。UI 应显示最终文件名预览，使用户在创建前能看见真实结果； Provider 仍负责平台特定文件名校验，Core 只接收已经创建好的 FumenFile。 当前格式可产生 .ogkr 或 .nyageki，以后应继续从序列化器注册表动态取得。

是否采用方案 A：用户只填写不带格式扩展名的谱面名称，所选保存格式追加唯一扩展名，并在 Setup 中显示最终文件名预览？

用户回答：

同意推荐方案。

审核归纳：
  • 名称与格式是两个职责清晰的字段。 “谱面文件名”输入框只保存名称主体； “保存格式”选择器提供一个具体的、已注册的可写扩展名。扩展名只有一个来源，不从用户输入中推断。

Q5. 最终谱面文件名已存在时，新建流程应如何处理？

已确认

代码事实与风险

当前 AvaloniaStorageProviderSimpleDirectory.CreateFileAsync 已在目录快照中按 OrdinalIgnoreCase 检查同名文件，发现匹配时抛出 IOException；项目定位符解析同样采用不区分大小写的语义。 因此 master.ogkr 与 MASTER.OGKR 在项目逻辑层必须被视为冲突，即使某些底层文件系统技术上允许二者共存。

覆盖尤其危险

Setup 尚未完成时直接覆盖已有谱面，会在编辑器初始化、音频解码或工程文件创建随后失败时留下不可恢复的数据损失。 而“指定现有谱面文件”分支已经提供了明确使用已有文件的入口，因此空白新建分支没有必要隐式兼任覆盖功能。

方案 A：拒绝冲突并要求改名

最终文件名存在任何不区分大小写的匹配时，Setup 将“创建”按钮禁用并显示实际冲突文件名； 用户必须修改名称或格式。若用户原意是打开已有谱面，应主动勾选“指定现有谱面文件”并选择它。 

ProjectDirectory 已有：Master.ogkr

输入名称：master
选择格式：.ogkr
最终预览：master.ogkr

结果：
  -> 检测到与 Master.ogkr 冲突
  -> 禁止创建
  -> 不覆盖、不删除、不自动切换分支
  -> 提示改名，或改用“指定现有谱面文件”

表单预检只能改善体验，不能替代创建时检查。外部程序可能在用户点击“创建”前后写入同名文件，因此 Provider 仍需捕获 CreateFileAsync 的冲突异常，刷新目录状态并回到 Setup，而不能把它当成致命应用错误。

方案 B：询问是否覆盖

检测到冲突时弹出确认框，用户确认后清空或替换已有文件。该方案需要在任何新文件写入前保存旧内容并支持完整回滚， 还必须解释“覆盖”究竟是创建空白谱面，还是加载旧内容后覆盖保存。它与两条互斥 Setup 分支的含义容易混淆。

方案 C：自动生成可用名称

自动改成 master (2).ogkr、master (3).ogkr 等。虽然能快速完成创建， 但工程引用的名称会与用户输入不同，且并发创建仍需要重试循环；对创作项目文件而言，静默改名通常不够透明。

推荐答案：方案 A，空白新建绝不覆盖或自动改名。

这与现有 CreateFileAsync 和项目路径大小写规则一致，也让复选框的语义保持清晰： 未勾选代表创建一个全新的谱面；勾选代表明确使用一个已有谱面。冲突是可修正的表单错误，不应成为破坏性操作入口。

Q6. 新谱面文件应何时写入有效内容，初始化失败时是否删除？

已确认

为什么紧接着决定

Q2-D2 要求 Provider 在交付上下文前得到真实的 FumenFile，Q3-D3 又要求通过 ProjectDirectory.CreateFileAsync 在项目根创建它。该 API 创建成功后，底层已经存在一个文件； 如果后面的空白谱面序列化、音频加载、工程文件创建或 ViewModel 初始化失败，项目目录可能残留一个零字节或半完成谱面。

当前代码已经具备实现严格回滚的基础：

  • ISimpleFile.WriteAsync 可把序列化结果写入目标文件。
  • AvaloniaStorageProviderSimpleFile.DeleteAsync 可删除文件并从父目录快照移除。
  • .ogkr 与 .nyageki 格式器都能把初始化后的 OngekiFumen 序列化为有效内容。
  • 现有 SVG 导入器已经使用“创建、写入、验证；失败则删除本次创建文件”的同类模式。

方案 A：把文件创建到编辑器成功初始化视为一个事务

Provider 或共享新建编排服务先在内存中构造空白谱面及工程模型，序列化成功后才创建最终文件； 创建后立即写入完整有效谱面，并可选地读回验证。随后继续创建/写入工程文件和初始化编辑器。 在所有权正式转交给编辑器之前，任一步失败都删除本次创建的谱面及其他新产物。 

Setup 校验通过
  -> 内存构造空白 OngekiFumen
  -> 选择的序列化器先生成 bytes
  -> CreateFileAsync(finalName)
  -> WriteAsync(bytes)
  -> 必要时读回并验证
  -> 构造/写入 ProjectFile
  -> 构造 EditorContext
  -> Core.New(context) 初始化音频和编辑器
  -> 成功：转交文件所有权，关闭 Setup

任一步失败
  -> 删除本次新建的 ProjectFile（若有）
  -> 删除本次新建的 FumenFile
  -> 保留原有文件与 Setup 输入
  -> 弹出错误对话框
  -> 清理失败只记录警告，不覆盖原始错误

这里的“事务”是应用级最佳努力事务，不声称底层 Storage API 提供跨文件原子性。关键不变量是： 只删除本次流程确实新建、且尚未转交所有权的文件，绝不能删除用户原先选择的音频或已有谱面。

方案 B：先创建零字节占位，首次保存才写有效谱面

Provider 只创建文件句柄并打开编辑器，等用户第一次保存时才序列化。这样减少 Setup 阶段写入， 但如果应用崩溃、用户关闭而不保存或初始化后来失败，项目中会留下无法解析的零字节谱面；最近记录和外部工具也可能看到这个无效文件。

方案 C：创建后立即写谱面，但初始化失败仍保留

该文件至少格式有效，可作为用户手工恢复的产物；但用户点击“新建”最终得到错误时，项目目录会产生他未明确接受的文件， 重试又会立即触发 Q5 同名冲突。还需要额外 UI 解释这个残留文件是否可用。

推荐答案：方案 A，写入有效初始内容，并在所有权转交前失败时删除本次产物。

它让 EditorFileAccessContext 的“可读写谱面文件”含义更强：交给 Core 的不是空句柄， 而是已经包含所选格式有效内容的文件。它也避免初始化失败后留下垃圾文件并导致下一次重试触发同名错误。 删除采用最佳努力；若清理本身失败，应在错误对话框中说明可能残留的文件名，并记录诊断日志。

Q8. Desktop Fast Open 是否允许 ProjectFile 为空？

已确认

代码事实与草案冲突

旧 WPF Fast Open 的目的，是直接选择一个 .ogkr/.nyageki 谱面并补选音频， 立即进入编辑器。DocumentOpenHelper.TryCreateEditorProjectDataModel 只设置谱面、音频和内存工程模型， 不创建或绑定 .nyagekiProj；窗口标题带有 [Fast Open] 前缀。

当前上下文声明过强

草案把 EditorFileAccessContext.ProjectFile 写成必需字段，同时又要求 Desktop 恢复原 Fast Open。 两者不能同时成立：要么 Fast Open 在打开前产生一个真实工程文件，要么上下文必须表达“谱面和音频已绑定，但尚无工程文件”的合法状态。

Q12. 运行时文件能力由谁唯一持有，角色字段应如何释放？

已确认

当前实现把“角色引用”和“资源所有权”混在同一个模型中

EditorProjectDataModel 当前同时保存可序列化工程数据和运行时句柄。 AudioFile、AudioAwbFile、FumenFile、ProjectFile、 ProjectRoot 的 setter 都会释放旧值；编辑器关闭时再调用 DisposeRuntimeFiles() 依次清空角色文件和目录根。

目录树中的文件角色通常只是别名，不能被当成独立所有者

AvaloniaStorageProviderFileSystemBuilder 会把整个文件夹树的所有权交给返回的根目录；根目录释放时递归释放所有子目录和子文件。 因此从该树解析出的 ProjectFile、FumenFile 和 AudioFile 只是指向树中节点的角色引用。 先逐个释放角色文件、再释放根目录，会对同一对象调用多次 Dispose()。当前若干实现恰好可重复释放， 但 ISimpleFile/ISimpleDirectory 契约没有承诺这一点，后续 Provider 也不应依赖该偶然性质。

另一方面，Desktop Fast Open 或多目录工程可能使用不属于 ProjectDirectory 树的独立本地文件句柄， 或由多个授权目录根提供谱面和音频。它们确实需要被某个长期对象持有并在文档关闭时释放，不能简单规定“只释放项目根”。

方案 A：EditorFileAccessContext 是唯一运行时所有者

让 EditorFileAccessContext 实现 IDisposable，显式记录它拥有的顶层资源； ProjectFile、FumenFile、AudioFile 和可选 AudioAwbFile 只是用于业务访问的借用角色引用。 EditorProjectDataModel 回归可序列化工程状态，不再持有或释放任何文件系统对象。 

EditorFileAccessContext（唯一运行时所有者）
  OwnedDirectoryRoots
    - ProjectDirectory
    - AdditionDirectories 中互不重叠的授权根

  OwnedStandaloneFiles
    - 不属于上述任一目录树、由 Provider 单独取得的文件能力

  BorrowedRoleAliases
    - ProjectFile?
    - FumenFile
    - AudioFile
    - AudioAwbFile?

释放顺序
  -> 每个顶层所有资源仅 Dispose 一次
  -> 不单独 Dispose 目录树内的角色别名

所有权转移规则：

  • Provider/Setup 在调用 Core 前拥有候选 EditorContext 及其文件访问上下文。
  • New(EditorContext)/Load(EditorContext) 返回成功时，所有权一次性转交给编辑器文档； 返回失败、取消或抛异常时，调用方仍负责释放候选上下文。
  • 编辑器文档在成功初始化后只持有一个当前上下文，并在文档关闭时释放一次；音频播放器、流等派生对象继续按各自生命周期释放。
  • Fast Open 首次保存或后续绑定替换时，新资源在提交前由保存编排持有；提交成功后再转入当前上下文，旧顶层资源随后释放。 同一个可释放对象不得同时登记为两个上下文的拥有资源。
  • 顶层拥有集合必须在构造时显式形成并去重，不能只靠路径字符串或 ParentDictionary 临时猜测； AdditionDirectories 也不得包含 ProjectDirectory 或彼此的后代目录。
优点序列化数据与运行时能力职责分离；单根、Desktop 多根和独立文件使用同一所有权模型；失败回滚与绑定替换有明确边界。
代价需要移除 EditorProjectDataModel 当前的运行时句柄和释放 setter，并为上下文构造、转移与替换增加专门 API 和测试。

方案 B：继续由 EditorProjectDataModel 持有句柄

EditorFileAccessContext 只作为进入 Core 的临时参数，初始化时把各字段再次写入项目模型。 该方案表面上改动较少，但会继续把持久化模型、目录树所有权和平台能力混在一起；上下文与模型之间还需要定义逐字段转移， 现有 setter 的“赋值即释放”会让 Fast Open 原地升级和事务回滚更容易提前释放仍在使用的旧绑定。

方案 C：每个字段独立拥有或引入引用计数

为每个目录和文件角色建立独立所有权或引用计数包装器。它可以容忍任意别名，但当前简单文件系统没有 AddRef/Release 契约，目录又会递归释放子项；为本次重构引入通用引用计数会扩大基础设施范围， 仍然不能替代 Provider 对顶层授权根的清晰建模。

推荐答案：方案 A，由 EditorFileAccessContext 独占运行时资源，角色字段全部是借用别名。

这与 Avalonia Storage Provider 的能力生命周期一致：平台在用户驱动流程中取得文件/目录能力，Provider 在初始化成功前持有， 成功后把整个上下文交给文档，文档关闭时统一释放。目录树按根释放，独立能力按显式顶层条目释放； EditorProjectDataModel 只描述工程内容和持久化定位符，不再承担平台资源生命周期。

Q13. Provider 应如何按宿主注册，两个服务接口如何保证同一实例？

已确认

问题来源：当前共享 Provider 与平台拆分计划存在注册冲突

当前 FumenVisualEditorProvider 位于共享 OngekiFumenEditor.Avalonia 程序集， 同时标注 [RegisterSingleton<IEditorProvider>] 和 [RegisterSingleton<IFumenVisualEditorProvider>]，并把 New/Load 直接转发给 ViewModel。 但重构草案要求 Browser 和 Desktop 分别实现具有平台行为的 Provider，并由 Provider 构造 EditorFileAccessContext 后调用新的 New(EditorContext)/Load(EditorContext)。

两个宿主都会先调用共享的 AddOngekiFumenEditorAvalonia()，随后再调用各自的 AddOngekiFumenEditorAvaloniaDesktop() 或 AddOngekiFumenEditorAvaloniaBrowser()。 当前 Injectio 配置为 InjectioDuplicateStrategy=Append，而框架的“新建”“打开”“打开最近记录”命令都会枚举 IEnumerable<IEditorProvider>。因此，如果保留共享 Provider 再追加一个平台 Provider，菜单和最近记录匹配会出现两个实现。

两个注册属性也不等于同一个单例对象

当前生成的 DI 代码分别写入两个 ServiceDescriptor.Singleton<IEditorProvider, FumenVisualEditorProvider> 与 ServiceDescriptor.Singleton<IFumenVisualEditorProvider, FumenVisualEditorProvider>。 Microsoft.Extensions.DependencyInjection 会按服务类型分别缓存实现类型实例；仅靠两个属性不能保证 IoC.Get<IFumenVisualEditorProvider>() 与 IoC.GetAll<IEditorProvider>() 取得的是同一对象。 Provider 一旦保存最近记录缓存、并发门或平台状态，这种差异会变成难以复现的行为分叉。

方案 A：每个宿主恰好注册一个平台 Provider，并把两个接口别名到同一实例（推荐）

共享程序集只保留 Provider 接口、文档工厂、与平台无关的解析/保存编排；不再让共享的具体 Provider 自动注册为 IEditorProvider。Desktop 程序注册 DefaultDesktopFumenVisualEditorProvider， Browser 程序注册 DefaultBrowserFumenVisualEditorProvider；每个宿主只选择其中一个实现。 两个服务接口都显式解析到同一个具体单例，示意如下： 

// 共享 AddOngekiFumenEditorAvalonia()
// 只注册公共服务，不注册具体 IEditorProvider

// Desktop 宿主
services.AddSingleton<DefaultDesktopFumenVisualEditorProvider>();
services.AddSingleton<IEditorProvider>(sp =>
    sp.GetRequiredService<DefaultDesktopFumenVisualEditorProvider>());
services.AddSingleton<IFumenVisualEditorProvider>(sp =>
    sp.GetRequiredService<DefaultDesktopFumenVisualEditorProvider>());

// Browser 宿主使用 DefaultBrowserFumenVisualEditorProvider 的同样模式

该方案的具体约束：

  • 每个宿主的 IEnumerable<IEditorProvider> 对本编辑器类型只有一项。 新建、打开、最近记录和文件扩展名匹配不会因共享/平台双注册而重复。
  • IFumenVisualEditorProvider 只是同一实例的窄接口视图。 现有需要专用能力的调用点可以继续依赖该接口，但不能再用第二个实现类型或第二个状态容器。
  • Provider 单例不保存单次操作状态。 对话框结果、候选上下文、取消令牌和回滚清单必须是每次调用的局部对象或短生命周期服务； 这样同一 Provider 才能安全处理多个文档和并发的最近记录校验。
  • 平台差异停留在宿主层。 Browser 使用 Storage Provider、书签和受限路径能力；Desktop 可增加本地路径、Fast Open 和多授权根， 但两者都通过同一个 EditorContext 契约交付给共享编辑器。
  • 注册顺序不承担选择语义。 不依赖 Append、最后注册优先或枚举顺序；错误地同时包含两个 Provider 应在启动/测试时显式检测并失败。
优点平台行为隔离；每个宿主只有一个文件类型 Provider；两个接口引用同一状态对象；核心程序集可在 Browser、Desktop、命令行测试中独立验证。
代价需要把现有共享 Provider 的业务拆为公共编排与宿主实现，并改写源生成注册属性或改用显式 DI 注册；迁移期会触及 Provider 测试和启动组合根。

方案 B：保留一个共享 Provider，在内部按运行时平台分支

继续由共享程序集注册唯一 FumenVisualEditorProvider，在每个操作内部使用 OperatingSystem.IsBrowser()、Storage Provider 能力和本地路径能力选择分支。 这样不需要改变 DI 数量，但 Provider 会同时承担 Browser 的异步授权/书签语义和 Desktop 的本地多目录/Fast Open 语义。

优点短期文件移动和注册改动最少；现有框架只看到一个 Provider。
风险共享核心重新依赖运行时平台判断；Browser 和 Desktop 的失败/取消/路径规则会互相污染；未来增加第三个平台时继续堆条件分支；平台行为难以用无平台单元测试覆盖。
额外陷阱即使保留一个具体类型，也必须改掉两个服务属性造成的“双描述符”问题，或改用显式工厂保证接口别名同实例。

方案 C：共享 Provider 与平台 Provider 同时注册，再依靠 Replace、优先级或枚举顺序

共享实现继续自动注册，宿主实现随后使用 Replace、自定义优先级或“取第一个/最后一个”来尝试覆盖它。 这种做法看起来能避免改共享源码，但框架的菜单和最近记录是按 IEnumerable<IEditorProvider> 枚举， 不同注册 API 对单服务解析和集合解析的行为并不相同；某些路径可能拿到平台实现，另一些路径仍拿到共享实现。 在 AOT/Trim 构建下，依赖反射顺序更不能作为协议。

表面优点迁移期间可以暂时保留旧类和旧测试，平台实现逐步接管。
实质风险重复菜单、最近记录误匹配、接口别名实例不一致，以及注册顺序随生成器或宿主项目变化而改变；问题通常只在特定启动方式出现。
推荐答案：方案 A，每个宿主只注册一个平台 Provider，并将 IEditorProvider 与 IFumenVisualEditorProvider 映射到同一具体单例。

这是唯一同时满足三条不变量的方案：共享核心不依赖平台实现；框架枚举对本编辑器类型只得到一个 Provider； 需要专用接口的调用点和通用接口调用点观察到同一生命周期与同一状态。注册责任应放在 Desktop/Browser 的应用组合根， 而不是让共享模块通过源生成属性隐式决定宿主行为。迁移完成后，启动自检应断言每个宿主的 Provider 数量和接口实例身份， 失败时尽早暴露配置错误。

Provider 从记录恢复时执行以下流程：

读取 RecordId 的二进制数据
  -> 校验版本、宿主类型、打开类型和角色完整性
  -> 当前宿主异步恢复所有根/独立文件能力
  -> 规范化并解析每个角色定位符，拒绝越界、重复根和角色错配
  -> 验证本场景必需文件可读；需要保存的角色还必须可写
  -> 构造候选 EditorFileAccessContext
  -> 调用 Core 的 Load(EditorContext)
       成功 -> 整体转交上下文并更新同一个 RecentRecordInfo
       失败 -> Provider 释放全部已恢复能力，不产生半初始化文档

该方案还包含以下约束：

  • 恢复配方属于平台 Provider，不属于 Core。 Core 只消费已经构造完成的 EditorContext；它不解析书签、绝对路径、HostKind 或 RootId。
  • 显示字段不参与恢复和去重。 Name 与 LocationDescription 可随 UI 更新；真实配方只存入稳定 RecordId 对应的数据区， 书签正文不得写入日志、异常文本或显示字段。
  • 可恢复性是可选能力。 平台无法创建完整配方时，本次文档仍可打开， 但不新增一个从产生起就无法恢复的最近记录；已有有效记录也不能被空配方覆盖。
  • 记录更新跟随绑定提交。 Fast Open 首次保存、复制导入或另存为完成“先建后换”后， Provider 才以新配方更新原 RecordId；写文件或上下文替换失败时保留旧记录和旧绑定。
  • 轻量校验与正式打开不共享活句柄。 CheckIsValid 为菜单状态临时恢复并立即释放； 用户点击后再次权威恢复，由正式打开流程取得最终上下文。缓存只能缓存结果，不能跨流程缓存可释放句柄。
优点保持 Q1 的平台边界；覆盖 Browser 单根、Desktop 多根与无工程文件 Fast Open；不把路径冒充权限；恢复失败有明确的资源回滚。
代价Desktop 与 Browser 需要各自的配方序列化和恢复器；上下文构造 API 要返回配方这一并列结果；绑定改变时必须同步更新最近记录。

方案 B：在共享层定义一个通用的“根 + 角色”序列化模型

把书签、本地路径、根 ID、角色定位符和打开类型都放进共享程序集，由同一个通用转换器在 RecentRecordInfo 与 EditorFileAccessContext 之间转换。它表面上减少两套数据类型， 但共享层必须理解“书签根”“本地路径根”和各宿主的恢复规则，重新破坏 Q1 已确认的平台封装； 新平台还会迫使公共枚举和序列化格式持续扩张。

优点数据结构看起来统一，公共序列化和部分结构校验可以复用。
风险Core/共享层知道平台权限拓扑；通用转换器容易把本地路径与书签误认为等价能力；无法自然表达某宿主不支持另一宿主配方的情况。

方案 C：最近记录只保存工程文件或显示路径

继续沿用单个 FolderBookmark + ProjectFileLocator，或在 Desktop 只保存工程文件绝对路径， 打开时再解析工程内容寻找谱面和音频。该方案不能表示 ProjectFile == null 的 Fast Open， 也不能证明 Browser 或多根 Desktop 对外部依赖仍有访问能力；若退回 LocationDescription 或路径字符串猜测，还会绕过已确认的授权边界。

表面优点最接近当前版本 1 数据，迁移代码最少。
实质风险合法上下文无法记录或无法恢复；文件移动和权限撤销后产生误判；可能在打开一半时才发现依赖缺失并泄漏已恢复资源。
推荐答案：方案 A，把最近记录定义为平台 Provider 的版本化恢复配方，而不是运行时上下文的序列化快照。

这延续了 Q1、D12 和 D13 的同一边界：平台负责取得能力和构造上下文，Core 只读写已经验证的角色文件， 上下文负责运行时所有权。配方可以精确表达每个宿主实际能够重获的根、角色和 Fast Open 状态； 若平台无法生成完整配方，就诚实地不创建最近记录。恢复失败如何区分永久失效、临时失败与需要用户重新授权， 将在 Q15 单独确认，不在本题用一个 false 混合决定。

Q15. 恢复失败如何区分永久失效、临时失败与需要用户重新授权？

已确认

问题来源：Q14 已确认快照方案，但恢复失败仍只有 true/false

D14 落地后，Provider.CheckIsValid 与 ProjectIO.Load(RecentRecordInfo) 已把 IOException/InvalidDataException 判为永久失效并调用 SetMarkedInvalid(true)， 其余异常按临时失败处理（仅记 warn、不置灰）。但 Q14 推荐答案指出恢复失败本应区分三种语义： 书签/文件确已不可恢复（永久失效）、平台暂时不可用（临时失败）、以及权限被撤销但可由用户重新授权（需要重新授权）。 当前实现把第三种并入了前两种，需要确认这是否足够。

框架只有二态 IEditorRecentFilesManager.SetMarkedInvalid(info, bool) 与 IsMarkedInvalid(info) 是当前唯一的失效持久化机制； CheckIsValid 返回 Task<bool>，OpenRecentFileCommandHandler 据此决定菜单项可点击与置灰
校验结果被缓存 IRecentRecordValidityCoordinator.GetOrCheckAsync 缓存 Provider 校验结果；点击时 forceFresh: true 强制复验。 临时失败会被下次 fresh 校验覆盖，因此不需要单独持久化“临时失败”态
Browser 权限撤销的典型表现 Avalonia StorageProvider 在权限被撤销时通常返回 null 而非抛异常，已被 ToContextAsync 映射为 IOException 并判为永久失效；要触发“需要重新授权”需要额外的权限探测 API，当前共享层没有
Desktop 几乎不存在第三态 Desktop 书签指向本地路径，权限撤销等价于文件删除/移动，已能被永久失效覆盖；“需要重新授权”主要面向 Browser/受限沙箱

方案 A：维持二态，需要重新授权并入永久失效（推荐）

保留 D14 当前实现：书签不可恢复（含权限撤销导致的 null）一律判为永久失效并置灰；临时平台异常按临时失败处理。 用户若想恢复一条被置灰的记录，通过“打开项目文件夹”重新选择并产生新记录（D38 已允许同项目生成新记录而不误合并）。 不引入第三态，避免扩展 Gekimini 框架的 IEditorRecentFilesManager 与 CheckIsValid 契约。

优点零框架改动；二态语义清晰；置灰记录可经“重新打开文件夹”自然恢复授权。

最终决策 D23：删除 FumenFilePath/AudioFilePath 的项目格式与运行时契约。 EditorFileAccessContext 是项目、谱面、音频主文件绑定的唯一事实来源；加载、保存、自动保存和恢复只操作上下文中的文件能力， 不从项目数据反向寻找文件。该决定使旧项目兼容、格式版本和“首次打开如何取得主文件能力”成为必须后续确认的独立问题。

Q24. 不再持久化主文件路径后，首次打开工程时 Provider 如何取得 FumenFile 与 AudioFile？

已确认

问题的完整背景

D22-D23 已把运行时和持久化路径全部移除：.nyagekiProj 不再说明谱面和音频位于何处， 而 ViewModel.Load(EditorContext) 又只接受已经完整绑定三个主文件的 EditorFileAccessContext。 因此，在没有最近记录快照的“冷打开”中，Provider 不能只得到一个项目文件就调用 Core；它必须通过另一种明确规则取得 FumenFile 和 AudioFile。

这个问题不影响两类已有完整上下文的入口：新建/Setup 本来就会要求用户提供主文件；最近记录快照 D14 已分别保存项目、谱面、音频书签。 真正受影响的是普通打开：用户选择项目文件夹并选择某个 .nyagekiProj，或 Desktop 直接选择一个 .nyagekiProj。项目文件自身已经不能告诉 Provider 应绑定哪些谱面和音频。

当前打开算法将失效 现有流程读取 .nyagekiProj 的 FumenFilePath/AudioFilePath 后在目录树内解析。 D23 删除这两个字段后，扫描到工程文件只能证明 ProjectFile，不能证明另外两个角色
目录中可能存在多个合法候选 一个项目文件夹可以包含多个难度谱面、备份谱面、不同格式音频、转换产物或多个工程。 仅按扩展名扫描可能得到多个可读文件，无法知道哪两个属于当前工程
文件名约定不是现有不变量 当前工程允许任意 FumenFilePath/AudioFilePath，并未要求与项目文件同名。 默认选择同名谱面、目录中第一个音频或最近修改文件都会改变既有语义，并可能静默打开错误内容
Browser 必须依赖已授权能力 Browser 不能在只选择单个项目文件后自行访问任意相邻文件；若选择整个目录，可以枚举候选，但仍需解决角色歧义。 独立文件选择器取得的文件也不能只靠路径字符串证明与项目目录的关系
最近记录只能解决后续打开 用户首次成功绑定后，D14 快照可保存三个文件书签并直接恢复；但最近记录不能为第一次打开凭空确定谱面和音频

方案 A：每次冷打开都显式确认谱面与音频绑定（最严格，推荐）

用户选择项目文件夹或 .nyagekiProj 后，Provider 打开“项目文件绑定”对话框，分别要求确认一个谱面文件和一个音频文件。 目录入口可以把已授权目录内、扩展名受支持的文件列为候选；Desktop 还可通过文件选择器补充外部文件。 即使各自只有一个候选，也在对话框中展示并要求确认，不根据数量自动作出业务关联。确认后 Provider 验证可读写性、格式、音频可解码性和所有权， 再构造完整上下文。最近记录恢复与当前会话内重复打开可跳过该对话框。

优点完全符合 D22-D23；不会因目录内容变化静默换绑；用户始终知道当前工程使用哪份谱面和音频；所有平台语义一致。
代价没有最近记录时，每次打开都至少多一次确认；包含大量文件的目录需要候选搜索、筛选和清晰的绑定 UI。
失败行为缺少任一文件、用户取消、文件不可读写或格式验证失败时，不构造 EditorContext，不创建最近记录，释放本轮取得的全部候选能力。

方案 B：唯一候选自动绑定，零个或多个候选时再询问（体验折中）

Provider 枚举已授权目录中的受支持谱面和音频。如果某角色恰好只有一个候选则自动绑定；为零时要求用户另外选择；超过一个时显示选择对话框。 成功后同样通过最近记录快照保存三个文件能力。

优点简单目录通常可直接打开；仍不需要在项目文件中持久化路径。
风险“当前只有一个”不等于“它属于这个工程”；增加或删除无关文件会改变是否弹窗，错误目录中可能自动绑定到可解析但不相关的文件。
需要的保护UI 必须在打开完成后明确显示绑定结果，并提供重新绑定入口；自动绑定也必须完成完整格式与可写性验证。

方案 C：采用文件名或目录结构约定自动发现（自动化优先）

例如优先选择与 .nyagekiProj 同名的 .ogkr/.nyageki，音频选择同名文件、固定名称或固定子目录； 不满足约定时再要求用户选择。该方案需要把命名规则提升为新的项目格式不变量，并决定大小写、多个扩展名、重命名和旧项目兼容行为。

优点遵循约定的新项目打开最快；项目文件本身仍不保存路径。
风险当前项目没有该约定；会改变旧项目语义，可能选错同名备份或转换产物；Desktop 多根和 Fast Open 很难共用同一规则。

方案 D：在项目文件中保存非路径身份信息，再扫描匹配

不保存路径，但为谱面和音频保存稳定 GUID、内容哈希或其他标识；Provider 扫描授权目录并匹配标识。 这能自动重绑定改名后的文件，但本质上仍让项目文件持久化“哪个文件属于工程”的映射，而且音频内容变化会使哈希失效，GUID 还需要写入或伴随目标文件。

优点理论上可兼顾重命名与自动发现。
风险复杂度最高；大文件哈希和全目录扫描成本高；新增身份协议可能违背“只从 EditorFileAccessContext 对应文件加载”的简化目标。
推荐答案：方案 A，冷打开时显式确认两个角色文件。

在完全不持久化关联信息的前提下，只有用户确认才能可靠建立“这个谱面和音频属于这个项目”的关系。 方案 B/C 都是在目录内容或命名上猜测；方案 D 则重新引入另一种持久化关联。方案 A 的额外交互可由最近记录快照抵消：首次绑定后，正常再次打开无需重复选择。

请确认的唯一问题

对于没有可用最近记录快照的普通打开，是否采用方案 A：Provider 在选定 .nyagekiProj 后始终显示文件绑定对话框， 由用户明确确认一个 FumenFile 和一个 AudioFile；不按唯一候选、文件名、修改时间或目录顺序自动关联， 成功验证并构造完整 EditorFileAccessContext 后才调用 ViewModel？

用户后续指示：按顺序全部实现。实施采用本题推荐的方案 A。
审核归纳：没有可用最近记录快照时，Provider 在用户选定工程描述符后必须显示项目文件绑定对话框； 用户明确选择一个受支持的谱面文件和一个音频文件后才能继续。即使目录内各自只有一个候选也不预选、不自动关联； 用户可以通过 StorageProvider 文件选择器补充目录外文件。取消、缺少角色文件或验证失败时不构造编辑器上下文，并释放本轮仍由对话框或 Provider 持有的文件能力。
最终决策 D24：冷打开采用显式绑定。Provider 不使用唯一候选、同名、修改时间或目录顺序猜测业务关联； 只有在项目、谱面、音频及需要时的外置 AWB 全部取得并验证后，才把完整 EditorFileAccessContext 交给 Core。 最近记录快照已经包含直接文件书签时，可沿恢复路径跳过该对话框。
实施状态（2026-08-17，提交 0667b2d9）：新增 ProjectFileBindingDialogView 与 ProjectFileBindingDialogViewModel；现有项目文件夹 TryOpen 流程会扫描候选、要求显式确认并通过 TryLoadFromContextAsync 加载。外部 ACB 会优先绑定其明确声明且可取得的 AWB，否则要求再次显式选择。 当前共享 Provider 尚未另行暴露 Desktop“直接选择单个 .nyagekiProj”入口；该平台入口一旦实现，也必须复用本决策的显式绑定规则。
