## 0. 当前实现审计（2026-08-06）

本节以当前工作区代码为准，是本文档的现状基线。第 1 节以后主要保留访谈过程、历史基线和已确认的目标设计；其中写为“应当”或“将实现”的内容，不代表已经存在。

### 0.1 用户现在可以使用的项目流程

| 能力 | 当前行为 |
| --- | --- |
| 打开项目 | 启动页和文件菜单通过系统目录选择器要求用户选择一个项目文件夹；不再先选择单个 `.nyagekiProj`。 |
| 发现工程 | 一次性递归枚举所选目录及子目录。没有 `.nyagekiProj` 时显示错误；只有一个时直接打开；多个时显示列表并要求用户明确选择。 |
| 加载工程 | 读取所选 `.nyagekiProj`，再从同一目录能力中解析并读取谱面和音频。项目文件缺失、格式错误、谱面或音频缺失、路径越界及大小写冲突都会终止打开并显示错误。 |
| 路径边界 | `.nyagekiProj` 内的谱面和音频路径以该工程文件的父目录为相对基准，规范化后的目标必须仍在用户选择的项目根内。路径可使用 `..`，但不能越过项目根。 |
| 旧绝对路径 | Desktop 仅在本地路径可用且能证明目标仍位于项目根内时，将旧绝对谱面/音频路径转换为工程相对定位符；Browser 无法证明时直接拒绝。项目文件版本仍为当前 `0.5.4`，没有为本次重构升级版本。 |
| 链接条目 | Desktop 会拒绝作为链接/联接/挂载点的项目根，并跳过扫描到的本地重解析点；依赖若因此不在索引中，会按文件不存在报错。非本地 StorageProvider 没有等价链接检测信息时，只能依赖平台授予的目录能力边界。 |
| 音频加载 | 打开工程时完成解码和重采样，并把完整 PCM 缓冲保存在内存中；打开完成后的播放不再持续读取项目音频文件。 |
| 多编辑器 | 允许同一个 `.nyagekiProj` 同时打开多个编辑器，不做实例去重或外部变更检测；底层保存若被调用，按全局串行且后保存者覆盖处理。 |
| 最近项目 | 平台能为所选目录创建书签时，保存“文件夹书签 + 已选 `.nyagekiProj` 根相对定位符”。再次打开同一组合会更新并置顶原记录。无法创建书签不影响本次打开，但不会新增最近记录。 |
| 最近项校验 | 菜单和启动页共用 Gekimini 的异步 `CheckIsValid` 链路；书签无法恢复、指定工程丢失、路径冲突或链接违规等确定失效会被持久化，记录保留但按钮置灰。临时平台异常只使本次校验失败并记录警告，不永久置灰。点击前会强制重新校验。 |

### 0.2 Desktop 与 Browser 的实际范围

| 项目 | Desktop | Browser |
| --- | --- | --- |
| 项目目录 | 使用 Avalonia `StorageProvider` 目录能力；本地路径可用于额外边界证明。 | 使用用户选择获得的目录能力和文件流，不假定存在可用本地路径。 |
| 普通音频 | MP3、PCM/IEEE-float WAV、AIFF；非 Native-AOT 构建还可转换部分其他 WAV 编码。 | PCM/IEEE-float WAV、AIFF。当前不支持 MP3。 |
| ACB/AWB | 支持 ACB；外置 AWB 必须先在项目目录中解析并验证，随后通过已验证本地路径解码到临时 WAV。 | 不支持 ACB/AWB，项目引用 ACB 时打开失败。 |
| 旧绝对依赖路径 | 目标被证明在项目根内时可以迁移。 | 拒绝，要求工程保存可移植的相对路径。 |
| 最近项目 | 取决于当前 StorageProvider 是否支持目录书签。 | 同样取决于浏览器与 Avalonia StorageProvider 的书签能力；没有书签时只能完成当次打开。 |

### 0.3 已接通的保存能力与仍受限入口

- `FumenVisualEditorViewModel` 已实现 Gekimini 的 `IPersistedDocumentViewModel`。标准“保存”、`Ctrl+S`、“保存全部”和关闭文档前保存检查现在会把 Fumen 编辑器识别为可保存文档。
- `Save()` 在应用级全局 I/O 门内，把谱面和 `.nyagekiProj` 写回打开时绑定的原文件；保存前会保留两份原始字节，任一步失败都会尝试恢复工程和谱面两份文件。成功后清除脏状态并删除对应恢复快照。
- 脏状态会响应谱面对象内容修改、工程模型属性修改以及 Gekimini 撤销栈变化；单纯选择对象不置脏。音频时长、BPM/拍号、显示缩放和渲染控件尺寸变化会触发时间轴总高度重算。
- “另存为”尚未建立项目文件夹范围内的目标选择与越界重试流程，因此该编辑器暂不声明支持 `SaveFileAsCommandDefinition`，接口调用只记录警告并返回失败。`FumenVisualEditorProvider.TryNew/TryOpen` 只负责确认文档类型并转发；项目文件夹选择、书签恢复和项目加载流程由 `FumenVisualEditorViewModel.New/Load` 持有。
- 自动保存调度已能为“当前激活编辑器”在应用临时目录生成独立的工程、谱面和定位元数据快照；项目 I/O 正忙时跳过当次快照。它当前不判断脏状态，也没有启动时发现、恢复或忽略快照的 UI。
- `ISimpleDirectory` 已有项目目录内创建目录/文件和写入能力，SVG 内容寻址导入器也保留了实现与测试；由于 SVG 功能入口已整体关闭，这些能力目前没有形成可达的 SVG 用户流程。

### 0.4 当前明确不能做到

- 不能新建项目、在项目内新建谱面、另存谱面或选择新的项目内保存位置。当前也不存在“选到项目外后报错并重试”的保存对话框，因为相应入口尚未实现；已经打开的工程可以通过标准保存写回原工程和原谱面。
- 不能从外部导入音频；Desktop 专属谱面包导入也尚未实现，Browser 不提供这些入口。
- 不能快速打开单独的 `.ogkr`/`.nyageki`。相关 Core 菜单与启动页按钮已注释，命令处理器未注册，辅助方法受未定义的 `ENABLE_CROSS_PLATFORM_FAST_OPEN` 条件保护。
- SVG 图片和文字物件当前整体停用：不会预检或读取 SVG 文件，不显示、不绘制、不能创建或编辑，也不会执行外部 SVG 自动导入。解析器/格式化器仍保留记录兼容性，因此未编辑的既有 SVG 数据可随谱面再次保存，但用户当前不可见，也不应依赖其编辑行为。
- 不能在打开后的会话中重新扫描目录；没有扫描进度、用户取消、流式发现或按需索引。大型项目会在打开时一次性枚举完整目录树，音频还会完整解码进内存，目前没有固定资源上限或内存压力提示。
- 没有独立的异步 `IProjectSession`。当前由 `EditorProjectDataModel` 持有项目根、工程、谱面、音频及外置 AWB 的运行时句柄，并在编辑器销毁时同步释放。
- 原 WPF 的活动编辑器创建、激活、停用和销毁通知尚未完整移植；依赖“当前激活编辑器”的自动保存、编辑器专属快捷键上下文和关闭资源回收仍需单独处理。本轮明确未把该生命周期问题并入保存接线。
- 新增的项目选择和错误文字当前主要是硬编码英文，尚未完整接入语言资源。

### 0.5 并发与失败语义

- 项目目录扫描、项目/音频加载、最近书签校验、底层正式保存和定时恢复快照共用一个应用级 `SemaphoreSlim(1, 1)`；任意项目之间也会串行。等待用户在多工程对话框中选择时不占用该门。
- 定时恢复快照使用非阻塞尝试，门正忙时直接跳过；普通打开、最近项校验和底层保存会排队等待。
- 致命异常救援 `FumenRescue.Rescue()` 尚未接入该全局门，仍属于暂缓决策。
- 同一工程的多个编辑器各自持有独立内存模型；没有文件版本、时间戳或内容哈希冲突检测，最终内容取决于最后一次成功写入。

## 2. 背景与问题

原 WPF 实现首先读取 `.nyagekiProj`，随后根据其中的字符串路径任意读取谱面、音频；谱面中的 SVG 图片物件又会继续读取外部 SVG。Desktop 全权限文件系统通常允许这种调用链，但 Browser 无法假定任意路径已获授权，也不能由程序自行弹出或补办每个依赖文件的权限。

新设计必须把一次用户授权得到的“项目文件夹”作为项目全部文件 I/O 的权限边界。加载工程后，业务代码只能通过该目录能力访问项目工程、谱面、音频和 SVG，不能再把序列化字符串直接交给 `System.IO`。

## 3. 用户已提出的目标约束

以下内容先按已提出需求记录，后续问题只补足精确定义和异常行为：

1. 打开编辑器时由用户选择一个“项目文件夹”。
2. 程序递归查找项目文件夹中的 `.nyagekiProj`。
3. 只有一个工程文件时直接使用；存在多个时弹出对话框供用户选择。
4. 工程引用的谱面和音频必须位于项目文件夹或其子文件夹中；越界时项目加载失败并提示用户。
5. 【已撤出当前范围】原目标要求谱面中 SVG 图片物件引用的 SVG 同样位于项目文件夹或其子文件夹中；SVG 物件整体停用期间不执行该检查。
6. 【已撤出当前范围】原目标要求外部 SVG 复制到项目内的 `autoImport/svgFiles/` 后再引用；导入器代码虽保留，但当前没有可达入口。
7. 需要用户选择谱面保存位置时，目标只能位于项目文件夹或其子文件夹；越界时提示，并允许用户决定是否重试。
8. “快速打开音击谱面”暂时从跨平台 Core 流程中注释或禁用，之后再考虑仅放入 Desktop。
9. 禁止通过内存型 `ISimpleFile` 适配器保存完整文件副本；需要保留文件能力时直接持有句柄或流，正式方案由项目会话统一管理。

## 4. 实现前代码事实（历史基线）

本节记录访谈开始时的代码状态，用于解释后续决策来源，不代表 0 节所述首轮实现后的现状。

### 4.1 工程加载仍以本地路径为中心

- `FumenVisualEditorViewModel.Load(string)` 使用 `File.Exists` 检查工程路径。
- `EditorProjectDataUtils.TryLoadFromFileAsync` 使用 `File.ReadAllBytesAsync` 读取工程，并以 `.nyagekiProj` 所在目录拼接谱面和音频路径。
- 谱面通过 `File.OpenRead` 加载；音频路径缺少运行时文件句柄时会构造 `LocalSimpleFile`。
- 这些调用无法作为 Browser 项目加载的基础。

### 4.2 现有目录抽象不足以完成目标流程

- `ISimpleDirectory` 当前只提供已加载子目录、子文件和只读查询，没有创建目录、创建文件、复制导入或刷新枚举能力。
- `AvaloniaStorageProviderFileSystemBuilder.LoadFromAvaloniaStorageFolder` 能递归建立目录快照。
- `FileDialogHelper.OpenDirectoryAsync` 当前调用的是 `LoadRootFromAvaloniaStorageFolder`，只包装所选根目录，并不递归枚举子项。因此当前入口无法发现任何 `.nyagekiProj` 或项目资源。
- `AvaloniaStorageProviderSimpleDirectory` 内部持有 `IStorageFolder`，但没有向业务抽象暴露创建子目录、创建文件或重新枚举的能力。
- Avalonia 11.3.18 的 `IStorageItem` 暴露 `Path`、`GetParentAsync()`、书签、移动和删除，但没有稳定的“两个句柄是否指向同一项”或“某项是否为已授权目录后代”的跨平台 API；其文档还明确 Browser 的 `Path` 可能是相对 URI。
- 因此，独立系统文件选择器返回的文件句柄不能仅靠字符串路径在所有平台可靠证明其属于已选择的项目目录。

### 4.3 SVG 路径仍会逃逸到本地文件系统

- OGKR 与 Nyageki 的 SVG 图片命令解析器在没有内嵌内容时，会把谱面中的路径直接包装成 `LocalSimpleFile`。
- SVG 序列化目前只写入 `LocalPath ?? FullPath`；已经撤销把非本地 SVG 内容嵌入谱面的过渡实现。
- 属性面板选择 SVG 后直接保留文件选择器返回的 `ISimpleFile`，仍然没有导入项目目录。
- 因此 SVG 的解析、运行时绑定、修改和序列化都需要改为项目上下文感知。

### 4.4 文件句柄所有权

- `EditorProjectDataModel` 当前只保存 `AudioFile` 与 `FumenFile` 两个运行时 `ISimpleFile`，替换和关闭项目时负责释放。
- 新方案还需要持有项目根目录能力，以及可能由谱面对象持有的 SVG 文件能力；必须统一定义所有权和释放顺序。

### 4.5 Gekimini 已加入异步最近记录有效性链路，但项目文件夹书签仍未接入

- 最新 `IEditorProvider` 已增加 `Task<bool> CheckIsValid(RecentRecordInfo)`；`ICommandHandler.Update()` 和列表 `Populate()` 也已改为异步任务。
- `OpenRecentFileCommandHandler` 在菜单列表构建和命令状态更新时等待 Provider 检查，捕获检查异常并将命令禁用；`TargetableCommand` 在异步状态完成后触发 `CommandManager` 重新查询。
- Ongeki 启动页的最近项目按钮已改用同一个 `TargetableCommand`，因此菜单与启动页现在都能由 `CheckIsValid` 返回值控制可点击和置灰，不再需要两套应用层判断。
- 当前 Fumen Provider 的 `CheckIsValid` 仍固定返回 `false`，所以所有 Fumen 最近项都会置灰；`TryOpen(RecentRecordInfo)` 也仍把 `LocationDescription` 当本地工程路径，尚未实现 D31 的“目录书签 + 工程定位符”。
- Gekimini 示例只实现文件书签，并通过全局主 `App.TopLevel.StorageProvider` 调用 `OpenFileBookmarkAsync()`；检查代码没有释放恢复得到的临时 `IStorageFile`。Fumen 文件夹检查不得复制这个资源泄漏。
- 当前每次菜单 `Populate` 和命令 `Update/CanExecute` 都可能再次调用 Provider，尚无按记录缓存、并发合并、取消或失效状态持久化；书签恢复成本会被重复支付。
- `RecentRecordInfo` 仍没有稳定 ID，`DefaultEditorRecentFilesManager` 仍以可变的 `LocationDescription` 计算附加数据键和判断重复；D31 的组合数据不能安全地把该字段仅当显示文本使用。
- 主解决方案在这次代码更新后编译通过，结果为 0 个错误；现有构建警告中未发现由 `CheckIsValid` 接口导致的编译失败，但没有覆盖最近记录异步状态与书签释放的专项测试。

## 5. 初步目标模型

以下是讨论起点，不视为最终决策：

```text
用户选择项目文件夹
        |
        v
ProjectFolder / ProjectFileSystem（唯一权限边界）
        |
        +-- 递归发现并选择 .nyagekiProj
        +-- 解析工程内相对路径
        +-- 加载谱面与音频
        +-- 解析并绑定 SVG 文件
        +-- 在 autoImport/ 下创建和复制文件
        +-- 验证所有保存目标仍在项目边界内
```

建议引入一个编辑器项目运行时上下文，至少区分：

- 用户授权的项目根目录；
- 当前选择的 `.nyagekiProj` 文件；
- `.nyagekiProj` 相对路径的解析基准目录；
- 规范化后的工程、谱面、音频和 SVG 相对定位符；
- 项目内查找、创建、复制、覆盖和边界验证能力。

序列化模型只保存可移植的相对定位符；平台文件句柄只存在于运行时上下文，不进入 `.nyagekiProj` 或谱面序列化。

## 6. 已确认决策

### D1. 项目权限边界与相对路径基准分离

- 用户最初选择的项目文件夹始终是项目全部读写的权限边界。
- 所选 `.nyagekiProj` 的父目录是工程内相对路径的解析基准。
- 相对路径允许包含 `..`，但规范化后的最终目标必须仍位于用户选择的项目文件夹内。
- 路径越界、无法规范化或无法解析到项目目录树中的文件时，按项目错误处理。
- 保存工程时，音频和谱面定位符继续写成相对于 `.nyagekiProj` 父目录的路径，以兼容现有工程语义。

### D2. 打开目录中不存在工程文件时直接失败

- “打开项目文件夹”递归扫描后没有发现任何 `.nyagekiProj` 时，直接结束打开流程。
- 向用户明确提示所选项目文件夹中不存在 `.nyagekiProj`。
- 不自动创建工程，不提供“在此新建”快捷操作，也不对所选目录执行任何写入。
- 新建项目流程不从该错误分支推导，若后续需要则单独设计。

### D3. 多工程候选必须由用户明确选择

- 递归发现多个 `.nyagekiProj` 时，每次都弹出候选对话框，不记忆或自动代选。
- 候选项显示相对于用户所选项目文件夹的完整相对路径，以区分不同子目录中的同名文件。
- 候选按相对路径进行不区分大小写的稳定排序，不能依赖平台目录枚举顺序。
- 初始不默认选中任何候选；只有用户明确选择后才能确认。
- 用户取消时静默终止本次打开，释放已经取得的项目目录及文件句柄，不显示错误消息。
- 本条适用于只提供项目文件夹、没有同时提供已选工程标记的普通打开流程；D31 的最近记录已经保存用户先前明确选择的工程定位符，恢复成功时可以直接打开该工程，不再次弹出多工程选择。

### D4. 绝对路径只允许 Desktop 在项目边界内迁移

- 新保存的 `.nyagekiProj` 和谱面只写相对定位符，不再产生绝对路径。
- Core 加载逻辑不把序列化的绝对路径直接交给 `System.IO`。
- 平台能够取得项目根目录真实 `LocalPath` 时，只有规范化后的绝对路径确实位于项目根目录内，才允许转换为相对于 `.nyagekiProj` 父目录的定位符并继续加载。
- 通过该兼容分支加载后，项目应标记为需要迁移保存。
- 绝对路径指向项目根目录外时，即使 Desktop 对其具有系统权限，也按越界项目错误处理。
- Browser 或其他没有 `LocalPath` 的后端遇到绝对路径时，提示工程需要先迁移，不进行文件名、路径后缀或目录结构猜测。

### D5. 项目定位符采用跨平台统一逻辑路径

- 序列化统一使用 `/` 作为路径分隔符，不产生平台相关的 `\`。
- 加载时兼容读取 `\`，规范化后在内存中统一使用 `/`。
- 定位符必须是无盘符、无 URI scheme、无前导 `/` 的相对路径；旧绝对路径只进入 D4 的兼容迁移分支。
- `.` 路径段被消除；`..` 可以参与解析，但最终结果必须通过 D1 的项目根目录边界检查。
- 项目逻辑路径在所有平台使用 `OrdinalIgnoreCase` 查找，不能随底层文件系统改变语义。
- 保存时采用目录枚举所得文件的实际大小写，不强制改成全小写或全大写。
- 同一次路径解析如果存在两个仅大小写不同且都匹配的候选，报告路径大小写冲突，不任意选择。

### D6. 加载采用无副作用完整预检

- 加载器先解析 `.nyagekiProj`，校验音频和谱面定位符，再在谱面可解析时枚举并校验全部 SVG 图片引用。
- 预检阶段尽量收集所有当前可发现的问题，不在第一个错误处立即退出。
- 谱面不可读取或不可解析时记录谱面错误，并明确说明其内部 SVG 校验未执行。
- 诊断项应包含错误类型、原始定位符、规范化结果和引用来源，最终统一展示。
- 音频、谱面和外部 SVG 都是必需依赖；存在任一错误时整体加载失败，不创建部分可用的编辑器文档。
- 错误界面提供“重新扫描”，允许用户在外部修复已授权目录后重试，无需重新选择项目文件夹。
- 预检不修改、复制或保存项目文件；只有全部校验成功后才提交运行时项目状态。

### D7. 保留旧内嵌 SVG，但新修改统一改为项目文件引用

- 有有效内嵌 SVG 内容时，它是自包含资源，不访问路径字段指向的外部文件。
- 路径字段只作为原始名称或来源提示；内嵌内容优先于路径。
- 内嵌内容损坏时记录 SVG 解析错误，不静默回退到外部路径，项目预检失败。
- 加载旧内嵌 SVG 时不自动写入 `autoImport/`。
- 未修改的内嵌 SVG 保存时继续保持内嵌形式。
- 用户新选或替换 SVG 时，统一导入项目目录并改用项目相对路径，新操作不再产生内嵌 SVG。
- 旧内嵌 SVG 外置应由后续独立、显式的迁移操作完成。

### D8. SVG 选择分为项目内引用与外部导入

- “从项目选择”使用应用内项目文件浏览器，只展示已挂载项目目录内的 SVG；选中后直接引用可信相对路径，不复制文件。
- “从外部导入”使用系统文件选择器；选中的文件始终复制到 `autoImport/svgFiles/`，再引用导入副本。
- Desktop 与 Browser 对外部导入采用相同语义，不因 `LocalPath` 是否可用而改变行为。
- UI 可以使用一个 SVG 选择对话框，在项目文件树旁提供明确的“从外部导入”命令，不要求暴露两个并列属性按钮。
- 不使用文件名、URI、父目录字符串、内容相同或平台路径猜测外部选择项是否属于项目。

### D9. 外部 SVG 采用内容寻址且不可覆盖的导入规则

- 导入前完整读取并验证内容是可解析的 SVG；验证失败时不创建项目文件，也不修改物件。
- 对内容计算完整 SHA-256，目标名称使用清洗后的原始 stem 和完整哈希，例如 `logo.<sha256>.svg`。
- 导入前在 `autoImport/svgFiles/` 查找相同完整哈希；再次比对内容一致后复用已有文件，即使原始文件名不同也不重复写入。
- 同名但内容不同的文件产生不同哈希目标，绝不覆盖已有导入文件。
- 目标名称已存在但内容与哈希不符时，按导入目录损坏或哈希冲突报错，不覆盖、不随机改名继续。
- 文件写入成功并重新读取、解析验证后，才切换 SVG 物件引用；失败或取消时保持原引用。
- 本次创建或写入失败时删除未完成目标；导入前已经存在的文件不能由失败清理删除。

### D10. `autoImport` 首版只增不自动清理

- 保存、替换 SVG、删除物件、关闭编辑器和自动保存都不删除 `autoImport/svgFiles/` 中的文件。
- 内容哈希去重用于限制重复导入，但允许目录保留不再使用的孤立文件。
- 首版不要求实现清理 UI。
- 后续清理必须由用户显式触发，并扫描所选项目根目录内所有 `.nyagekiProj` 及其可解析谱面引用，不能只依据当前编辑器。
- 任一相关工程或谱面无法解析时，阻止自动判断“未引用”，避免误删。
- 清理执行前展示候选文件、大小和扫描范围；优先使用隔离目录或平台回收能力，永久删除需要再次明确确认。

### D11. 项目会话采用实时异步目录能力与可重建索引

- 项目作用域文件系统/会话对象持有用户已授权的根目录能力，不能以 `LocalPath` 作为基础访问方式。
- 核心能力包括异步枚举、相对路径查找、创建目录、创建或覆盖文件、从流复制、删除未完成文件和重新扫描。
- 打开项目时递归扫描目录元数据，建立大小写不敏感的相对路径索引，但不预读全部文件内容。
- 索引只代表一次扫描代次，不是永久事实来源。
- 用户执行“重新扫描”时丢弃旧索引并重新枚举授权目录。
- 程序自身成功创建、导入或保存文件后，主动更新或失效对应索引项。
- 业务解析器只接收项目会话解析出的文件或流，不自行拼接系统路径，也不把目录快照当作权限证明。
- 当前 `ISimpleDirectory` 是扩展还是由新接口替代，留到实现设计阶段决定。

### D12. 项目组成文件使用应用内受限保存浏览器

- 已有工程或谱面直接覆盖项目会话中已绑定的文件，不重复选择目标。
- “另存谱面”“新建谱面文件”等操作使用应用内项目目录树，只能选择项目根目录及子目录。
- 对话框支持项目相对文件名输入和必要的新建子目录能力，返回规范化项目定位符，不返回系统路径。
- 文件扩展名必须由目标谱面序列化器支持。
- 目标存在时明确确认覆盖；大小写冲突按 D5 报错。
- 用户取消时保持原文件绑定和编辑器状态。
- 项目工程、谱面、音频依赖和 SVG 资源不通过系统 SaveFilePicker 保存到项目外。
- 独立于项目的格式转换、WAV 导出等输出仍可使用系统保存选择器。

### D13. 所有项目受同一个应用级全局 I/O 门约束

- 任意时刻只能有一个项目执行受控项目 I/O；其他项目必须排队等待。
- 全局异步独占门覆盖项目目录枚举、重新扫描、工程/谱面/SVG/音频内容读取、项目内创建与导入、保存、回滚和恢复副本生成。
- 一次加载在取得门后完成预检所需的全部项目文件读取；音频和 SVG 转成内存数据后，后续播放、绘制和纯内存编辑不再占门。
- 纯 CPU 序列化可以先在门外完成；读取备份和写入提交必须位于同一次持锁区间。保存不比较磁盘内容代次或外部修改指纹，按 D26 保持后保存者覆盖语义。
- 文件夹或文件选择器、确认对话框和错误对话框不得在持锁期间等待用户输入；用户完成交互后再排队取得门。
- 等待全局门必须支持取消，并在 UI 中显示正在等待其他项目 I/O。
- 不允许锁内重入请求同一全局门；项目服务需要传递当前 I/O 上下文，避免死锁。

### D14. 完整保存采用可回滚的最佳努力多文件事务

- 第一次写入前完成工程与谱面的全部序列化、路径规范化和校验；任一序列化失败时不修改目标文件。
- 写入前读取全部待覆盖文件的原始字节，作为本次事务的内存回滚副本；工程和谱面按可接受内存规模处理。
- 先提交谱面，最后提交 `.nyagekiProj`，让工程描述文件作为最后提交标志。
- 每个文件通过项目文件系统的替换 API 写入；后端支持原子替换时使用原子实现，不支持时明确退化为流式替换。
- 后续写入失败时，按相反顺序最佳努力恢复已经修改的文件。
- 回滚成功仍报告保存失败并保持编辑器脏状态。
- 回滚失败时报告高优先级“不一致保存”错误，列出成功、失败和恢复失败的文件，并把可获得的新旧序列化内容写入恢复存储。
- 只有全部目标提交成功后才清除脏状态、更新文件绑定和标题。
- 整个正式提交和回滚阶段受 D13 的应用级全局 I/O 门约束。

### D15. 自动保存只生成恢复快照

- 自动保存不覆盖项目目录中的 `.nyagekiProj`、谱面或 SVG。
- 仅项目处于脏状态时生成恢复快照；成功后不清除脏状态。
- 快照写入应用恢复存储，包含恢复编辑状态所需的工程模型、谱面序列化内容和项目定位信息，不复制未修改的音频或 SVG 大文件。
- 手动正式保存成功后，清理或标记早于该保存代次的快照。
- 再次打开同一项目时，如果恢复快照比正式文件新，提示用户恢复、忽略或查看时间信息。
- 自动保存以低优先级等待 D13 全局门；已有加载或手动保存排队时允许跳过本轮，不堆积任务。
- 自动保存失败只显示非阻塞状态并记录日志，不中断用户编辑。

### D16. 关闭脏项目采用保存、放弃、取消三态

- “保存并关闭”执行 D14 正式保存；成功后删除旧恢复快照并关闭，失败则保持文档打开。
- “放弃修改”需要再次明确确认；确认后关闭文档并删除该编辑会话对应的恢复快照。
- “取消”保持文档和恢复快照不变。
- 关闭干净文档不弹确认，释放项目会话、目录和文件句柄、音频播放器及 SVG 运行时资源。
- 应用正常退出时按文档顺序处理脏项目，每次正式保存受 D13 全局门约束。
- Browser 页面被直接关闭或刷新时不依赖异步关闭确认完成，数据保护依赖最近一次成功的恢复快照。

### D17. 快速打开音击谱面暂时退出跨平台 Core

- 当前跨平台 Core 暂停或注释“快速打开 `.ogkr` / `.nyageki`”入口和相关自动音频发现流程。
- `FumenVisualEditor` 的标准打开入口只接受用户授权的项目文件夹。
- 快速打开不作为本轮项目文件夹 I/O 重构的兼容分支。
- 后续若恢复，优先作为 Desktop 专属功能单独设计和注册，不能让其本地路径假设重新进入 Core。

### D18. 允许把项目外部音频导入项目目录

- “从项目选择音频”使用应用内项目浏览器，直接绑定项目相对定位符。
- “导入外部音频”使用系统文件选择器；选定后将音频复制到 `autoImport/audioFiles/`，项目只绑定导入后的副本。
- 系统文件选择器等待用户期间不持有 D13 全局 I/O 门；用户确认后，源文件验证、流式复制、项目副本验证和绑定切换在全局门约束下执行。
- 导入按流复制并显示字节进度，支持取消，不允许为了导入而一次性把整个音频读入内存。
- 可选扩展名来自当前平台实际音频能力；扩展名通过后仍必须从项目副本完成真实解码并读取时长，不能只凭后缀认定成功。
- 只有复制和解码验证全部成功后才替换当前音频绑定；失败或取消时保留原绑定。
- 失败清理只删除本次创建且未完成的导入文件，不得覆盖或删除既有文件。
- 导入音频的最终命名、重复内容复用和冲突策略另行确认。

### D19. ACB 与其外置 AWB 作为原子文件包处理

- Desktop 导入和加载 `.acb` 时必须先识别它使用内嵌 AWB 还是外置 AWB；Browser 不声明支持 ACB，也不显示 ACB 导入选项。
- 使用内嵌 AWB 的 ACB 只导入和校验 `.acb`。
- 使用外置 AWB 的 ACB 必须在提交导入前定位实际伴随 `.awb`；伴随文件不存在或不可读时直接报错，不产生项目文件。
- `.acb` 与 `.awb` 一起复制到 `autoImport/audioFiles/` 下的独立包子文件夹，保留解码器要求的文件名和相对关系；工程音频定位符指向包内 `.acb`。
- 如果外置引用无法安全重建在包目录内，例如必须越过包目录或依赖无法确定的绝对位置，则拒绝导入，不在本轮重写 ACB 二进制内容。
- 必须从导入后的 `.acb` 完成解码验证，并保证伴随文件解析结果仍位于项目根目录内；验证通过后才切换工程绑定。
- 任一复制、验证或取消失败时，只删除本次新建且尚未提交的整个包，不影响已有导入。
- 加载既有项目时同样预检外置 AWB；它必须存在于项目根目录内，否则项目整体加载失败并列出该隐藏依赖。

### D20. 外部音频采用流式内容寻址并保持导入区追加式

- 外部源复制到项目内暂存项的同时增量计算完整 SHA-256，不把整个音频载入内存。
- 普通音频最终命名为 `safeStem.<完整SHA256><小写扩展名>`；`safeStem` 使用项目定义的跨平台固定规则清洗和限长，不依赖运行平台的非法字符表。
- 普通音频去重键为“完整内容哈希 + 规范化扩展名”；相同内容和扩展名即使原文件名不同也复用已有项目副本。
- 外置 AWB 的 ACB 文件包以确定顺序组合“相对文件名 + 各文件完整哈希”得到包哈希；目录命名为 `safeStem.<包哈希>/`，内部保留 ACB/AWB 所需名称关系。文件名关系不同的包不强行合并。
- 查找可复用项时必须重新校验候选内容和解码结果；名称声明的哈希与实际内容不符、包缺文件或内容损坏时直接报错，绝不覆盖该既有项。
- 同名但内容不同会因哈希不同生成不同目标，不弹覆盖确认；同内容命中复用时不重复复制。
- 暂存项仅在完整复制、哈希和解码验证成功后由项目文件服务提交；后端不支持原子移动时使用可检测、可清理的退化流程。
- 更换工程音频后，旧的 `autoImport/audioFiles/` 文件或文件包不自动删除，避免破坏根目录内其他 `.nyagekiProj`；后续仅通过显式全项目引用扫描清理。
- 项目文件系统服务需要补充独占创建、暂存提交和目录级失败清理能力，不能退回本地 `Path`/`File` 操作。

### D21. 跨平台 Core 拒绝项目外谱面，谱面包导入仅由 Desktop 实现

- `FumenVisualEditor` 的标准工程设置只通过应用内项目浏览器选择谱面；项目外谱面直接报错，可重试或取消，不复制文件，也不修改工程绑定。
- 系统文件选择器、拖放和旧路径迁移不能绕过该规则；新建空谱面和“另存为”继续按 D12 在项目内部创建。
- 跨平台 Core 不提供把单个外部谱面直接绑定为项目谱面的兼容分支，也不创建通用的 `autoImport/fumenFiles/` 单文件复制流程。
- “导入谱面包”限定为 Desktop 功能，只在 Desktop 注册命令、入口和外部源目录访问实现；Browser 不显示入口，也不提供降级版。
- Desktop 谱面包导入必须由用户明确选择外部源文件夹，再从该能力范围内选择谱面、收集全部文件型 SVG 依赖、按 D9 导入 SVG、重写为项目定位符，并以全有或全无事务把谱面写入当前项目根目录。
- 外部谱面或其任一依赖缺失、越过已选源目录、无法解析或无法安全重写时，整个导入失败，原项目绑定保持不变。
- Desktop 导入编排仍受 D13 全局 I/O 门约束；等待源文件夹选择和确认对话框时不得持有该门。
- 谱面包导入不在 Browser 实现，也不能让 Desktop 本地路径假设进入跨平台项目加载 Core。

### D22. 项目依赖禁止经过符号链接、目录联接或挂载点

- Desktop 选择的项目根本身若是符号链接、目录联接或挂载点，直接报错并要求用户选择真实目录。
- 递归扫描不进入任何目录链接；链接后面的 `.nyagekiProj` 不计入候选，并防止链接形成递归循环。
- 未被项目引用的链接条目只记录一次可见警告并从项目浏览器隐藏，不因无关链接让整个项目加载失败。
- 工程、谱面、音频、SVG 或 ACB/AWB 的任一路径段或最终文件若是链接，预检将其列为错误；保存、新建和导入同样拒绝链接目录或链接文件目标。
- Desktop 平台适配器必须通过真实文件系统元数据识别符号链接、联接和挂载点，不能只依赖词法路径比较；无法可靠分类的重解析点按链接处理。
- Browser 或其他没有本地路径/链接元数据的后端，只接受从已授权项目根目录句柄逐级取得的子句柄；外部 URI、伪造路径或其他选择器返回的句柄不能冒充项目内部文件。
- 对可能存在外部别名的普通硬链接，可写工程文件必须通过“创建新内容后替换目录项”提交，不能原地截断；后端只能原地写且无法证明隔离时，拒绝覆盖并要求另存为项目内新文件。

### D23. 项目发现不设数值硬上限，采用流式遍历和按需索引

- 不设置目录深度、枚举条目数量、`.nyagekiProj` 候选数量或固定扫描超时上限。
- 第一阶段以显式栈或队列流式遍历目录，只保留项目候选定位符、当前遍历状态和少量统计，不为每个普通文件创建长期对象。
- 多个项目候选通过可虚拟化列表展示，不要求预先构建整个项目文件树。
- 用户选定项目后，只解析该工程并按定位符逐级解析音频、谱面、SVG 和 ACB/AWB 依赖；项目内部浏览器展开目录时再按需枚举并缓存该目录。
- D11 的“可重建元数据索引”定义为增量缓存：重新扫描使相关缓存失效，后续访问按需重建，而不是每次完整复制整棵目录树。
- 扫描超过 300 毫秒显示非百分比进度和已扫描统计，并始终允许取消；不因设备较慢自动超时。
- D22 的链接禁止与循环防护继续生效，禁止通过链接无限遍历。
- 任一目录无法枚举时，项目发现结果视为不完整，报告具体相对位置并整体失败；取消同样不能从部分候选继续打开。
- 取消或失败时释放本轮子句柄和临时状态，但保留已授权项目根句柄以便重试。
- 扫描、按需枚举和依赖读取仍受 D13 全局 I/O 门约束，每次操作完成、失败或取消后立即释放。

### D24. 不设固定资源预算，高内存压力只记录日志

- 不设置预定义的文件 MB、音频时长、对象数量、解码内存或 Desktop/Browser 差异阈值，也不因资源估算主动拒绝项目。
- 工程 JSON 直接从流反序列化；谱面逐行解析；外部复制、哈希和保存使用固定大小缓冲区，移除不必要的完整输入副本。
- 音频按 D27 在项目加载阶段完整解码为 PCM 并常驻内存；本条的流式读取和有界缓冲要求不适用于最终 PCM，但解码管线应避免除必要最终 PCM 外的额外完整副本。
- 播放、跳转和波形使用当前编辑器拥有的 PCM 缓冲，不建立临时磁盘缓存，也不在加载完成后继续读取项目音频文件。
- SVG 直接从流解析并避免重复字节副本；同一项目 SVG 的不可变解析资源允许由会话共享和统一释放。
- 解析和 I/O 仍响应用户取消，但运行时报告高内存压力时只写日志警告，不主动取消加载，也不弹出资源警告对话框。
- 若随后发生实际分配、解析或解码异常且进程仍可继续，按普通项目加载失败处理并遵守 D6，不发布部分编辑器状态。
- 明确保留残余风险：Browser、Skia 原生内存或第三方解码器可能在没有可靠压力信号时耗尽资源，极端输入可能直接终止标签页，无法保证友好报错或完成恢复快照。

### D25. 文件能力与运行时资源统一由异步项目会话持有

- 每个已打开编辑器独占一个 `IProjectSession : IAsyncDisposable`；会话拥有授权项目根、选中工程定位符、会话取消源、按需目录缓存和资源缓存。
- `EditorProjectDataModel` 移除 `[JsonIgnore]` 的 `AudioFile`、`FumenFile` 及 `DisposeRuntimeFiles()`；模型只保存项目定位符和业务数据，克隆、迁移、序列化不执行 I/O 或转移句柄。
- `SvgImageFilePrefab` 保存规范化项目定位符或稳定资源键，不直接拥有 `ISimpleFile`；对象删除或复制不自行打开、复制或释放底层文件能力。
- 短期读取在单次方法内取得流并通过 `await using` 释放；需要跨调用存活的资源使用 `IProjectFileLease` 或等价租约表达，租约只能由所属会话创建。
- 音频文件只在加载或更换音频阶段短期打开；完整 PCM 建立后关闭全部项目音频文件。播放器拥有 PCM 缓冲和播放资源，不持有项目文件租约。
- SVG 运行时缓存以规范化定位符和文件代次为键，共享不可变源或解析资源；各 SVG 对象只持引用计数句柄或会话资源引用，最终资源由会话统一释放。
- 工程设置或加载流程创建候选会话；失败或取消时异步释放，成功时只向编辑器转移一次所有权，不能由对话框和编辑器共同拥有。
- 关闭顺序固定为：取消并等待会话活动任务，停止并释放音频播放器，释放 SVG 对象引用及资源缓存，释放剩余文件租约和目录缓存，最后释放项目根能力。
- 关闭确认完成后再异步释放；`OnViewBeforeUnload` 不做同步阻塞 I/O。释放流程幂等，异常写日志并继续释放其余资源。
- 属性 setter 不执行 `.GetAwaiter().GetResult()` 文件读取；资源变更通过显式异步命令或会话服务完成。

### D26. 允许同一项目打开多个独立编辑器，并保持后保存者覆盖语义

- 同一 `.nyagekiProj` 可以在单进程内打开多个编辑器；每次打开创建独立的 `IProjectSession`、工程模型、谱面模型、撤销历史和脏状态。
- 不建立项目身份唯一注册表，不因项目已打开而激活已有编辑器，也不自动创建只读副本。
- D13 全局 I/O 门只负责串行化实际保存执行顺序；先取得门的保存先提交，后取得门的保存随后提交并可覆盖前一次结果。
- 保存前不比较加载时内容指纹、时间戳、版本标识或其他外部修改代次；不因另一个编辑器、程序实例或外部工具已经修改文件而阻止保存。
- 每一次保存仍独立执行 D14 的序列化、备份、提交和最佳努力回滚，后保存者覆盖不允许绕过单次事务完整性。
- 一个编辑器保存成功后，其他打开同一项目或共享谱面的编辑器不自动重载、不更新基线、不标记冲突，也不清除各自脏状态。
- 多个编辑器最终写入结果由用户触发保存的实际先后顺序决定，保持原项目行为；应用不提供自动合并或冲突提示。

### D27. 音频在项目加载阶段完整解码为 PCM 并常驻内存

- 项目加载在 D13 全局 I/O 门内打开音频及必要的 ACB/AWB 依赖，完成解码、目标采样率转换和声道转换，生成完整 PCM 内存缓冲后关闭全部项目音频文件。
- 播放、暂停、跳转和波形直接使用 PCM，不再产生项目目录 I/O，也不需要应用临时音频缓存或长期音频文件租约。
- 每个编辑器拥有自己的 PCM 缓冲；D26 允许同一项目打开多个编辑器时，同一音频可以在内存中存在多份，不跨会话共享。
- 更换音频时先完整解码新音频；成功后原子切换播放器并释放旧 PCM，失败或取消时继续使用旧 PCM 和旧项目绑定。
- 不设置音频文件大小、时长或 PCM 内存上限；高内存压力只按 D24 写日志，实际内存不足可能导致加载失败，极端情况下 Browser 标签页可能直接终止。
- 在最终 PCM 本身不可避免之外，解码实现应减少峰值内存和不必要的完整中间副本，但这属于实现优化，不改变完整 PCM 常驻内存的行为契约。

### D28. `.nyagekiProj` 保持当前 `0.5.4` 版本

- 用户撤回先前升级到 `0.6.0` 的决定；Avalonia 继续将 `EditorProjectDataModel.VERSION` 保持为当前 `0.5.4`。
- 不新增 `0.6.0` 序列化器，不设置待格式迁移状态，也不因新的项目文件夹 I/O 规则触发版本升级提示或旧版兼容备份。
- 现有 `0.5.2 -> 0.5.4` 迁移继续保留；项目正式保存仍写 `Version: 0.5.4`。
- 音频、谱面和 SVG 定位符仍按 D1、D4、D5、D7 的新边界规则读取、校验和规范化，但这些行为变化不通过项目版本号区分。
- 旧 WPF 会继续把该项目识别为受支持的 `0.5.4`。它可能按旧路径规则读取项目，尤其可能找不到或错误解析新的 SVG 相对定位符；该风险不通过版本门阻止。
- 不承诺新 Avalonia 与旧 WPF 能对同一项目交替保存后保持完全一致的资源解析结果；若后续要求兼容，必须修改旧 WPF 的路径解析逻辑，而不是依赖项目版本区分。

### D29. SVG 定位符统一以用户选择的项目根目录为基准

- `.ogkr` / `.nyageki` 中非内嵌 SVG 的定位符保存为项目根目录相对路径，不以谱面文件或 `.nyagekiProj` 的父目录为基准。
- 定位符继续遵守 D5：使用 `/`、无盘符、无 URI scheme、无前导 `/`，并在保存时采用项目目录枚举所得的实际大小写。
- 项目会话直接以该定位符查询项目根索引并执行 D1 边界校验；解析器不能把谱面字符串直接交给 `File.Exists`、`Path.GetFullPath` 或 `LocalSimpleFile`。
- 项目内移动、改名或另存谱面时，不需要重写其 SVG 定位符；移动 SVG 文件本身时仍必须显式更新引用。
- `autoImport/svgFiles/` 的导入结果可直接作为最终 SVG 定位符，例如 `autoImport/svgFiles/logo.<sha256>.svg`。
- 旧项目中的绝对 SVG 路径按 D4 处理；旧的相对 SVG 字符串一律按项目根基准解释，不回退尝试谱面父目录、进程工作目录或本地系统路径。
- 谱面脱离项目会话后不能独立解析外部 SVG，这与 D17 暂停跨平台 Core 快速打开谱面的范围一致。

### D30. 跨平台 Core 的工程编辑器只通过项目文件夹会话读写

- `FumenVisualEditorViewModel` 只接收预检成功且所有权明确的 `IProjectSession` 或等价 `ProjectOpenResult`；移除 `Load(string)`、`Save(string)`、直接模型打开和音频本地路径回退。
- 标准 `FumenVisualEditorProvider.TryOpen(document)` 只转发到对应 ViewModel；`FumenVisualEditorViewModel.Load()` 负责选择项目文件夹、扫描和选择 `.nyagekiProj`、创建候选会话，但仍只使用 Avalonia `StorageProvider` 取得的目录能力，不把路径退化为 `System.IO` 授权依据。
- 正式保存通过当前会话的 `SaveAsync()` 完成，工程和谱面目标来自会话定位符；另存谱面继续遵守 D12。
- `EditorProjectDataUtils` 的工程加载、完整保存和回滚职责迁入项目会话/项目存储服务；Core 删除以 `string` 为目标并直接调用 `File.*` 的工程相关方法。
- `EditorProjectFileManager` 作为纯 JSON 编解码器保留 `Stream` 接口；本地字符串路径便利重载从 Core 删除或移到 Desktop 适配层。
- 删除 `IFumenVisualEditorProvider.TryOpen(..., string)`；框架的最近记录入口不能再把 `LocationDescription` 直接当作路径。
- Desktop 命令行、未来快速打开谱面或其他本地工具可以在 Desktop 程序集中实现路径适配器，但不能重新暴露给标准跨平台编辑器流程。
- 实施顺序为：建立会话 API 与测试，迁移 Provider、ViewModel 和保存调用方，再删除旧入口；不长期保留能绕过权限边界的 `[Obsolete]` 包装。

### D31. 最近项目保存“项目文件夹书签 + 已选工程定位符”组合

- 每条 Fumen 最近记录保存一个带版本的专用数据结构，至少包含项目文件夹书签和用户上次选择的 `.nyagekiProj` 项目根相对定位符。
- 文件夹书签只负责恢复项目根目录的访问能力；工程定位符只负责在该授权目录中指定目标文件，两者不能互相替代。
- 工程定位符遵守 D5 的规范化规则并保存实际大小写，不保存或恢复系统绝对路径。
- 点击最近项目时先通过书签恢复 `IStorageFolder`，再从恢复的项目根解析指定工程定位符；定位符有效时直接打开该 `.nyagekiProj`，不重新显示多工程候选对话框。
- 恢复后仍执行 D6 的完整项目预检；“直接打开指定工程”只省略候选选择，不跳过音频、谱面、SVG 和边界校验。
- `RecentRecordInfo.LocationDescription` 只用于显示项目根和工程相对路径，不能作为加载地址或权限凭据；不透明书签保存在最近记录的数据区且不写日志。
- 成功打开或用户改选工程后更新书签与工程定位符组合；清除最近记录时同时清除其书签数据。
- 书签无法创建、恢复失败或工程定位符失效时的降级行为继续单独确认。

### D32. 已确认失效的项目文件夹书签保留记录但禁用打开

- 当程序尝试恢复项目文件夹书签并确认失败、过期或权限已撤销时，保留对应最近记录，不自动删除。
- 最近记录进入持久化的“书签失效”状态；列表中置灰显示，主点击命令禁用，不能继续尝试打开指定工程。
- 书签失效时不自动弹出文件夹选择器，不使用显示路径、本地路径或工程定位符猜测权限，也不改为扫描其他文件夹。
- 失效记录仍显示项目根说明和已保存的 `.nyagekiProj` 相对定位符，便于用户识别，并允许用户显式从最近列表删除。
- 应用重启后继续保持置灰，不把已确认失效的书签恢复成可点击状态。
- 是否提供独立的重新授权入口、何时主动验证尚未确认的书签，以及平台从一开始就无法创建书签时是否记录，继续分别决定。

### D33. 最近记录有效性检查和置灰能力在 Gekimini.Avalonia 框架层实现

- Gekimini 的 `IEditorProvider` 增加面向 `RecentRecordInfo` 的异步有效性检查契约；具体 Provider 负责理解自己保存在最近数据区中的书签、定位符和状态。
- Gekimini 统一维护每条最近记录的可用性状态，并让主菜单最近项、启动页最近项和其他未来入口共享同一结果，避免 OngekiFumenEditor 在多个 UI位置重复实现判断。
- Fumen Provider 的检查实现负责读取 D31 组合数据，通过当前 TopLevel 的 `IStorageProvider` 恢复项目文件夹书签，并按后续约定检查指定工程定位符。
- Gekimini 负责把无匹配 Provider、检查中、有效和失效状态映射到命令可执行性与视觉置灰；Provider 不直接操作菜单或启动页控件。
- 已确认失效状态按 D32 持久化；清除或更新最近记录时同步清除或重置对应状态。
- 最近记录需要稳定 ID 作为附加数据和可用性缓存的键，不能继续依赖可变的 `LocationDescription` 哈希。
- 精确接口返回类型、异步检查触发时机和同步 `PickDocumentProvider` 如何消费结果继续由 Q34 确认。

### D34. 首版采用现有异步 `Task<bool> CheckIsValid(...)` 链路

- 保留 Gekimini 当前 `IEditorProvider.CheckIsValid(RecentRecordInfo)` 契约，不以状态枚举、同步缓存或其他接口重构作为首版前置条件。
- `OpenRecentFileCommandHandler` 先按文件类型选择 Provider，再等待 Provider 校验；主菜单和启动页继续通过同一 `TargetableCommand` 结果控制可执行性与置灰。
- Fumen Provider 从以稳定最近记录 ID 为键的附加数据读取 D31 的“项目文件夹书签 + 工程定位符”，不得把 `LocationDescription` 当作加载路径或权限凭据。
- 校验通过书签恢复临时 `IStorageFolder`，完成检查后立即释放；`TryOpen(RecentRecordInfo)` 正式打开时重新恢复目录能力，并把句柄所有权转交 `IProjectSession`。
- 最近记录需要新增稳定 ID 或等价稳定数据键；显示名称和 `LocationDescription` 变化不得导致书签数据丢失、串用或无法清除。
- Provider 校验异常继续由 Gekimini 转为当前不可打开，并记录不包含书签正文的安全日志；哪些失败应同时写入 D32 的持久失效状态由 Q35 确认。
- 重复书签恢复、并发合并和结果缓存属于后续性能策略，不影响本决策的首版正确性边界。

### D35. 只有确定无效的最近记录才持久化置灰

- `CheckIsValid` 的所有失败在当前界面上都返回 `false`，但只有能够证明最近记录自身已经无效的结果才写入 D32 的持久失效状态。
- 附加数据缺失或损坏、数据版本无法解析、记录明确没有可用书签，或者存储服务已就绪时书签恢复明确返回空，属于确定失效。
- 尚未取得所属 GUI `TopLevel`、`StorageProvider` 暂时不可用、检查取消、应用正在关闭，以及不能证明书签已失效的恢复异常，均属于临时失败；它们只令当前入口置灰并保留后续重试机会。
- Fumen Provider 负责区分并持久化确定失效状态；Gekimini 的通用异常兜底只令本次检查返回 `false`，不得替 Provider 宣告记录永久失效。
- 已持久化为失效的记录不再重复调用书签恢复 API；临时失败可以在下一次命令状态更新时重新校验。

### D36. 最近记录轻量校验包含精确工程文件，但不加载工程

- 文件夹书签恢复后，`CheckIsValid` 同时按 D5 校验并解析已保存的 `.nyagekiProj` 项目根相对定位符。
- 目标必须是项目根目录内、扩展名正确且不经过 D22 禁止链接的普通文件；不递归扫描其他工程，不按文件名猜测，也不自动选择替代工程。
- 目标缺失、类型错误、定位符非法或越过项目根，属于最近记录自身的确定失效，按 D35 持久化置灰并保留记录供用户识别和删除。
- 轻量校验不反序列化 `.nyagekiProj`，不检查音频、谱面或 SVG，也不读取或解码任何项目资源。
- 用户真正执行打开后才运行 D6 的完整无副作用预检；工程内容损坏或依赖资源错误在该流程中报告。

### D37. 最近记录采用持久化 GUID；旧双设置直接切换，不迁移

- `RecentRecordInfo` 增加持久化的非空 `Guid RecordId`，新记录由 Gekimini 生成并保持稳定。
- 新附加数据只按 `RecordId` 关联；显示名称和 `LocationDescription` 不再参与附加数据的读取、写入或清除。
- 旧版本缺少稳定 ID，而且旧 Fumen 最近项只保存本地项目路径或文件书签，无法可靠转换成 D31 的“项目文件夹书签 + 工程定位符”。
- 首次读取旧格式时直接创建空的新版聚合存储，并清空旧的 `RecentRecordDataStoreSetting`；不生成 ID、不复制旧哈希键数据，也不尝试从本地路径补造权限。
- GUID 只标识最近记录及其附加数据，不代表项目业务身份，也不自动解决同一项目的最近记录去重。

### D38. 最近记录只在身份可证明相同时合并

- 从最近项打开时沿用其 `RecordId`；对应编辑器后续保存或刷新最近信息时更新同一记录、保留 ID 并将其移到列表顶部。
- 普通项目文件夹打开后，只有现有记录的书签不透明值与新书签完全相同，并且规范化工程定位符也相同时，Fumen Provider 才能复用该记录 ID。
- 无法精确证明相同时创建新的 GUID 记录，不使用 `LocationDescription`、本地路径、文件名或内容哈希推测合并。
- 同一物理项目在平台重新签发书签后可能出现少量重复最近项；这是为避免把不同项目的权限、定位符和失效状态错误合并而接受的结果。
- 未合并记录的附加数据彼此独立，删除或淘汰一条不得影响另一条。
- Gekimini 最近记录 API 区分“按 `RecordId` 更新并置顶”和“创建新记录”，移除当前按显示字符串隐式去重的行为。

### D39. 最近记录有效性按界面刷新代次缓存

- Gekimini 以 `RecordId` 为键管理当前校验代次，并合并同一记录在同一代次内的进行中任务和结果，不使用固定时间 TTL。
- 启动页构建或刷新、最近项目子菜单重新展开，以及应用从挂起状态恢复时开始新代次；每条记录在一个代次内最多调用一次 Provider。
- 菜单绑定、`CanExecute` 重查询和其他同代入口只消费共享结果，不因焦点、按键或命令重新查询而重复恢复书签。
- 已持久化失效的记录直接返回 `false`；成功和临时失败只缓存到当前代次，下一代次重新判断。
- 用户真正点击最近项时绕过旧代次成功缓存并执行一次权威校验，通过后才进入 `TryOpen` 和 D6 完整预检。
- 最近记录及其书签、工程定位符或失效状态发生变化时立即使对应缓存失效。
- 实际目录恢复和目标工程存在性读取继续受 D13 全局 I/O 门约束；协调层位于 Gekimini，Fumen Provider 只实现一次具体校验。

### D40. 首次无法创建文件夹书签时不新增最近记录

- 用户通过文件夹选择器取得的当前 `IStorageFolder` 仍交给 `IProjectSession`，项目正常打开、编辑和保存；无法持久书签只影响应用重启后的快捷恢复。
- 只有成功取得非空文件夹书签和有效工程定位符后，才创建新的最近记录及其附加数据。
- `CanBookmark == false`、书签保存明确返回空或保存失败时，不创建从产生起就无法点击的记录，也不以本地路径、显示文本或工程定位符替代权限能力。
- 书签保存异常只记录不含书签正文的安全警告，不阻止本次项目打开。
- 更新已有记录时，新书签保存失败不得用空值覆盖仍可用的旧书签；旧书签已确定失效时继续按 D32 保留并置灰。
- 平台以后具备书签能力时，用户重新通过普通文件夹入口打开项目即可创建可用的新最近记录。

### D41. 失效记录参与普通上限淘汰并完整清理附加数据

- 已确认失效的记录不因失效立即删除或改变排序权重，但继续计入 `RecordMaxCount` 并按普通最近访问顺序淘汰。
- D32 的“保留”表示校验失败不会立即静默删记录，不表示绕过数量上限永久保存。
- Gekimini 增加按 `RecordId` 删除单条记录的 API；禁用的打开命令不影响用户从独立操作删除该项。
- 单条删除、清空全部和上限淘汰都同步清除记录信息、稳定 ID 附加数据、持久失效状态及内存校验缓存。
- 最近记录管理器先计算保留和淘汰集合，再持久化并清理；不得继续只在写入时 `Take(RecordMaxCount)`，却把超额项留在内存和数据区。
- 旧键迁移残留只有在确认不再被任何记录引用后才能删除，异常时以保留孤立副本优先于误删仍在使用的数据。

### D42. 首版书签不做应用层加密，但禁止进入日志和诊断数据

- 文件夹书签按 Avalonia 的持久书签契约作为敏感不透明数据保存，不增加无法跨 Desktop 与 Browser 统一兑现的应用层加密。
- Desktop 依赖当前用户账户及文件权限保护应用设置；Browser 依赖浏览器同源存储边界，不宣称能够抵御本机管理员、同源恶意脚本或 XSS。
- Base64、JSON 字符串转义和哈希不视为加密，不能作为书签机密性保证。
- `LocationDescription`、记录名称、UI、异常消息、结构化日志字段、崩溃报告、恢复快照及诊断导出不得包含书签正文。
- Browser `SettingManager` 必须删除当前输出完整设置键值的日志；所有设置和最近记录路径只记录类型、`RecordId`、结果类别及不敏感工程定位符。
- D41 的删除、清空和淘汰同步删除书签数据；保留可替换的书签存储抽象，方便未来 Desktop 接入系统凭据库。
- 若未来要求 Browser 书签抵御同源脚本读取，则在引入用户口令或外部密钥前禁用 Browser 最近项目能力，不能用同源保存的自有密钥制造虚假安全性。

### D43. 最近记录采用带版本的聚合快照并直接切换

- `RecentRecordInfoStoreSetting` 版本设为 2，在同一设置对象中保存有序记录列表、按 `RecordId` 关联的 Provider 不透明数据和持久失效状态。
- 新建、更新并置顶、删除、清空、上限淘汰、附加数据变化和失效状态变化都先修改内存副本，再以一次 `SaveSetting` 提交完整快照；提交失败时继续使用旧快照。
- 加载时移除空 ID、重复 ID、孤立附加数据和孤立失效状态，并同步清理超过数量上限的记录及其全部关联状态。
- 按修订后的 D37 直接丢弃旧双设置数据，不实现旧哈希键到 GUID 的迁移或双读回退。
- Browser 以单个 `localStorage.setItem` 保存聚合对象；Desktop 把完整 `setting.json` 写入同目录 UTF-8 临时文件，刷新到磁盘后原子替换目标。
- 项目文件格式版本保持 D28 的当前 `0.5.4`；这里的版本 2 只属于 Gekimini 最近记录设置，不改变 `.nyagekiProj` 版本。

## 7. 暂缓事项

### Q17. 致命异常时，崩溃救援是否等待全局 I/O 门重新序列化全部编辑器？

当前 `FumenRescue` 会在崩溃路径中遍历编辑器并重新写出工程、谱面副本。如果异常发生在持有 D13 全局门的 I/O 内部，崩溃处理继续无限等待该门可能死锁；进程已经处于致命异常状态时，复杂 I/O 和序列化本身也不再可靠。

**建议答案：正常自动快照是主要恢复手段；崩溃处理只做有超时的最佳努力补充。**

- 致命异常处理绝不写入用户项目目录，不尝试正式保存或回滚用户文件。
- 已成功写入的最近自动保存快照始终保留，作为最低恢复基线。
- 崩溃处理可以尝试在很短的固定超时内取得 D13 全局门；立即取得时，按顺序为脏编辑器生成额外应急快照。
- 超时、锁不可用或任一序列化失败时立即放弃本次补充，不覆盖或删除已有快照，也不无限等待。
- 应急快照写入应用恢复存储，并标记为 crash generation；恢复界面显示其时间和是否可能不完整。
- 崩溃路径不弹交互对话框，只记录恢复位置和失败信息。
- 现有 `FumenRescue` 应并入统一恢复快照服务，避免维护两套不一致的工程/谱面恢复格式。

这样把可靠性放在平时的自动快照，而不是寄希望于进程已经失效后的复杂补救。

**状态：** 用户决定暂时搁置，后续另行讨论。本轮不形成崩溃应急快照决策；D15 的正常自动保存快照不受影响。

## 8. 访谈问题与回答记录

### Q23. 项目递归扫描是否采用统一硬上限，并在失败时禁止使用部分结果？

当前 `AvaloniaStorageProviderFileSystemBuilder` 会递归枚举整个目录并为所有条目创建内存对象，只支持取消令牌，没有进度、深度、数量上限或不可读目录的完整性策略。用户可能误选仓库根目录、磁盘目录或包含海量文件的文件夹；Browser 尤其容易因此长时间无响应或耗尽内存。

**建议答案：扫描只读元数据、可取消并设置跨平台统一上限；任何不完整扫描都整体失败。**

- 使用显式栈或队列迭代扫描，不使用递归调用栈；不跟随 D22 禁止的链接。
- 扫描阶段只读取名称、类型、相对定位符和必要的长度/链接元数据，不读取文件内容。
- 默认最大目录深度为 64 层，最大枚举条目总数为 50,000，最多接受 512 个 `.nyagekiProj` 候选；三个上限在 Desktop 与 Browser 保持一致，并作为集中常量和测试边界。
- 扫描超过 300 毫秒后显示非百分比进度，至少包含已扫描目录数、文件数、项目候选数和当前项目相对目录；总量未知时不显示虚假百分比。
- 扫描和重新扫描始终支持取消；取消后释放本轮取得的子句柄和临时索引，但保留用户已授权的项目根句柄，以便重试或改选文件夹。
- 达到任一上限、任一目录无法枚举或元数据读取失败时，报告具体相对位置和原因，丢弃本轮全部候选与索引；不能让用户从不完整结果继续打开项目。
- 不内置跳过 `.git`、`node_modules`、隐藏目录等名称规则，因为需求要求搜索整个项目根；用户应选择更精确的项目文件夹。
- 不设置固定扫描超时，慢设备可继续运行；资源边界由计数上限和用户取消控制。
- 扫描全程受 D13 全局 I/O 门约束，完成、失败或取消后立即释放。

**状态：** 用户否决该方案，不采用固定的 64 层、50,000 条目和 512 个项目候选上限。是否保留其他扫描约束，转由 Q23a 继续确认。

### Q23a. 是否取消所有数值硬上限，改为流式发现和按需索引？

取消硬上限后，不能继续沿用当前“一次性递归构建整个目录对象树”的实现，否则大目录仍会造成不必要的内存占用。需要把项目发现、依赖加载和项目浏览器枚举拆开。

**建议答案：不设目录深度、条目数量、项目候选数量或固定超时上限，但保留进度、取消与完整性要求。**

- 第一阶段以迭代方式流式遍历目录，只保留 `.nyagekiProj` 候选定位符、当前遍历队列和少量统计，不为每个普通文件创建长期对象。
- 候选发现后使用可虚拟化列表展示；即使候选很多，也不要求预先构建整个项目文件树。
- 用户选定项目后，只解析该工程并按定位符逐级解析其音频、谱面、SVG 和 ACB/AWB 依赖；项目内部浏览器展开目录时再按需枚举并缓存该目录。
- D11 的“可重建元数据索引”相应解释为增量缓存：重新扫描使缓存失效，后续访问按需重建，而不是每次完整复制整棵目录树。
- 扫描超过 300 毫秒仍显示非百分比进度和已扫描统计，并始终允许取消；不因设备较慢自动超时。
- D22 的链接禁止和循环防护继续生效，因此无深度上限也不允许通过链接无限遍历。
- 任一目录无法枚举时仍认为项目发现结果不完整，报告具体相对位置并整体失败；取消同样不允许从部分候选继续打开。
- 扫描、按需枚举和依赖读取仍受 D13 全局 I/O 门约束，每次操作完成、失败或取消后立即释放。

**状态：** 用户同意，形成 D23。

### Q24. 是否为项目加载设置显式的平台资源预算？

当前实现存在多条整体驻留内存路径：工程 JSON 会先复制到 `MemoryStream` 和 `byte[]`；部分 SVG 操作会读取完整字节并由 Skia 建立图形模型；音乐播放器会把整首音频转换成 PCM `byte[]`，重采样和单双声道转换还可能产生额外完整数组。压缩音频的源文件很小，也可能解码成数百 MB，因此只限制磁盘文件大小不能解决问题。

**建议答案：设置显式资源预算，但按实际资源类型和平台能力判断，具体阈值下一问确认。**

- 引入跨平台 `IProjectResourceBudget`，由 Desktop 和 Browser 提供各自配置；Core 在分配大块内存或进入昂贵解析前统一查询。
- 工程文件和谱面按输入字节、结构深度或对象数量检查；SVG 同时考虑单文件输入、项目累计输入和解析后的复杂度保护。
- 音频不按压缩文件大小判断，而是在读取格式和时长后估算目标采样率、声道数及样本格式下的解码 PCM 大小与峰值转换内存。
- 超过预算时在预检阶段报错，显示资源类型、实际或估算值、当前平台预算及处理建议，不尝试部分加载，也不让进程依赖 `OutOfMemoryException` 收尾。
- Desktop 与 Browser 可以有不同预算；项目格式仍保持一致，但低资源平台可能明确拒绝在高资源平台可打开的项目。
- 无论预算多少，都要移除可避免的重复完整副本并优先流式解析、流式复制或单缓冲转换；预算不能成为保留低效实现的理由。
- 外部导入在复制前能判断时提前拒绝，只有复制后才能判断时按 D9/D18 清理本次未提交项并保持原绑定。
- 预算值集中配置并覆盖边界测试，不散落在解析器或 ViewModel 中。

**状态：** 用户否决显式的平台资源预算，不设置按 Desktop/Browser 配置的固定输入、对象数量或解码内存阈值。替代策略转由 Q24a 确认。

### Q24a. 是否不设固定阈值，但强制流式/有界缓冲并响应运行时内存压力？

完全不限制输入且保留当前整块缓冲实现并不可行：音乐加载会为整首 PCM 及格式转换生成多个完整数组，工程 JSON 会重复复制，极端 SVG 或谱面对象图也可能让 Browser 标签页直接耗尽内存。`OutOfMemoryException` 或浏览器终止并不保证应用还能显示错误或保存恢复信息。

**建议答案：不设置任何预定义的 MB、时长、对象数或平台差异阈值；改以实现级有界内存和运行时压力信号控制。**

- 工程 JSON 直接从流反序列化，不再先复制到 `MemoryStream` 和 `byte[]`；谱面继续逐行解析并避免保留原始全文副本。
- 外部文件复制、哈希和保存全部使用固定大小缓冲区，文件大小本身不成为拒绝条件。
- 音乐播放改为流式解码和有界环形缓冲，不再把整首 PCM 存入 `byte[]`；随机跳转通过可寻址解码器或重新定位实现。
- 波形数据与播放缓冲解耦，按块生成降采样峰值缓存，不能为了绘制波形恢复整首 PCM 常驻内存。
- SVG 直接从流解析，避免重复字节副本；多个对象引用同一项目 SVG 时共享不可变解析资源，并采用引用计数或会话缓存释放。
- 解析过程中响应用户取消；运行时能够提供高内存压力信号时只记录日志警告，不主动中止本次加载，也不把该信号换算成应用固定大小上限。
- 如果 Browser、Skia 原生内存或第三方解码器无法提供可靠压力信号，文档明确保留残余风险：恶意或极端输入仍可能导致标签页被终止，无法保证友好报错。
- 预检负责格式、依赖和可解码性验证，但不因估算资源大小拒绝项目；正式打开过程中若资源失败，仍遵守 D6，不发布部分编辑器状态。

**状态：** 用户同意，但要求高内存压力只记录日志警告，不主动中止；形成 D24。

### Q25. 是否移除数据模型和 SVG 对文件句柄的所有权，统一交给异步项目会话？

当前 `EditorProjectDataModel.AudioFile/FumenFile` 在属性替换时直接 `Dispose()`，`SvgImageFilePrefab` 也持有并释放 `ISimpleFile`，复制对象时甚至同步读取完整内容。编辑器、工程设置对话框和文档管理器都可能参与释放，所有权转移依赖手工把局部变量设为 `null`。在 Browser 中，目录和文件对象代表实际授权能力；D24 的流式音频还要求播放器在播放期间持有明确的长期读取租约。

**建议答案：序列化模型只保存项目定位符和业务数据；所有文件能力、流与运行时资源由 `IProjectSession` 统一管理。**

- 每个已打开编辑器独占一个 `IProjectSession : IAsyncDisposable`；会话拥有授权项目根、选中工程定位符、会话取消源、按需目录缓存和资源缓存。
- `EditorProjectDataModel` 移除 `[JsonIgnore]` 的 `AudioFile`、`FumenFile` 及 `DisposeRuntimeFiles()`；克隆、迁移和序列化不再执行 I/O 或转移句柄。
- `SvgImageFilePrefab` 保存规范化项目定位符或稳定资源键，不直接拥有 `ISimpleFile`；对象删除或复制不会自行打开、复制或释放底层文件能力。
- 短期读取在单次方法内取得流并通过 `await using` 释放；需要跨调用存活的资源使用 `IProjectFileLease` 或等价租约表达，租约只能由所属会话创建。
- 流式音频播放器拥有音频租约直到停止、替换或关闭；切换音频时先验证并建立新播放器，再释放旧播放器和旧租约，失败时保持旧绑定。
- SVG 运行时缓存以规范化定位符和文件代次为键，共享不可变源或解析资源；各 SVG 对象只持引用计数句柄或会话资源引用，最终资源由会话统一释放。
- 工程设置或加载流程创建候选会话；失败或取消时异步释放，成功时只向编辑器转移一次所有权，不能由对话框和编辑器共同拥有。
- 关闭顺序固定为：取消并等待该会话活动任务，停止并释放音频播放器，释放 SVG 对象引用及资源缓存，释放剩余文件租约和目录缓存，最后释放项目根能力。
- 关闭确认完成后再执行异步释放；`OnViewBeforeUnload` 不做同步阻塞 I/O。释放流程幂等，异常写日志并继续释放其余资源。
- 所有异步读取和释放避免在属性 setter 中使用 `.GetAwaiter().GetResult()`；需要加载资源的属性变更通过显式异步命令或会话服务完成。

**状态：** 用户同意，形成 D25。

### Q26. 同一项目是否只允许一个编辑器实例，并在保存前校验外部变更？

### Q27. 流式音频是否先复制到应用临时缓存，使播放不占项目 I/O 门？

D13 的原始前提是音频加载到内存后，播放不再读取项目文件；D24 改为流式解码和有界缓冲后，如果播放器直接持有项目文件租约，它会在整个播放期间持续读取项目目录。此时要么长期占用全局 I/O 门并阻塞所有项目加载、保存和导入，要么绕过全局门而违反“同一时间只有一个项目读写”的规则。

**建议答案：加载时在全局门内把音频流式复制到应用临时存储；播放、跳转和波形只读取该不可变缓存。**

- 项目预检和加载取得 D13 全局门后，将普通音频流式复制到会话临时缓存；ACB 外置 AWB 按 D19 作为完整包缓存并保留名称关系。
- 复制过程使用固定缓冲区并可同时计算内容哈希；随后从缓存完成完整解码验证。验证成功后释放项目音频文件句柄，再发布编辑器会话。
- 音频播放器持有的是应用缓存租约，不是项目文件租约；播放、暂停、跳转、流式解码和波形降采样读取缓存时不占 D13 项目 I/O 门。
- 应用缓存不属于用户项目，不写入 `.nyagekiProj`，也不能作为项目定位符；正式保存仍保留原项目音频定位符。
- Desktop 使用应用临时目录，Browser 使用应用可用的临时/OPFS 存储；若平台无法提供可读写临时缓存，本次项目加载明确失败，不退化为长期持有项目文件并绕过全局门。
- 缓存项可以按完整内容哈希在多个会话间复用，但由独立 `IAudioSourceCache` 以引用计数管理；D26 的多个同项目编辑器不必重复保存相同缓存内容。
- 会话关闭或更换音频时释放缓存租约；最后一个租约释放后允许删除缓存。失败或取消只清理本次未提交缓存项。
- 运行时高内存压力仍按 D24 只记录日志；临时存储不足或缓存 I/O 失败则作为普通加载失败处理。
- 若同意，本条将修正 D25 中“播放器持有项目音频租约”的表述为“播放器持有应用音频缓存租约”。

**状态：** 用户否决应用临时缓存方案，要求音频直接读入内存。内存中保存原始音频字节还是完整解码 PCM，转由 Q27a 确认。

### Q27a. “直接读进内存”是否指完整解码后的 PCM？

当前 `DefaultMusicPlayer` 会把音频解码、重采样并转换声道后保存为完整 PCM `byte[]`；播放、跳转和波形读取该数组，因此加载完成后不会再访问项目文件。另一种实现是只把 MP3/WAV/AIFF/ACB 原始字节放入内存，再按需解码，但当前 Desktop MP3 使用只接受本地路径的 Media Foundation，ACB 也通过路径寻找 AWB，必须额外替换或重写解码管线。

**建议答案：若目标是保持原项目行为，则明确采用完整解码 PCM 常驻内存。**

- 项目加载在 D13 全局门内打开音频及必要的 ACB/AWB 依赖，完成解码、目标采样率转换和声道转换，生成完整 PCM 内存缓冲后释放全部项目音频句柄。
- 播放、暂停、跳转和波形直接读取 PCM，不再产生项目目录 I/O，也不需要应用临时音频缓存或长期音频文件租约。
- 每个编辑器拥有自己的 PCM 缓冲；D26 允许同一项目打开多个编辑器时，同一音频会在内存中存在多份，不跨会话共享。
- 更换音频时先完整解码新音频；成功后原子切换播放器并释放旧 PCM，失败则继续使用旧 PCM 和旧绑定。
- 不设置音频大小、时长或 PCM 内存上限；高内存压力只按 D24 写日志，实际内存不足可能导致加载失败或 Browser 标签页终止。
- D24 中“流式音频播放、有界环形缓冲、波形降采样缓存”的要求将撤销；工程 JSON、谱面、SVG、复制、哈希和保存的流式/有界缓冲要求继续保留。
- D25 中播放器长期持有文件租约的要求将撤销；播放器只拥有 PCM 内存和播放资源。

**状态：** 用户同意建议方案，形成 D27，并同步修正 D24、D25。

### Q28. 是否把新项目定位符语义升级为 `.nyagekiProj` `0.6.0`，并停止承诺旧 WPF 的写回兼容？

Avalonia 与旧 WPF 当前都把 `0.5.4` 视为最新项目格式。工程中的 `AudioFilePath`、`FumenFilePath` 表面上已经可以保存相对路径，但新设计还定义了项目根能力边界、统一 `/` 定位符、不区分大小写的逻辑查找，以及谱面内 SVG 必须由项目会话解析。旧 WPF 没有项目会话解析器，会把 SVG 路径直接包装成本地文件路径。若继续写成 `0.5.4`，旧程序可能接受文件却按不同语义解析，比明确拒绝更危险。

#### 例 1：相同的音频相对路径，在旧 WPF 中合法，在新项目边界中越界

```text
D:/Songs/
├─ SongA/                         <- 用户授权的项目文件夹
│  └─ project/song.nyagekiProj
└─ CommonAudio/bgm.wav            <- 项目文件夹之外
```

假设 `song.nyagekiProj` 保存：

```json
{
  "Version": "0.5.4",
  "AudioFilePath": "../../CommonAudio/bgm.wav"
}
```

- 旧 WPF 以 `.nyagekiProj` 父目录 `D:/Songs/SongA/project/` 为基准拼接，得到 `D:/Songs/CommonAudio/bgm.wav`。只要 Windows 账户能读取，它就会正常加载。
- 新设计以用户授权的 `D:/Songs/SongA/` 为权限边界。规范化结果已经越界，必须按 D1、D6 报错，不能因为 Desktop 实际有权限而继续读取。
- JSON 字段和字符串都没有改变，但“这个值是否合法”的定义已经不同。若仍标记为 `0.5.4`，旧 WPF 会把新编辑器明确禁止的项目当作合法项目。

#### 例 2：相同的 SVG 相对路径，会以完全不同的目录为基准

```text
D:/Songs/SongA/                   <- 项目文件夹
├─ song.nyagekiProj
├─ charts/master.ogkr
└─ autoImport/svgFiles/logo.abc123.svg
```

假设谱面以谱面父目录为基准保存 SVG 定位符；如果最终选择以项目根为基准，差异结论相同：

```text
../autoImport/svgFiles/logo.abc123.svg
```

- 新设计不会把该字符串直接交给 `System.IO`，而是由项目会话从 `charts/` 解析为项目内的 `autoImport/svgFiles/logo.abc123.svg`，完成边界和大小写校验后取得已授权文件。
- 旧 WPF 的 OGKR/Nyageki SVG 解析器直接调用 `File.Exists(filePath)`。相对路径会相对于进程当前工作目录解析，例如可能检查 `C:/Program Files/autoImport/svgFiles/logo.abc123.svg`，因此通常找不到 SVG。
- 更危险的情况是工作目录下碰巧存在同名文件，旧 WPF 可能加载另一个 SVG。此时项目能够打开，但画面内容错误，没有明确的格式错误提示。

#### 例 3：旧绝对路径只能在 Desktop 中有条件迁移

旧项目可能保存：

```json
{
  "Version": "0.5.4",
  "AudioFilePath": "D:\\Songs\\SongA\\audio\\bgm.wav"
}
```

- Desktop 选择 `D:/Songs/SongA/` 后，可以取得真实本地路径并证明目标位于项目根内，因此按 D4 转换为 `audio/bgm.wav`。
- Browser 只持有用户授权的目录/文件能力，无法用一个 Windows 绝对路径证明它对应目录树中的哪一项，因此必须提示需要先迁移。
- 第一次正式保存后写成 `0.6.0` 和规范化相对定位符，表示该项目已经不再依赖旧式任意绝对路径解析。

#### 例 4：大小写冲突在新格式中是确定错误

```text
ProjectRoot/
├─ Assets/logo.svg
└─ assets/Logo.svg
```

如果谱面保存 `assets/logo.svg`：

- 新设计按 D5 使用 `OrdinalIgnoreCase` 逻辑查找，会发现两个候选并报告大小写冲突，不能随平台或枚举顺序任选一个。
- 旧路径逻辑依赖底层文件系统：可能只匹配一个、可能找不到，也可能表现随平台或目录设置变化。
- 因而 `0.6.0` 还表示项目采用统一的跨平台定位规则，而不是继承宿主文件系统的路径语义。

#### 例 5：版本号负责把隐蔽误读变成明确拒绝

当前项目加载器按 `Version` 精确选择序列化器，旧 WPF 只登记 `0.5.2` 和 `0.5.4`：

```text
旧项目 0.5.4 -> Avalonia 读取并在内存迁移 -> 用户正式保存 -> 项目变为 0.6.0
                                                               |
                                                               +-> Avalonia 按新语义读取
                                                               +-> 旧 WPF 找不到 0.6.0 解析器并明确拒绝
```

如果保存后仍伪装成 `0.5.4`，旧 WPF 会继续进入旧解析器，然后出现前述越界读取、SVG 丢失或错误文件加载。升级版本号的作用不是让新代码更容易编写，而是阻止不理解新语义的程序静默接受文件。

版本号只能保护“从 `.nyagekiProj` 打开项目”的入口。用户若绕过工程文件，直接把 `master.ogkr` 交给旧 WPF，旧程序仍可能错误解释其中的相对 SVG；这属于不再承诺兼容的旧版直接打开行为。若未来需要让独立谱面也能明确拒绝旧解析器，还需另行设计谱面级格式标记，不能仅依赖 `.nyagekiProj` 版本。

**建议答案：升级到 `0.6.0`；继续读取旧格式，但新版本保存后不保证旧 WPF 能再次打开。**

- 保留 `.nyagekiProj` 扩展名；`0.6.0` 表示项目资源定位与权限边界的语义升级，不只是新增 JSON 字段。
- Avalonia 继续读取 `0.5.2` 和 `0.5.4`，通过迁移器转换为当前内存模型；单纯打开、预检或取消不改写任何用户文件。
- 成功加载旧项目后标记“待格式迁移”；用户第一次成功执行正式保存时，工程文件写为 `0.6.0`，工程、谱面和 SVG 定位符按 D1、D4、D5、D7 规范化。
- 旧绝对路径只按 D4 处理：Desktop 仅迁移确认位于项目根内的目标，Browser 无法证明时直接报告需要迁移；不得为兼容旧 WPF 继续写绝对路径。
- 不双写两套字段，不在普通保存中生成 `0.5.4` 降级副本，也不维持“新旧编辑器可交替保存”的承诺。
- 旧 WPF 遇到未知 `0.6.0` 应拒绝加载，从而避免错误解析 SVG；若以后确实需要旧版导出，应设计为 Desktop 专属的显式“导出旧版项目”，不属于正常保存流程。
- 首次迁移保存是否需要额外警告和永久兼容备份，留到本题确认后单独决定。

### Q29. SVG 相对定位符应以项目根目录还是谱面文件父目录为基准？

例如：

```text
ProjectRoot/
├─ configs/song.nyagekiProj
├─ audio/bgm.wav
├─ charts/master.ogkr
└─ autoImport/svgFiles/logo.svg
```

工程文件继续保存：

```text
AudioFilePath = ../audio/bgm.wav

```

SVG 有两种可选表示：

```text
项目根目录基准：autoImport/svgFiles/logo.svg
```

### Q30. 跨平台 Core 是否彻底移除工程编辑器的本地路径 API，只允许通过项目文件夹会话打开和保存？

当前路径入口并非只有 `FumenVisualEditorViewModel.Load(string)`：`Save(string)`、`EditorProjectDataUtils.TryLoadFromFileAsync(string)`、多个字符串保存重载、`EditorProjectFileManager.Load/Save(string)`、`IFumenVisualEditorProvider.TryOpen(..., string)` 和直接传入 `EditorProjectDataModel` 的打开方式都会绕过用户授权的项目根。只保留其中任意一个，业务代码以后仍可能重新使用 `File.Exists`、`Path.Combine` 或 `File.Copy` 逃出 D11 的项目会话边界。

**建议答案：是；先引入项目会话入口并迁移调用方，然后从跨平台 Core 删除这些兼容路径入口。**

- `FumenVisualEditorViewModel` 只接收已经预检成功并拥有明确所有权的 `IProjectSession` 或等价 `ProjectOpenResult`；移除 `Load(string)`、`Save(string)`、模型直接打开和 `GetAudioFile()` 的本地路径回退。
- 标准 `FumenVisualEditorProvider.TryOpen(document)` 只转发到对应 ViewModel；`FumenVisualEditorViewModel.Load()` 负责让用户选择项目文件夹、扫描并选择 `.nyagekiProj`，随后创建会话，同时继续通过 Avalonia `StorageProvider` 与目录书签维持跨平台权限边界。
- 正式保存改为当前会话上的 `SaveAsync()`，目标来自会话已绑定的项目定位符；另存谱面按 D12 先从应用内项目浏览器取得定位符。
- `EditorProjectDataUtils` 中工程加载、完整保存和回滚职责迁入项目会话/项目存储服务；删除以 `string` 为目标并直接调用 `File.*` 的工程相关方法。
- `EditorProjectFileManager` 作为纯项目 JSON 编解码器保留 `Stream` 接口；接受本地字符串路径的便利重载移到 Desktop 适配层或删除，不能由 Core 项目打开流程调用。
- `IFumenVisualEditorProvider.TryOpen(..., string)` 删除；框架要求的 `TryOpen(document, RecentRecordInfo)` 不能再把 `LocationDescription` 当成本地路径，最近项目的能力恢复方式下一问单独设计。
- Desktop 命令行、未来快速打开谱面或其他明确的本地工具可以在 Desktop 程序集中拥有独立路径适配器，但不能把这些重载重新暴露给跨平台 `FumenVisualEditor` 标准流程。
- 迁移顺序固定为：建立新会话 API和测试，迁移 Provider/ViewModel/保存调用方，再删除旧入口；不长期保留 `[Obsolete]` 包装，因为包装仍能绕过权限边界。

### Q31. 最近项目是否记录项目文件夹书签，并在书签不可用时要求用户重新选择文件夹？

当前 `RecentRecordInfo` 只有显示名称和 `LocationDescription` 字符串，现有 Provider 会把后者直接交给 `Load(string)`。Avalonia 的 `IStorageFolder` 在部分平台支持 `CanBookmark`、`SaveBookmarkAsync()` 与 `OpenFolderBookmarkAsync()`，可以恢复目录能力；但 Browser 或具体存储提供者可能不支持书签，书签也可能过期、被撤销或恢复失败。

**建议答案：最近记录保存目录书签作为可选能力；没有有效书签时，只能在用户点击最近项后重新选择项目文件夹。**

- 最近记录的业务含义改为“最近使用的项目文件夹”，不是可直接访问的系统路径；`LocationDescription` 只用于显示，不能作为权限或加载地址。
- 为 Fumen 项目定义独立且带版本的最近数据，例如目录书签、项目根显示名和上次选择的 `.nyagekiProj` 项目根相对定位符；书签作为不透明数据保存，不写日志。
- 目录支持书签时，在成功打开项目后保存书签；点击最近项时先调用 `OpenFolderBookmarkAsync()`，成功后用恢复的 `IStorageFolder` 创建新的项目会话。
- 不支持书签、书签为空、过期、权限被撤销或恢复返回空时，不尝试使用显示路径或 Desktop 本地路径绕过；在该次用户点击动作中打开文件夹选择器，请用户重新授权。
- 用户取消重新授权时静默结束，不删除最近项；恢复失败的非取消错误可以提示，并允许用户从最近列表显式移除记录。
- 无论书签恢复还是重新选择，都重新扫描目录；发现多个 `.nyagekiProj` 时继续按 D3 弹出选择对话框，不用最近记录中的上次定位符自动代选。
- 成功重新授权后，用新的书签和显示信息更新该最近记录；不保留已经失效的旧书签。
- 清除最近记录时同时清除保存的书签数据；编辑器关闭时释放本次恢复得到的目录句柄，但不删除持久化书签字符串。
- 这种重新选择只在用户主动点击最近项后发生，不属于程序后台自主请求文件权限。

**状态：** 用户要求保存“项目文件夹书签 + 用户选择的项目文件标记”组合，以恢复权限并直接打开指定工程；形成 D31，并修订 D3 的适用范围。

### Q32. 平台无法创建或恢复项目文件夹书签时，是否仍保留最近记录，并在点击时要求用户重新授权文件夹？

工程定位符本身不能授予目录权限。Browser 或某些存储提供者可能令 `CanBookmark` 为假，持久书签也可能过期或被撤销；此时程序无法自动打开最近项目，但仍可以在用户点击最近项后通过文件夹选择器重新取得权限。

**建议答案：保留最近记录；用户点击后重新选择项目文件夹，再用已保存的工程定位符直接定位。**

**状态：** 用户不同意重新选择文件夹的降级方案；书签失效时保留最近记录，但置灰且不可点击，形成 D32。

### Q33. 为了在点击前识别失效书签，是否在最近项目列表加载时主动验证全部书签？

Avalonia 没有单独的同步“书签仍有效”标志，通常只能实际调用 `OpenFolderBookmarkAsync()` 才知道是否能恢复。若不主动验证，最近项只能先显示为可用，用户第一次点击恢复失败后再按 D32 置灰；若启动时验证，则需要后台逐个恢复目录句柄再立即释放。

**建议答案：不在启动时批量验证；用户点击最近项时才尝试恢复，失败后立即置灰并持久化状态。**

- 避免应用启动或打开首页时后台访问所有历史项目目录，也避免大量最近项拖慢启动。
- 点击本身是明确的用户打开意图；恢复成功后创建正式项目会话，恢复失败则不弹文件夹选择器，直接按 D32 禁用该项并提示书签失效。
- 已经持久化为失效的记录不再调用恢复 API，除非后续设计并由用户触发独立的重新授权操作。
- 若平台能提供无 I/O、无权限副作用且可靠的有效性查询，未来可以用它更新显示，但不能把实际目录恢复伪装成轻量状态检查。

**状态：** 用户没有采用“只在点击时检查”的建议，要求在 Gekimini.Avalonia 增加 Provider 有效性检查，并由最近项选择逻辑统一判断和置灰；形成 D33，精确异步集成转入 Q34。

### Q34（代码更新后重审）. 是否直接采用现有异步 `Task<bool> CheckIsValid(...)` 链路？

**建议答案：可以采用当前 `Task<bool>` 契约完成首版，但 Fumen 实现必须补齐以下边界。**

- `CheckIsValid` 从最近记录附加数据读取目录书签和工程定位符，使用当前 GUI TopLevel 的 `StorageProvider.OpenFolderBookmarkAsync()`；不能读取 `LocationDescription` 作为路径。

- 当前无缓存会重复恢复书签，但不影响正确性；是否加入缓存、并发合并和 D32 失效状态持久化，下一问单独确认。
- 异步命令基础设施应增加专项测试，并为 `TargetableCommand.Execute(async void)` 和菜单 `OnSubmenuOpened(async void)` 补充异常观察，避免 Provider 之外的异步异常直接进入 UI 同步上下文。

### Q35. 哪些校验失败应写入持久化“已失效”状态？

当前 `CheckIsValid` 只向命令层返回 `bool`，因此所有失败在本次界面上都会置灰，但 Provider 仍可决定是否把失败写入 D32 的持久状态。若把任何 `false` 或异常都永久化，启动阶段尚未取得 `TopLevel`、存储服务暂时不可用或一次瞬时 I/O 异常，也会让原本有效的最近项目永久不可点击。

**建议答案：只有能够确定记录本身无效的结果才持久化；环境或执行层面的临时失败只在当前检查中置灰。**

- 附加数据缺失或损坏、版本无法解析、已保存记录明确没有可用书签，以及存储服务已就绪时 `OpenFolderBookmarkAsync()` 明确返回空，均可标记为持久失效。
- 尚未取得所属 GUI `TopLevel`、`StorageProvider` 暂时不可用、检查被取消、应用正在关闭或恢复 API 抛出未能证明书签失效的异常时，返回 `false` 使当前入口置灰，但不写入持久失效标记。
- 临时失败保留下一次命令状态更新重新校验的机会；已确认失效的记录按 D32 直接保持置灰，不重复恢复书签。
- Provider 负责判断并写入持久状态，Gekimini 的通用异常兜底只负责本次返回 `false`，不能替具体 Provider 宣告书签永久失效。

**状态：** 用户同意建议方案，形成 D35。

### Q36. 最近记录校验是否同时确认指定 `.nyagekiProj` 存在？

目录书签恢复成功只说明程序重新获得了项目根目录能力；用户可能已经移动或删除最近记录指向的 `.nyagekiProj`。如果 `CheckIsValid` 只检查书签，这条记录会显示为可点击，随后在 `TryOpen` 中才报告项目文件不存在。反过来，如果校验阶段加载整个工程及其依赖，打开菜单或启动页就会解析谱面、读取 SVG，甚至按 D27 解码整段音频，明显超出轻量有效性检查范围。

- 校验阶段不反序列化 `.nyagekiProj`，不检查音频、谱面或 SVG，更不读取或解码这些资源；完整且无副作用的 D6 预检只在用户真正打开项目时执行。

### Q37. 如何为现有最近记录补入稳定 ID 并迁移附加数据？

当前 `RecentRecordInfo` 没有 ID，附加数据以 `XxHash64(LocationDescription)` 为键。若新版本只增加 ID 并立即改用新键，旧记录保存的文件书签或其他 Provider 数据将无法读取；若继续保留旧哈希作为回退，显示文本仍会参与身份判断，并长期留下碰撞和数据串用风险。

**建议答案：为记录增加持久化 GUID，并在首次加载旧设置时执行一次单向、可恢复迁移。**

- `RecentRecordInfo` 增加 `Guid RecordId`，新记录由 Gekimini 生成非空随机 GUID；旧 JSON 缺少该字段时先反序列化为 `Guid.Empty`，随后为每条旧记录生成一次 ID 并立即持久化，后续启动不得重新生成。
- 新附加数据键使用带命名空间的稳定格式，例如 `recent:v2:{RecordId:N}`，所有新读写、清除和有效性状态都只使用该键。
- 迁移旧记录时，先按原算法查找 `LocationDescription` 哈希键；若存在数据，先复制到新 ID 键并保存数据区，再保存包含新 ID 的记录列表，最后清除已确认迁移成功的旧键，使中途崩溃最多留下可清理副本而不丢失数据。
- 通用迁移只搬运不透明字节，不解析或改写 Provider 数据；旧 Fumen 数据若不是 D31 的文件夹书签组合，由 Fumen Provider 按 D35 判定为不支持或失效，Gekimini 不把旧本地路径转换成权限能力。
- 发现空 ID、重复 ID、旧键冲突或数据区写入失败时记录安全警告；不得覆盖另一条记录已有的新键数据，也不得删除仍无法确认归属的旧数据。
- `LocationDescription` 迁移后只用于显示；同一项目再次打开时如何识别并更新已有记录，而不是生成重复记录，下一问单独决定。

**状态：** 用户在确认 GUID 只作为稳定记录标识、并了解可选替代方案后，同意建议方案，形成 D37。

### Q38. 同一项目再次打开时，最近记录如何去重？

当前 `PostRecent` 通过 `LocationDescription` 相等删除旧记录，但 D34 已规定该字段只用于显示。Avalonia 没有跨 Desktop 与 Browser 都可靠的目录句柄身份比较 API；本地路径不可作为 Browser 身份，项目内容哈希会随保存变化，而重新生成的书签字符串也不保证与旧书签相同。强行猜测同一项目可能把两套权限和附加数据错误合并。

**建议答案：只在能够证明记录身份相同时更新；无法证明时允许生成独立最近记录。**

- 从最近项打开时沿用其 `RecordId`；该编辑器后续保存或刷新最近信息时更新同一记录、保留 ID 并移到列表顶部。
- 普通文件夹选择打开后，若 Fumen Provider 找到“书签不透明值完全相同且规范化工程定位符相同”的已有记录，可以复用其 `RecordId`；书签不同不能反推项目不同，也不能据此误合并。
- 无精确匹配时创建新 GUID 记录，即使显示文本相同也不使用 `LocationDescription`、本地路径、文件名或内容哈希猜测合并；因此同一物理项目在书签重新签发后可能暂时出现重复项。
- 每条未合并记录独立保存书签、定位符和失效状态；删除或淘汰其中一条不得影响另一条。
- Gekimini 最近记录管理器提供“按现有 `RecordId` 更新并置顶”和“新建记录”两种明确操作，移除当前基于显示字符串的隐式去重。
- 若未来平台提供可靠项目身份，或者项目格式以后增加持久项目 ID，可以在不改变记录 GUID 语义的前提下增强匹配。

**状态：** 用户同意建议方案并接受无法证明相同时保留少量重复记录，形成 D38。

### Q39. 最近记录有效性结果应缓存到什么范围？

当前 `TargetableCommand.CanExecute` 在没有进行中任务时会再次调用 `Update`，而 `CommandManager` 会在焦点、按键、命令执行及其他 UI 状态变化时频繁触发重新查询。若不增加结果复用，一条最近记录在同一次菜单显示期间也可能多次恢复文件夹书签并遍历工程定位符；固定时间 TTL 又会引入计时竞态，且很难解释何时应重新校验。

**建议答案：使用按记录、按界面刷新代次的内存缓存，并合并同一记录的进行中任务；不采用固定秒数 TTL。**

- 启动页构建或刷新最近列表、最近项目子菜单每次重新展开，以及应用从挂起状态恢复时，开始新的校验代次。
- 同一代次内，每个 `RecordId` 最多调用一次 Provider；菜单绑定、`CanExecute` 重查询和其他入口共享同一进行中任务及结果，不重复恢复书签。
- 已持久化失效的记录直接返回 `false`，不发起 I/O；成功和临时失败结果只缓存到当前代次，下一代次按 D35 重新判断。
- 用户点击最近项时执行一次不使用旧代次成功缓存的权威校验；通过后才进入 `TryOpen`，随后仍由 D6 完整预检决定能否真正打开。
- 新建、更新、删除最近记录，写入新书签或工程定位符，以及改变持久失效状态时，立即使该 `RecordId` 的当前缓存失效。
- 所有实际目录恢复和工程文件存在性读取继续受 D13 全局 I/O 门约束；等待期间命令保持禁用，不并发绕过项目 I/O 串行规则。
- 缓存和任务合并由 Gekimini 最近记录有效性协调层管理，Fumen Provider 仍只负责一次具体 `CheckIsValid`，不直接持有 UI 菜单生命周期。

**状态：** 用户同意建议方案，形成 D39。

### Q40. 平台首次就无法创建文件夹书签时，是否仍新增最近记录？

D32 处理的是一条已有最近记录的书签后来失效：记录需要保留并置灰，避免静默丢失用户历史。但某些平台或存储 Provider 可能在项目首次成功打开时就令 `IStorageFolder.CanBookmark` 为 `false`，或者 `SaveBookmarkAsync()` 返回空。此时应用从未获得可持久恢复的权限能力，新建的最近项从产生起就不能点击。

**建议答案：不创建新的最近记录，但不影响本次已授权项目会话。**

- 用户通过文件夹选择器取得的当前 `IStorageFolder` 仍交给 `IProjectSession`，项目按正常流程打开、编辑和保存；缺少书签只影响应用重启后的快捷恢复。
- 只有成功保存非空文件夹书签，并已生成有效工程定位符后，才调用 Gekimini 创建新的最近记录及其附加数据。
- `CanBookmark == false`、保存书签明确返回空或书签保存失败时，不创建一条立即置灰的无效记录，也不使用本地路径或显示文本替代权限。
- 瞬时书签保存异常记录不含敏感内容的警告；是否向用户显示一次非阻塞提示继续沿用应用统一错误呈现策略，不阻止项目打开。
- 若正在更新一条已有最近记录而新书签保存失败，不用空值覆盖仍可用的旧书签；旧书签已经确定失效时仍按 D32 保留并置灰。
- 未来平台获得书签能力后，用户再次通过普通文件夹打开项目即可创建可用的新最近记录。

**状态：** 用户同意建议方案，形成 D40。

### Q41. 失效最近记录是否仍参与普通数量上限淘汰？

D32 的“保留”可以解释为书签失效后不立即删除，也可以解释为除非用户手动删除否则永久保留。当前 Gekimini 默认只保存最近 10 条，但实现只是截断写入的列表，没有从内存集合删除超额项，也没有清理其 `RecordInfoDataMap`；引入文件夹书签后，这会让已经不可见的权限数据长期残留。

**建议答案：失效记录不因失效而立即删除，但仍像普通记录一样计入上限并按时间淘汰。**

- 已确认失效的记录继续按 D32 保留、置灰并显示在原时间顺序中，不因为状态无效而提前删除或降低排序权重。
- 失效记录计入 `RecordMaxCount`；创建或置顶记录超过上限时，按正常最近访问顺序淘汰最旧记录，无论其当前有效或失效。
- “保留”表示不会因一次失效检查被静默删除，不表示绕过数量上限永久保存。
- Gekimini 增加按 `RecordId` 删除单条记录的 API；启动页等能够展示独立删除操作，使禁用的主打开命令不妨碍用户清理该记录。
- 单条删除、清空全部和上限淘汰都必须同时清除记录信息、新 ID 附加数据、持久失效状态及内存校验缓存；旧键迁移残留仅在确认无其他记录引用后清除。
- 保存列表时先确定完整保留集合和淘汰集合，再持久化并清理，不能继续只对序列化结果调用 `Take(...)` 而把超额项留在内存和数据区。

**状态：** 用户同意建议方案，形成 D41。

### Q42. 文件夹书签是否要求应用层加密后再持久化？

文件夹书签是不透明的权限能力，应按敏感数据处理。当前 Desktop `DesktopSettingManager` 把设置以 JSON 写入程序目录的 `setting.json`；Browser `BrowserSettingManager` 把 JSON 写入站点 `localStorage`，并且当前第 86、93 行会在调试日志中输出完整设置值。Browser 同源脚本能够读取 `localStorage`，而把加密密钥也保存在同一站点存储中并不能抵御同源脚本或 XSS；Desktop 使用 DPAPI、Keychain 等又会引入各平台不同的密钥和迁移语义。

**建议答案：首版不增加无法跨平台兑现的应用层加密，但严格禁止书签进入日志、显示文本和诊断导出。**

- 书签按 Avalonia 的持久书签契约原样保存在最近记录专用附加数据中；Base64 或 JSON 转义只作为序列化，不宣称是加密。
- `LocationDescription`、记录名称、异常消息、结构化日志字段和 UI 不得包含书签正文；日志只记录 `RecordId`、Provider 类型、结果类别和不敏感的工程定位符。
- Browser `SettingManager` 必须移除完整设置值日志，改为只记录设置键、类型和成功/失败；其他设置加载、保存及崩溃诊断路径也需要扫描同类泄漏。
- Desktop 依赖当前用户账户和文件权限保护 `setting.json`；Browser 依赖浏览器同源存储边界。不能把这描述为抵御本机管理员、同源恶意脚本或 XSS 的安全存储。
- 单条删除、上限淘汰和清空历史按 D41 删除书签数据；错误日志与恢复快照不得留下副本。
- 保留可替换的书签存储抽象；未来若 Desktop 接入系统凭据库，可以迁移具体存储而不改变 `RecentRecordInfo.RecordId` 和 Provider 契约。
- 如果必须要求书签在 Browser 本地存储中也具备独立于同源脚本的机密性，则首版 Browser 最近项目功能应禁用，除非另行引入用户口令或外部密钥方案。

**状态：** 用户同意建议方案，形成 D42。

### Q43. 最近记录信息和书签附加数据是否合并为一次原子保存？

当前 Gekimini 分别保存 `RecentRecordInfoStoreSetting` 与 `RecentRecordDataStoreSetting`。创建、更新、删除、淘汰和 D37 迁移都至少需要两次 `SaveSetting`；任一步失败或进程中断，都可能留下可见记录却没有附加数据，或者列表已删除但书签数据仍然残留。Desktop 的 `File.WriteAllText` 本身也可能在覆盖过程中留下截断的 `setting.json`。

**建议答案：新增带版本的聚合最近记录存储，并让一次逻辑变更只提交一个完整快照。**

- 定义 `RecentRecordsStoreV2`，在同一设置对象中保存版本、按顺序排列的 `RecentRecordInfo` 列表，以及按 `RecordId` 关联的 Provider 不透明数据和通用失效状态。
- 新建、更新并置顶、删除、清空、上限淘汰和状态变更都先在内存副本中生成完整新快照，校验 ID 与数据引用一致后再调用一次持久化提交；提交失败时继续使用旧快照。
- Browser 使用单个 `localStorage.setItem` 键提交整个快照；Desktop 设置管理器先把完整 JSON 写入同目录临时文件，刷新并原子替换 `setting.json`，不得直接截断覆盖原文件。
- 旧的两个设置对象不迁移，直接切换为空的 V2 快照；旧 Fumen 本地路径和文件书签不得推断或补造成项目文件夹权限。
- 加载时发现列表和数据不一致、重复 ID 或损坏条目，只隔离对应记录并记录安全警告；不得因一条最近记录损坏导致整个应用设置加载后直接退出。
- 聚合快照仍以 GUID 支持命令缓存、记录更新和 Provider 数据隔离；合并存储不改变 D37 的稳定记录身份语义。
- 若底层平台无法提供真正的原子替换，则至少采用“写新快照成功后再切换当前版本指针”的双槽策略，不用破坏旧快照换取表面上的一次写入。

**状态：** 用户要求停止继续提问并直接更改；采用聚合快照，同时明确不迁移旧双设置数据，形成 D43。
