CA-001 图片加载队列存在丢失唤醒竞态

首次记录：2026-08-12 · 状态最后确认：2026-08-12

高 未修复 静态确认 潜伏
位置ImageLoader.cs，LoadImage / PrcessQueue
结果返回的 Task<byte[]> 永久不完成
覆盖情况现有测试仅覆盖顺序缓存复用，没有并发入队测试

触发时序

  1. 已有处理器在 while (!tasks.IsEmpty) 处观察到队列为空，准备退出。
  2. 另一个线程在处理器执行 isProcessing = false 之前调用 LoadImage，先把任务压入栈，再调用 PrcessQueue。
  3. 新调用看到 isProcessing == true 后直接返回。
  4. 旧处理器随后把 isProcessing 置为 false 并退出；队列中已有新任务，但没有任何处理器，也没有后续唤醒。

源码证据

tasks.Push(new LoadTask(taskCompleteSource, url, cancellationToken)); // 50
PrcessQueue();                                                       // 51

while (!tasks.IsEmpty)                                               // 62
{
    ...
}

isProcessing = false;                                                // 99

ConcurrentStack 只保证栈操作本身线程安全，不会把“判空、入队、处理器状态切换”组合成一个原子协议，因此上述交错不依赖未定义行为。

影响

调用方会无限等待图片数据；如果 UI 正在等待该任务，表现为图片不再出现、加载状态不结束，或者依赖该任务的后续流程停滞。取消令牌在任务滞留队列期间也不会主动完成对应的 TaskCompletionSource。

修复方向与回归门槛

  • 使用单一、可证明无丢失唤醒的生产者/消费者原语，例如 Channel<LoadTask> 加固定数量消费者，或用锁保护“入队 + 启动/退出”状态机。
  • 增加确定性并发测试，覆盖“处理器判空后、清除运行标记前”发生入队的交错，并断言所有返回任务在超时内完成。
  • 本次全仓检索只找到单例注册和测试调用，未找到生产调用；问题当前属于潜伏缺陷，但代码一旦重新接入即可能触发。

CA-002 图片加载处理器门闩非原子，并发上限可失效

首次记录：2026-08-12 · 状态最后确认：2026-08-12

中 未修复 静态确认 潜伏
位置ImageLoader.cs，isProcessing / PrcessQueue
结果ParallelCount = 2 不能构成全局并发上限
附带成本达到局部上限时反复 Task.Yield，产生调度器空转

触发时序

  1. 两个线程近同时进入 PrcessQueue，都在另一个线程写入前读到 isProcessing == false。
  2. 两个线程都写入 true 并进入处理循环。
  3. 每个处理器都有自己的局部 currentTaskRunningCount，因此每个处理器都可以再启动两个工作任务；实际并发量可超过常量声明的 2。

源码证据

private volatile bool isProcessing = false; // 25

if (isProcessing)                          // 57
    return;
isProcessing = true;                       // 59

var currentTaskRunningCount = 0;           // 61

volatile 提供可见性，但“检查后设置”不是原子操作；局部计数器也无法约束其他同时启动的处理器。

影响

高并发入队时可能同时执行超过预期数量的网络、磁盘和解码任务，造成带宽突发、内存峰值和响应抖动。队列饱和时的反复 Task.Yield 还会产生无效调度。

修复方向与回归门槛

  • 与 CA-001 一并替换为固定消费者或原子状态机；不要只把字段改成另一种可见性修饰符。
  • 使用阻塞点记录测试下载器的同时运行数，在并发提交大量请求时断言峰值不超过 ParallelCount。
  • 修复后不应再靠循环 Task.Yield 等待容量，应等待明确的工作完成或通道可读事件。

CA-003 OPFS 预览与普通下载长期保留 Blob URL

首次记录：2026-08-12 · 状态最后确认：2026-08-12

中 未修复 静态确认 活动
位置opfsBrowser.js，预览、普通下载和卸载清理
结果已关闭预览或已完成下载对应的 Blob 仍被主页面持有
暴露面Browser 菜单中的 OPFS 文件浏览器已直接调用这些路径

触发方式

  1. 反复双击 OPFS 文件进行预览，或者下载多个/较大的单文件。
  2. 每次操作都通过 URL.createObjectURL 创建 URL，并加入全局 retainedObjectUrls。
  3. 成功路径没有从集合移除，也没有调用 URL.revokeObjectURL；关闭预览标签页或下载完成均不会触发清理。
  4. 只有主应用页面发生 beforeunload 时才一次性释放全部 URL。作为长期运行的 Browser 应用，该事件可能数小时都不发生。

源码证据

const retainedObjectUrls = new Set();                 // 23

objectUrl = URL.createObjectURL(previewContent);      // 257
retainedObjectUrls.add(objectUrl);                    // 258
previewWindow.location.replace(objectUrl);            // 259

const objectUrl = URL.createObjectURL(file);           // 432
retainedObjectUrls.add(objectUrl);                    // 433
anchor.click();                                       // 440

globalThis.addEventListener?.("beforeunload", () => { // 846
    // 唯一的成功路径清理点
});

影响

对象 URL 会让对应 Blob 保持可达。对较大的音频、谱面资源、压缩包或其他 OPFS 文件反复预览/下载时，浏览器进程内存会持续增长，最终可能触发明显卡顿、内存压力或页面崩溃。

修复方向与回归门槛

  • 普通下载在浏览器已接收点击后安排有界延迟清理，并从集合移除对应 URL。
  • 预览需要独立生命周期：使用可感知预览页关闭/卸载的包装页，或跟踪子窗口关闭后释放该 URL；不能在资源尚未加载时过早撤销。
  • 增加 JS 生命周期测试或浏览器集成测试，断言连续完成下载、关闭预览后保留集合回到基线，而主应用无需卸载。

CA-004 渲染初始化异常会进入应用级崩溃流程

首次记录：2026-08-12 · 状态最后确认：2026-08-12

高 未修复 静态确认 活动
入口FumenVisualEditorView.xaml.cs 的 Loaded 事件
传播InitializeRenderControlAsync 清理后再次 throw
桌面结果全局 Dispatcher 异常处理最终执行 Environment.Exit(-1)

触发方式

打开谱面编辑器时，只要渲染控件初始化、绘制目标初始化或纹理资源加载中的任意一步抛出非取消异常，就会走到该路径。资源缺失、损坏的本地资源覆盖、后端不匹配或设备初始化失败都属于可能来源。

源码证据

private async void OnRenderControlHostLoaded(...) // View: 37
{
    ...
    await viewModel.InitializeRenderControlAsync(contentControl); // 41
}

catch (Exception exception)                     // Drawing: 1002
{
    DetachRenderControl();
    renderInitializationTaskSource.TrySetException(exception);
    throw;                                      // 1011
}

异常从返回 Task 的方法重新抛出后，由 async void 事件处理器交给 UI SynchronizationContext。桌面入口的 Program.cs 在 Dispatcher.UIThread.UnhandledException 中处理后，于第 149 行退出整个进程。音频波形视图的同类挂载代码已经捕获并记录异常，说明谱面编辑器缺少的是局部错误边界。

影响

单个文档的渲染初始化失败会升级为整个桌面应用退出，其他已打开且可能未保存的谱面也受影响。Browser 端没有同等的本地捕获，行为依赖运行时的未处理异常策略。

修复方向与回归门槛

  • 在视图或专用挂载协调器中捕获异常，记录完整错误，并在该文档内显示不可用状态；不要让它逃出 async void 事件。
  • 保留现有资源清理，但明确初始化失败后的重试或关闭语义。
  • 增加 Headless 测试：注入会抛错的渲染管理器，断言控件被释放、错误被报告且没有触发 Dispatcher 未处理异常。

CA-005 调度器时间字典永久保留已移除实例

首次记录：2026-08-12 · 状态最后确认：2026-08-12

中 未修复 静态确认 活动
位置SchedulerManager.cs
所有权ConcurrentDictionary<ISchedulable, DateTime> 的键是强引用
增长来源编辑器激活/关闭，以及每个新建的桌面音频播放器

触发时序

  1. AddScheduler 同时把实例加入列表和 schedulersCallTime。
  2. 文档切换、文档关闭、音频暂停或播放器释放时调用 RemoveScheduler。
  3. 移除方法只从 schedulers 列表删除，没有从 schedulersCallTime 删除。
  4. 调度器是应用级单例，因此字典键会保留这些实例直到进程结束。

源码证据

private readonly ConcurrentDictionary<ISchedulable, DateTime>
    schedulersCallTime = [];                         // 11

schedulers.Add(s);
schedulersCallTime[s] = DateTime.MinValue;          // 36-37

schedulers.Remove(s);                               // 111
// 缺少 schedulersCallTime.TryRemove(s, out _)

影响

长时间打开、关闭谱面或重复装载音频会让字典无界增长，并阻止对应编辑器和播放器实例被 GC。即使播放器释放时清空了大块采样数组，残留对象图、事件源和管理器引用仍会持续占用内存，也使生命周期测试产生误判空间。

修复方向与回归门槛

  • 移除调度项时同步删除时间记录；终止管理器时清空两个容器。
  • 把列表和时间状态纳入同一个原子所有权协议，避免只修字典却保留 CA-006。
  • 增加弱引用回收测试：注册并移除编辑器/播放器后，在管理器仍存活时实例应可被回收。

CA-006 调度器后台枚举与前台增删存在集合竞态

首次记录：2026-08-12 · 状态最后确认：2026-08-12

中 未修复 静态确认 活动
容器普通 List<ISchedulable>
读线程Task.Run 启动的后台循环
写线程Shell 文档事件和音频播放命令所在的 UI 线程

触发方式

在后台循环执行 LINQ 枚举期间切换/关闭文档，或播放、暂停音频。List<T> 在枚举中检测到版本变化会抛出 InvalidOperationException；增加操作中的“按名称查重再加入”也不是原子的。

源码证据

private readonly List<ISchedulable> schedulers = []; // 10

runTask = Task.Run(() => Run(runCts.Token), ...);    // 24

var pending = Schedulers                             // 48
    .Where(...)
    .Select(...)
    .ToArray();

schedulers.Add(s);                                   // 36
schedulers.Remove(s);                                // 111

循环会捕获并记录异常后重试，所以通常不是永久停止，而是丢失本轮调度、产生错误日志，并在频繁增删时出现抖动。

影响

音频的 60 FPS 属性刷新、编辑器性能统计和自动保存都共用该循环。竞态发生时会出现更新跳帧、自动保存周期延后或日志刷屏；重复注册检查也可能在多写线程下失效。

修复方向与回归门槛

  • 用锁保护增删并在锁内生成快照，随后在锁外调用调度项；或使用不可变快照/并发友好的注册表。
  • 注册、按名称去重、时间记录初始化和移除必须作为一个一致操作处理。
  • 增加压力测试，在循环运行期间并发增删数千次，断言无异常、无重复项且每个存活项仍能被调用。

CA-007 非正自动保存间隔会触发无延迟调度

首次记录：2026-08-12 · 状态最后确认：2026-08-12

高 未修复 静态确认 活动
输入FumenVisualEditorGlobalSettingView.axaml 的普通文本框
转换TimeSpan.FromMinutes(AutoSaveTimeInterval)，无下限检查
结果调度项每轮都到期，循环不执行 10 ms 退避

触发方式

在设置页把自动保存间隔输入为 0 或负整数，或者从旧/手工修改的配置中载入该值。模型、反序列化和 UI 均没有范围验证。

源码证据

Text="{Binding Setting.AutoSaveTimeInterval}"         // XAML: 35

scheduleCallLoopInterval = TimeSpan.FromMinutes(
    EditorGlobalSetting.Default.AutoSaveTimeInterval); // Manager: 165

DateTime.Now - lastCall >= ScheduleCallLoopInterval   // Scheduler: 49
// interval <= 0 时恒为 true；pending 非空时不会执行第 60 行的 Task.Delay

影响

没有活动文档时，调度器会以尽可能高的频率执行一个同步返回任务并占用 CPU；存在可保存文档时，它会连续生成恢复快照，造成高 CPU、持续磁盘/OPFS 写入、日志增长和界面卡顿。

修复方向与回归门槛

  • UI 改用带最小值的数值控件，并在模型反序列化/应用设置时再次钳制，不能只依赖控件验证。
  • 调度器自身拒绝或归一化非正间隔，作为所有 ISchedulable 的最后防线。
  • 增加对 0、负数和超大值的测试，使用调用计数证明固定时间窗内不会紧循环。

CA-008 单例绘制目标在每个编辑器中重复加载并保留纹理

首次记录：2026-08-12 · 状态最后确认：2026-08-12

高 未修复 静态确认 活动
生命周期TapDrawingTarget 等均注册为 Singleton
重复入口每个编辑器的 PrepareRenderLoop 都遍历并调用 Initialize
关闭行为编辑器只清空自身引用，不释放共享绘制目标

触发时序

  1. 打开第一个谱面，单例目标加载纹理并把纹理作为多个字典的键。
  2. 再打开一个谱面，同一单例目标再次执行 Initialize，字段被新纹理覆盖，并向既有字典继续加入新键。
  3. 旧纹理仍被字典强引用；关闭编辑器时 DisposeRenderResources 只把该编辑器的 drawingTargets 设为空。
  4. 重复开关文档会持续增加 Skia/GPU 图片对象和空绘制列表。

源码证据

[RegisterSingleton<IFumenEditorDrawingTarget>]       // Tap: 14

foreach (var drawTarget in drawingTargets)
    drawTarget.Initialize(renderImpl);               // Drawing VM: 232-233

texture = ResourceUtils.OpenReadTextureFromResource(...);
normalList[texture] = new();                         // Tap: 47-50

drawingTargets = [];                                // Drawing VM: 1189

TapDrawingTarget.Dispose 只释放当前 7 个纹理中的 4 个，且编辑器关闭时并不会调用它；BulletDrawingTarget 每次初始化还会把新纹理加入继承的绘制字典，但自身没有实现 IDisposable。

影响

打开多个谱面或反复关闭重开后，图形资源和字典项随初始化次数增长，可能造成工作集/GPU 资源上升、绘制循环额外遍历，以及最终的内存压力或渲染失败。单例目标还保存逐帧可变状态，所有权边界与多文档模型不一致。

修复方向与回归门槛

  • 优先让绘制目标成为每编辑器实例并由编辑器显式释放；可共享的不可变纹理资源应拆到独立缓存并采用引用计数或应用级所有权。
  • 所有实现必须完整释放其创建的 IImage，重复初始化前也要有确定的旧资源处理。
  • 增加双编辑器生命周期测试，跟踪创建/释放的图片数量，断言关闭后回到基线且两个编辑器不共享逐帧可变目标实例。
