CA-001 图片加载队列存在丢失唤醒竞态

首次记录：2026-08-12 · 状态最后确认：2026-08-12

高 未修复 静态确认 潜伏
位置ImageLoader.cs，LoadImage / PrcessQueue
结果返回的 Task<byte[]> 永久不完成
覆盖情况现有测试仅覆盖顺序缓存复用，没有并发入队测试

触发时序

  1. 已有处理器在 while (!tasks.IsEmpty) 处观察到队列为空，准备退出。
  2. 另一个线程在处理器执行 isProcessing = false 之前调用 LoadImage，先把任务压入栈，再调用 PrcessQueue。
  3. 新调用看到 isProcessing == true 后直接返回。
  4. 旧处理器随后把 isProcessing 置为 false 并退出；队列中已有新任务，但没有任何处理器，也没有后续唤醒。

源码证据

tasks.Push(new LoadTask(taskCompleteSource, url, cancellationToken)); // 50
PrcessQueue();                                                       // 51

while (!tasks.IsEmpty)                                               // 62
{
    ...
}

isProcessing = false;                                                // 99

ConcurrentStack 只保证栈操作本身线程安全，不会把“判空、入队、处理器状态切换”组合成一个原子协议，因此上述交错不依赖未定义行为。

影响

调用方会无限等待图片数据；如果 UI 正在等待该任务，表现为图片不再出现、加载状态不结束，或者依赖该任务的后续流程停滞。取消令牌在任务滞留队列期间也不会主动完成对应的 TaskCompletionSource。

修复方向与回归门槛

  • 使用单一、可证明无丢失唤醒的生产者/消费者原语，例如 Channel<LoadTask> 加固定数量消费者，或用锁保护“入队 + 启动/退出”状态机。
  • 增加确定性并发测试，覆盖“处理器判空后、清除运行标记前”发生入队的交错，并断言所有返回任务在超时内完成。
  • 本次全仓检索只找到单例注册和测试调用，未找到生产调用；问题当前属于潜伏缺陷，但代码一旦重新接入即可能触发。

CA-002 图片加载处理器门闩非原子，并发上限可失效

首次记录：2026-08-12 · 状态最后确认：2026-08-12

中 未修复 静态确认 潜伏
位置ImageLoader.cs，isProcessing / PrcessQueue
结果ParallelCount = 2 不能构成全局并发上限
附带成本达到局部上限时反复 Task.Yield，产生调度器空转

触发时序

  1. 两个线程近同时进入 PrcessQueue，都在另一个线程写入前读到 isProcessing == false。
  2. 两个线程都写入 true 并进入处理循环。
  3. 每个处理器都有自己的局部 currentTaskRunningCount，因此每个处理器都可以再启动两个工作任务；实际并发量可超过常量声明的 2。

  • 增加可控任务屏障测试：启动 A 的清理，在循环退出前启动 B 的准备，释放屏障后断言无异常且最终会话仍属于 B。

  • 在 BrowserOpfsBrowserViewModelTests 中用目录读取屏障复现：启动打开、先关闭、再释放刷新，并断言等待超过轮询间隔后没有新增服务调用；重新打开时只能存在一个轮询。

等待窗口方法先清空列表，再等待编辑器渲染初始化完成；新建文档尚未初始化时可长时间停在该边界

触发时序

  1. 激活渲染尚未初始化完成的编辑器 A，重建任务 A1 清空列表并等待 A 的初始化任务。
  2. 在 A 完成前切换到编辑器 B，再切回 A；这会启动第二个同样等待 A 的任务 A2。
  3. A 初始化完成后，A1 与 A2 捕获的引用都等于当前 Editor，因此两者都通过过期检查。

  5. UpdateRenderOrder 对重复包装器逐行写回同一个目标，后半组覆盖前半组，使实际顺序号变为 N..2N-1；继续拖动或保存会把错误状态扩大或持久化。

源码证据

{
    set
    {
        if (SetProperty(ref field, value))
            _ = RebuildItemsAsync(false);               // 无请求代次
    }

private async Task RebuildItemsAsync(bool sortByDefault)
{
    ControlItems.Clear();
    var editor = Editor;
    await editor.WaitForRenderInitializationIsDone();
    if (editor != Editor)                               // A → B → A 时仍为真
        return;

    foreach (var target in editor.CurrentDrawingTargets)
        ControlItems.Add(new RenderControlItem(target));
    UpdateRenderOrder();
}

WaitForRenderInitializationIsDone 返回同一编辑器的完成任务，因此 A1 与 A2 会在同一个信号后继续执行。比较对象引用只能拒绝当前为 B 的请求，不能拒绝已经绕回 A 的旧请求。

影响

修复方向与回归门槛

  • 为每次重建分配单调递增代次或取消前一请求；等待完成后同时核对编辑器引用和请求代次。
  • 先在局部变量中构建完整快照，确认请求仍有效后再一次性替换 UI 集合，避免半成品或多个续体交错追加。
  • 用可控初始化任务测试 A → B → A，按顺序释放 A/B，断言每个绘制目标恰好一行且顺序号从 0 连续递增。
  • 再覆盖连续执行重置默认值与关闭工具的情况，保证过期任务不能修改当前集合或全局绘制目标。

CA-029 渲染控制重排在文档切换后无法撤销

首次记录：2026-08-12 · 状态最后确认：2026-08-12

中 未修复 对象身份确认 活动
撤销快照Reorder 把当前 RenderControlItem 实例数组直接捕获进编辑器 A 的撤销动作
重建行为每次切换活动编辑器都会清空集合，并为绘制目标创建全新的 RenderControlItem 包装器
应用方式ApplyControlItemOrder 通过引用身份执行 ControlItems.IndexOf(oldItem)；旧包装器不在新集合时返回 -1 并静默跳过

触发方式

  1. 在编辑器 A 的渲染控制面板拖动一行。动作立即执行，并把旧/新顺序的包装器数组压入 A 的 UndoRedoManager。
  2. 切换到编辑器 B，再切回 A。单例工具重建列表，目标仍可相同，但所有行包装器已换成新实例。
  3. 对 A 执行撤销。撤销栈调用旧动作，但数组中的每个对象在当前 ControlItems 中都找不到。
  4. 循环不移动任何行，随后只按当前错误顺序重写一次顺序号；撤销栈却已经消费该动作，界面和渲染结果保持不变。

源码证据

    "Reorder render controls".ToLocalizedStringByRawText(),
    () => ApplyControlItemOrder(after),
    () => ApplyControlItemOrder(before));

private void ApplyControlItemOrder(IReadOnlyList<RenderControlItem> order)
{
    for (var i = 0; i < order.Count; i++)
    {
        var oldIndex = ControlItems.IndexOf(order[i]);   // 重建后的新集合找不到旧实例
        if (oldIndex >= 0 && oldIndex != i)
            ControlItems.Move(oldIndex, i);
    }
    UpdateRenderOrder();
}

RenderControlItem 没有按目标实现值相等，默认使用引用身份。即使底层 IFumenEditorDrawingTarget 是同一个单例，重新包装后也不会与撤销快照相等，因此这是确定的对象身份失配。

影响

用户在多文档间切换一次后，渲染顺序的撤销/重做会无提示失效；历史计数仍前进并把文档置脏，但实际顺序没有恢复。若随后保存渲染设置，用户原本打算撤销的全局配置仍会被持久化。

修复方向与回归门槛

  • 撤销快照应保存稳定目标身份及顺序，例如绘制目标类型/实例与其目标顺序，而不是保存易失的行包装器。
  • 撤销动作应绑定创建它的编辑器和目标集合；应用时按 Target 匹配当前行，并在工具当前显示其他文档时更新底层目标后按需重建界面。
  • 测试应在 A 重排、切到 B、切回 A 后执行撤销和重做，断言 UI 行序、每个目标的 CurrentRenderOrder 与历史计数同步变化。
  • 还需覆盖重建期间执行撤销，确保与 CA-028 的请求代次修复协同，不会让旧重建再次覆盖撤销结果。

实时修改已发生离开前的 PointerMoved 已经通过 OnDragMove 修改对象模型；只有正常 PointerReleased 的 OnDragEnd 才创建撤销动作并清理拖拽状态

CA-070 单独删除个人变速区域尾点后无法撤销

首次记录：2026-08-13 · 状态最后确认：2026-08-13

高 未修复 选择、删除、撤销与保存链确认 活动
尾点可被独立选择IndividualSoflanAreaDrawingTarget 分别把区域头和 EndIndicator 注册为可选择对象；键盘 Delete 会直接枚举当前选择

AddObject 不支持尾点Undo 对 expectedObjects 逐个调用 Fumen.AddObject，但其分派没有个人变速尾点分支，只记录 “add-in list target not found” 后返回

最小复现

  1. 创建一个个人变速区域，确保起点和右上角尾点处于不同位置。
  2. 只点击右上角尾点，使 IndividualSoflanAreaEndIndicator.IsSelected 为真，按 Delete。
  3. 删除器把尾点映射到父区域并从 IndividualSoflanAreaMap 移除整个区域，区域立即从画布和保存枚举中消失。
  4. 执行 Undo。撤销委托只调用 Fumen.AddObject(endIndicator)；该类型不被接受，日志出现警告，区域仍然缺失，但撤销历史已经前进。
  5. 保存并重新打开 OGKR 或 Nyageki，原区域永久丢失。

影响

用户点击的是一个明确可选择、可拖动的区间尾点，却会删除整个个人变速区域；最关键的是常规 Undo 无法恢复。保存后两种支持格式都不会再包含该区域，影响区域内物件的 Soflan 组归属和预览速度。操作表面上拥有正常的撤销历史项，因此用户可能在执行 Undo 后误以为数据已恢复并继续覆盖文件。

修复方向与回归门槛

  • 为所有复合区间对象建立明确的删除语义：选择尾点时可以拒绝删除、只移动/重置尾点，或规范化成删除父对象；无论选择哪种，Execute 与 Undo 必须操作同一个规范对象。
  • DeleteSelection 应先把选择集合归一化为可由 Fumen 容器添加/删除的所有者对象，并去重；不能让尾点进入普通 AddObject 分支。
  • AddObject/RemoveObject 应返回成功状态，删除命令只有在实际发生模型变化时才登记历史；Soflan/LaneBlock 尾点不能制造空历史和错误脏状态。
  • 回归测试分别只选中 IndividualSoflanArea、Soflan、InterpolatableSoflan 和 LaneBlock 的尾点，执行 Delete、Undo、Redo，并断言集合成员、端点值、可见对象、历史计数和脏状态一致。
  • 个人变速区域用例还必须在 Undo 后分别进行 OGKR/Nyageki 保存重载，断言区域、分组、起止 TGrid/XGrid 完整恢复且只出现一次。
