草案摘要

拟新增上下文

class EditorFileAccessContext
{
    ISimpleDirectory ProjectDirectory;
    List<ISimpleDirectory> AdditionDirectories;
    ISimpleFile ProjectFile;
    ISimpleFile FumenFile;
    ISimpleFile AudioFile;
}

class EditorContext
{
    EditorFileAccessContext FileAccessContext;
}

职责迁移

  1. 取消当前单一 FumenVisualEditorProvider 的跨平台业务混合，按 Browser 与 Desktop 实现不同 Provider。
  2. FumenVisualEditorViewModel 不再负责无参数 New()、Load() 和 Load(RecentRecordInfo) 的平台交互。
  3. Provider 完成选择、权限恢复和上下文构造；ViewModel 接收 New(EditorContext) 或 Load(EditorContext)。
  4. EditorFileAccessContext 与 RecentRecordInfo 之间建立转换或恢复关系。

平台行为

入口BrowserDesktop
新建项目文件夹 + 音频 + 可选已有谱面与 Browser 相同
打开项目文件夹保留现有目录选择流程草案未明确是否保留
打开 .nyagekiProj草案未声明按桌面本地文件流程构造上下文
Fast Open不支持从原始谱面及音频推导上下文

已核实事实

  1. EditorFileAccessContext 与 EditorContext 目前只存在于草案，生产代码尚无实现。
  2. 当前只有一个核心层 FumenVisualEditorProvider，同时注册为 IEditorProvider 与 IFumenVisualEditorProvider；CanCreateNew 仍为 false。
  3. 当前 Provider 的三个入口只是把操作转发给 ViewModel：New()、Load()、Load(RecentRecordInfo)。
  4. 当前普通打开通过 IStorageFolder 取得目录能力，转换为 ISimpleDirectory，扫描并选择项目文件，再由 ViewModel 加载。
  5. 当前最近记录的附加数据已经保存“文件夹书签 + 项目相对定位符”；LocationDescription 只承担显示用途。
  6. ISimpleFile 与 ISimpleDirectory 都实现 IDisposable，因此上下文不是纯数据对象，必须有明确所有权和失败释放规则。
  7. 当前 EditorProjectDataModel 持有项目根、工程、谱面、音频和 AWB 句柄；属性替换会释放旧值，编辑器关闭时调用 DisposeRuntimeFiles()。
  8. 已检查的 ISimpleFile/ISimpleDirectory 实现均没有终结器；IDisposable 不会触发自动清理。Avalonia 实现的 Dispose() 会释放底层 IStorageFile/IStorageFolder，目录还会递归释放子项。
  9. 既有设计文档 D25 已决定由每个编辑器独占的异步项目会话统一持有文件能力、缓存和取消状态；新草案尚未说明是继承、替代还是撤销该决策。
  10. Fast Open 的命令处理器存在但未在跨平台核心项目注册；字符串与 ISimpleFile 快速打开逻辑受 ENABLE_CROSS_PLATFORM_FAST_OPEN 条件编译控制。
  11. Browser 与 Desktop 已有独立项目和独立服务注册入口，可承载平台 Provider，但当前核心 Provider 的自动注册需要相应调整，避免重复实现同时出现在容器中。
  12. 旧 WPF 新建流程不会复制外部输入，只保存绝对路径；现有 Avalonia 设计曾为音频规定 autoImport/audioFiles/，但明确禁止标准跨平台流程复制外部谱面。Q3 的新决定会覆盖后一个限制。

主要证据：当前 Provider、当前项目 I/O、运行时文件所有权、既有文件系统设计决策。

初步审查

已接受风险本次重构不新增资源所有权协议。 按 Q2 的取向，继续依赖当前 EditorProjectDataModel.DisposeRuntimeFiles()、属性替换释放以及 ViewModel 关闭清理。技术上 IDisposable 本身不会自动调用；因此任何未进入现有模型清理链的候选句柄仍可能泄漏，但该问题不纳入本方案继续设计。
冲突“与 RecentRecordInfo 相互转换”在类型层面不成立。 最近记录是可持久化描述和不透明恢复数据；ISimpleFile/ISimpleDirectory 是当前进程中的能力对象。合理关系应是“上下文生成最近记录恢复描述”与“Provider 使用最近记录异步恢复一个新上下文”，而不是对象间对称转换。
缺口草案没有表达定位符、创建模式和可选性。 新建时 ProjectFile 可能尚不存在，FumenFile 明确可选；项目加载还需要项目根相对定位符来做边界校验、最近记录和显示。当前非空可变属性无法表达这些状态。
已确认新建流程完成复制后必须重新绑定项目内文件。 外部选择器返回的音频和可选谱面只作为复制源；复制、校验完成后，从 ProjectDirectory 取得目标 ISimpleFile，并以该对象填充上下文及后续工程模型。外部源不能成为编辑器的长期文件引用。
命名Provider 示例名存在歧义。 DefaultDesktopBrowserEditorProvider 同时包含 Desktop 与 Browser，无法直观看出平台归属。若确实拆分，建议采用 BrowserFumenVisualEditorProvider 与 DesktopFumenVisualEditorProvider，或项目现有命名约定下的等价名称。

当前问题

Q4：新建工程复制输入文件时，项目目录采用哪种固定布局？

  1. ProjectDirectory/audio/<音频文件>、ProjectDirectory/charts/<谱面文件>，.nyagekiProj 位于项目根。
  2. 全部直接复制到 ProjectDirectory 根目录。
  3. 沿用导入区：autoImport/audioFiles/ 与新增的 autoImport/fumenFiles/，工程文件位于项目根。

建议答案：选择第 1 种。

audio/ 与 charts/ 表达项目的正式资源，而 autoImport/ 更适合作为后续追加导入和内容寻址缓存区。固定分目录也能避免项目文件、谱面和音频同名冲突。此问只确定目录布局；保留原名、哈希命名、覆盖或自动改名会在下一问确认。

决策记录

D1 / Q1：EditorFileAccessContext 是普通 DTO
已确认选择方案 1。上下文只用于传递数据和资源引用，本身不拥有、不释放 ISimpleFile 或 ISimpleDirectory，也不作为贯穿编辑器生命周期的项目会话。既有 D25 的会话所有权设计不适用于本重构。
D2 / Q2：不为 DTO 引用另行设计所有权机制
用户要求忽略所有权问题，并以相关类型实现 IDisposable 为理由。审查结论按实际代码语义规范化为：本次重构保持现有 EditorProjectDataModel 与 ViewModel 的显式释放链，不新增 IProjectSession 或其他所有者；未进入现有清理链的资源泄漏风险被明确接受。IDisposable 不等于自动回收。
D3 / Q3：外部音频和可选谱面先复制到项目目录再引用
已确认选择方案 1。Provider 选择到的外部文件只作为一次性复制源；文件必须先复制并校验到 ProjectDirectory 范围内，再从项目目录取得对应 ISimpleFile 填充 EditorFileAccessContext.AudioFile/FumenFile。工程只保存项目根相对定位符，不长期依赖外部目录权限。该决定覆盖既有 D21“标准跨平台流程不复制外部谱面”的限制。
