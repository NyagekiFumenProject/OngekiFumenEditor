WPF 项目代码审查

报告文件：docs/wpf-code-review-2026-10-09.html　|　审查对象：OngekiFumenEditor/　|　状态：已完成

本报告记录静态代码审查发现的可复现程序缺陷。发现按严重度编号，审查过程中持续追加；仅记录有明确触发路径、后果和可执行修复方向的问题，不把纯风格意见列为 bug。

审查结果：共确认 38 项问题，其中 Critical 4 项、High 22 项、Medium 12 项。优先处理 IPC 死锁/异常转储、工程救援与双文件保存、更新器回滚、图形初始化等待和音频异步生命周期问题。

审查范围与方法

  • 启动、退出、异常处理、日志和崩溃转储。
  • 文件/数据 I/O、谱面解析与保存、设置、缓存和资源生命周期。
  • WPF UI、Dispatcher、async/await、线程、音频、渲染、事件和并发。
  • 通过源码路径、调用链和已有构建结果交叉核对；必要时补充最小化复现或构建验证。

严重度定义

级别含义
Critical可导致数据损坏/丢失、进程无法启动或大范围崩溃，且触发条件现实。
High常见操作下导致崩溃、功能不可用或关键结果错误。
Medium特定输入、环境或时序下出现明显错误、丢失或不一致。
Low影响有限但可确认的错误，或需要较苛刻条件才能触发。

发现项

F-001 · Medium　ShowXOffsetScrollBar 写入了错误的设置项

位置： OngekiFumenEditor/Modules/FumenVisualEditor/Models/EditorSetting.cs:187-196

触发条件： 用户在编辑器设置中切换“显示 X 偏移滚动条”。ShowXOffsetScrollBar 的 setter 第 193 行把值写入了 EditorGlobalSetting.Default.ForceXGridMagneticDock，而不是 ShowXOffsetScrollBar。

后果： X 偏移滚动条选项无法正确持久化；每次切换还会覆盖“强制 X 网格吸附”的设置。当前会话内 backing field 可能暂时显示用户选择，但重启后从配置重新加载时会恢复旧值，同时网格吸附行为可能被意外改变。

推荐解决方案： 将赋值改为 showXOffsetScrollBar = Properties.EditorGlobalSetting.Default.ShowXOffsetScrollBar = value;，并增加设置 setter 回归测试：分别切换两个选项，保存并重新加载设置，验证两个属性互不影响。

F-002 · High　图像加载失败会让等待者永久挂起

位置： Utils/ImageLoader.cs:37-70、:140-166

触发条件： 图片文件不存在、网络请求失败、缓存损坏，Load() 返回 null；ProcessTask 随后无条件访问 r.Length。后台 Task.Run 的异常没有传给 TaskCompletionSource，也没有 finally 清理并发计数。

后果： 图片绑定等待的 Task 永不完成，界面可能永久显示加载中；队列任务异常也无法被调用方观察。

推荐解决方案： 将消费者改成可等待的 Task，在统一 try/catch/finally 中处理 null、缓存异常和取消，使用 TrySetResult/TrySetException/TrySetCanceled，始终递减运行计数并删除损坏缓存。

F-003 · High　确定性临时缓存路径在命中后忙等死循环

位置： Utils/TempFileHelper.cs:14-24、ImageLoader.cs:109-123

触发条件： ImageLoader.GetCacheFile 以 random:false 请求固定文件名。文件第一次写入后，GetTempFilePath 仍循环等待“文件不存在”，但没有任何删除或改名路径。

后果： 同一网络图片第二次加载会占满一个线程并永久卡在生成缓存路径，调用方同时因 F-002 无法完成。

推荐解决方案： random:false 直接返回确定性路径；随机模式才检查冲突。缓存读写还应使用临时文件和原子替换，避免半写文件成为永久缓存。

F-004 · High　转换器在检查空输入前解引用路径

位置： FumenConverterWrapper.cs:16-30、DefaultFumenParser.cs:16-22

触发条件： 转换对话框未选择输入文件，option.InputFumenFilePath 为空；代码先调用 GetDeserializer，解析器内部直接对 null 调用 EndsWith。

后果： 用户应得到“未选择输入文件”的结果，却收到 NullReferenceException；命令行或异步 UI 调用还可能把异常升级为未处理异常。

推荐解决方案： 先用 IsNullOrWhiteSpace 验证输入，再调用 parser manager；manager 的 serializer/deserializer API 也应对空路径返回 null 而不是解引用。

F-005 · High　转换输出不会截断旧文件尾部

位置： FumenConverterWrapper.cs:52-57

触发条件： 输出文件已存在且本次转换结果比旧文件短。File.OpenWrite 使用 OpenOrCreate，从位置 0 覆盖但不截断文件。

后果： 旧尾部字节保留，生成的谱面或二进制文件可能包含不可见残留，解析失败或内容异常。

推荐解决方案： 使用 FileMode.Create 或 File.WriteAllBytesAsync；更稳妥是同目录临时文件写完并 Flush 后原子替换目标。

F-006 · High　旧项目缺少音频路径时无法进入手动选音频流程

位置： EditorProjectDataUtils.cs:24-45

触发条件： 旧版本或手工编辑的工程 JSON 中 AudioFilePath 为 null、空字符串或空白。代码只为 FumenFilePath 提供默认值，随后直接把 AudioFilePath 传给 Path.Combine。

后果： 工程在打开阶段抛异常，用户无法进入编辑器再手动选择音频；空字符串的 FumenFilePath 也不会触发默认谱面路径。

推荐解决方案： 对两个字段统一使用 IsNullOrWhiteSpace；谱面路径为空时生成工程同名 .ogkr，音频路径为空时保留为空并交给 UI 的音频选择流程处理。

F-007 · Critical　工程文件与谱面文件的双写不是原子操作

位置： EditorProjectDataUtils.cs:142-183

触发条件： 保存工程时先覆盖项目文件，再覆盖谱面文件；任一步骤中断、磁盘满、进程崩溃或断电。

后果： 项目文件可能已经指向新内容，而谱面仍是旧内容、半写内容或不存在，形成不可恢复的项目/谱面不一致。临时文件也没有 finally 清理。

推荐解决方案： 两个临时文件分别写入并 Flush(true)，验证可重新加载后，用备份/事务清单协调替换；至少先替换谱面和项目的临时副本，失败时保留旧文件并清理临时文件。

F-008 · Critical　崩溃救援工程引用错误路径，未保存谱面无法恢复

位置： Utils/DeadHandler/FumenRescue.cs:38-80

触发条件： 崩溃救援先按原 EditorProjectData 保存项目，再另存谱面。第 67-68 行在原谱面名非空时才随机改名；原路径为空时文件名为空，且项目中的 FumenFilePath 从未改为救援目录内的文件名。

后果： 救援项目仍指向原路径，打开救援目录时找不到刚写出的谱面；新建/未保存文档还会把目录路径当输出路径而保存失败，崩溃时丢失未保存谱面。

推荐解决方案： 先生成确定的救援谱面文件名（空路径使用文档名或随机名），克隆项目数据并改为相对救援路径，再分别写临时文件、重新加载验证后原子落盘。

F-009 · Medium　损坏的最近文件配置会阻止启动

位置： DefaultEditorRecentFilesManager.cs:40-52

触发条件： 最近文件 Base64 被截断、JSON 被手动修改，或 JSON 反序列化返回 null。

后果： 构造 recent-files manager 时异常直接冒出，编辑器可能在启动早期退出；list.Take 对 null 还会产生 NullReferenceException。

推荐解决方案： 分别捕获 Base64/JSON 异常，把坏数据移到备份并回写空列表；反序列化结果使用空列表兜底，不让最近文件阻断主程序启动。

F-010 · High　窗口位置配置受区域设置影响并可能直接阻断启动

位置： AppBootstrapper.cs:333-339、:420-427

触发条件： 关闭窗口时用当前文化格式化 double 并用逗号拼接；在逗号小数文化下保存的值再次按逗号 Split 会被拆成更多字段。配置被截断或手工修改时也没有长度和格式校验。

后果： 下次启动可能在 UI 初始化阶段抛 FormatException/IndexOutOfRangeException，或把位置和尺寸错位解析。

推荐解决方案： 使用 JSON/四个独立设置项，数字统一 InvariantCulture；读取使用 TryParse、数量检查和屏幕边界校验，失败时忽略配置并恢复默认。

F-011 · Critical　IPC 写入忙时未释放 Mutex，会造成双向死锁

位置： Utils/IPCHelper.cs:114-136

触发条件： 共享内存的消息槽仍有数据时，WriteLine 在已取得 Mutex 后直接 continue，没有 ReleaseMutex。

后果： 发送端永久持有命名 Mutex 并等待槽清空；接收端读取完成后再次等待同一 Mutex，第二实例/宿主通信和退出都可能永久卡死。

推荐解决方案： 将读取、写入和释放放进 try/finally；发现槽忙时先释放锁再等待，并使用信号量/事件而不是持锁 Sleep。

F-012 · High　IPC PID 存在 TOCTOU 和跨安装误路由

位置： IPCHelper.cs:41-70、:148-162

触发条件： 从 MMF 读出 PID 后目标进程恰好退出，或 PID 已被系统复用；源码 Debug、Release、桌面部署同时运行时还共享固定的 MMF/Mutex/Event 名称。

后果： Process.GetProcessById 可直接抛异常；更危险的是命令可能被发送给另一套安装，或被更新器按名称误杀。

推荐解决方案： 用命名 Mutex 原子选主，校验进程路径、启动时间和安装实例 ID；对象名称包含规范化安装标识和用户 SID。处理进程退出/复用的 TOCTOU，失效时清理并重试。

F-013 · Medium　IPC 消息长度截断但发布了原始长度

位置： IPCHelper.cs:129-135

触发条件： 序列化后的命令超过 MMF 可用容量。写入数据按容量截断，但长度字段仍写入 buffer.Length。

后果： 接收端按超出实际数据的长度读取，可能越界、抛异常或破坏后续 IPC 状态；命令内容也已损坏。

推荐解决方案： 发布实际写入长度并拒绝超长消息；更好是分片传输或改用命名管道，并在读写两端做最大长度校验。

F-014 · High　IPC 线程退出时可能与 UI 互相等待

位置： AppBootstrapper.cs:434-460、:673-676

触发条件： IPC 线程收到命令后同步调用 Dispatcher.Invoke，同时 UI 线程进入退出流程并调用 ipcThread.Abort()，而 Abort 默认等待线程结束。

后果： IPC 线程等待 UI 执行命令，UI 线程等待 IPC 线程退出，形成关闭死锁。

推荐解决方案： 使用 Dispatcher.InvokeAsync 并在 IPC 线程不阻塞等待；退出时先取消并设置有界等待，超时后记录并继续关闭。

F-015 · Critical　AppDomain 未处理异常回调可能在转储前终止进程

位置： AppBootstrapper.cs:525-571、:639-646

触发条件： AppDomain.UnhandledException 事件通过 async void 调用 ProcessException 后立即返回；CLR 随后进入终止流程，而处理器还可能停在第一次 await。

后果： DumpFileHelper.WriteMiniDump、FumenRescue 和异常报告窗口可能根本没有执行。若首个文件日志写入失败，也会直接跳过转储。

推荐解决方案： 对 AppDomain/native 异常使用同步最小路径：先写 dmp，再做有界日志刷写；每条日志独立捕获异常，不能让日志 I/O 阻断转储。异常处理入口还应以 Interlocked 闸门防并发重入。

F-016 · High　OnExit 的异步清理不受 WPF 等待，异常还会跳过后续步骤

位置： AppBootstrapper.cs:655-687、SchedulerManager.cs:180-208

触发条件： OnExit 是 async void，首个未完成 await 后 WPF 不会等待；音频 Dispose、Scheduler.Term 或某个 OnSchedulerTerm 抛异常时，后续日志和 base.OnExit 不再执行。

后果： 正常退出可能留下调度线程、音频资源和未写入日志；CLI/更新器也可能卡在清理任务。

推荐解决方案： 把退出协调移到同步可等待入口，或每一步使用有界同步等待；每个清理步骤独立 try/finally，Scheduler 逐项捕获异常，最终无论如何都执行日志刷写和 base.OnExit。

F-017 · High　更新器会按进程名杀掉其它安装和实例

位置： DefaultProgramUpdater.cs:420-433

触发条件： 更新器枚举所有名为 OngekiFumenEditor 的进程，只排除自己的 PID，不校验可执行文件路径。

后果： 源码、Release、桌面部署或其他用户实例可能被强制终止，未保存文档和日志丢失。

推荐解决方案： 只处理目标安装目录内、且启动时间/实例 token 匹配的进程；优先通过 IPC 请求正常退出，禁止按进程名全局 Kill。

F-018 · High　更新失败回滚无法覆盖已经复制的新文件

位置： DefaultProgramUpdater.cs:376-398

触发条件： 更新复制阶段中途失败，目标文件已经存在新版本；回滚使用不带 overwrite 的 File.Move(backup, target)。

后果： 回滚移动因目标存在而失败，安装目录留下新旧文件混合状态，程序可能无法启动或加载错误程序集。

推荐解决方案： 使用全新 staging 目录并原子切换；若保留现有方案，回滚前安全删除/替换目标并逐项校验恢复结果，失败时阻止启动并保留可恢复备份。

F-019 · High　Skia/OpenGL 初始化异常会让等待者永久等待

位置： DefaultSkiaDrawingManagerImpl.cs:44-94、DefaultOpenGLRenderManagerImpl.cs:198-210

触发条件： 初始化通过 Dispatcher.CurrentDispatcher.InvokeAsync(...) fire-and-forget；项目的 NoWait 扩展为空实现。Initialize 抛异常时，初始化 TCS 不会 SetException；取消令牌也没有传给等待任务。

后果： 编辑器等待渲染初始化直到外层超时或永久挂起，真实图形错误被隐藏，异常还可能以未观察任务形式出现。

推荐解决方案： 使用应用 UI Dispatcher 并 await 初始化任务；在 catch/finally 中 TrySetException/TrySetCanceled，WaitForInitialization 必须真正响应 CancellationToken。应删除空的 NoWait 实现或至少统一观察异常。

F-020 · High　自动保存在线程池直接访问 UI 编辑器对象

位置： DefaultEditorDocumentManager.cs:90-103

触发条件： SchedulerManager 使用 TaskScheduler.Default 运行自动保存；代码中的 Dispatcher.CurrentDispatcher 只是取得当前线程的 Dispatcher，并没有切回 WPF UI 线程。

后果： 保存期间可能与用户编辑并发读写 Observable/模型集合，出现枚举修改、半更新快照或保存内容不完整。

推荐解决方案： 将保存快照或整个保存操作派发到应用 UI Dispatcher；为每个编辑器加保存互斥和取消旧保存机制，并让保存接受 scheduler cancellationToken。

F-021 · High　播放结束回调使用了错误的 Dispatcher

位置： AudioPlayerToolViewerViewModel.cs:78-89、DefaultMusicPlayer.cs:78-82

触发条件： NAudio 线程触发 OnPlaybackFinished，回调中使用 Dispatcher.CurrentDispatcher。该属性取得的是音频线程自己的 Dispatcher，不是应用 UI Dispatcher。

后果： OnStopButtonClicked、编辑器滚动和属性通知可能在线程错误上执行，触发跨线程异常；若文档同时关闭，回调还可能访问已失效 Editor。

推荐解决方案： 保存并使用应用 UI Dispatcher，使用 BeginInvoke/InvokeAsync；派发前校验当前 editor/player 身份，关闭后取消回调。

F-022 · High　音频 Stop/Dispose 的 async void 竞态会在释放后访问 reader

位置： DefaultMusicPlayer.cs:159-193

触发条件： Stop 移除 scheduler 后 await；期间另一条关闭/换曲路径进入 Dispose 并把 audioFileReader 置 null，Stop 恢复后仍调用 Seek。Play/Pause/Dispose 都是 async void，调用方无法等待或串行化。

后果： 快速切歌、关闭窗口或退出时会产生 NullReferenceException/未观察异常，且 NAudio 资源可能在 scheduler 仍使用时被释放。

推荐解决方案： 改为可等待的 Task/ValueTask，使用生命周期锁或取消令牌串行化 Play/Stop/Pause/Dispose；Dispose 必须幂等，先停止 scheduler 和 mixer，再释放 reader。

F-023 · High　波形后台任务的取消异常和旧结果发布未受控

位置： WaveformDrawing.cs:219-249、PeakPointCollection.cs:20-30

触发条件： Task.Run 调用 async void；切歌或修改采样尺寸时取消旧 token，但 GetSamplesAsync 返回后没有再次确认当前 player/generation，ResamplePeak 取消异常也没有调用方捕获。

后果： TaskCanceledException 可进入全局异常处理；旧音频的波形或节奏曲线可能覆盖新音频，界面出现串曲数据。

推荐解决方案： 全链路改为 Task，统一 catch OperationCanceledException；每次加载分配 generation，只有 token 未取消且 player 仍是当前实例时才发布结果。

F-024 · Medium　关闭编辑器/工具后全局事件仍持有旧对象

位置： FumenVisualEditorViewModel.cs:188-196、:465-475、AudioPlayerToolViewerViewModel.cs:152-161、:288-292

触发条件： 编辑器和音频工具订阅全局设置/文档管理器事件，但关闭和 Dispose 只释放部分渲染资源，没有解除这些订阅或取消所有异步波形任务。

后果： 单例事件源长期持有已关闭 ViewModel；反复开关文档/工具会累积回调、内存和 CPU，回调还可能访问已经释放的渲染状态。

推荐解决方案： 实现完整 Dispose，解除 EditorSetting、UndoManager、文档管理器和 RenderContext 事件，停止渲染、取消 CTS，并确保关闭路径最终调用它。

F-025 · Medium　Music.xml 读取流未释放

位置： Utils/DocumentOpenHelper.cs:201-235

触发条件： XDocument.LoadAsync(File.OpenRead(...)) 直接把流交给 XML 加载，没有 using。

后果： 每次快速打开/读取 Music.xml 都可能在 Windows 保留文件句柄，阻止文件替换删除，长时间运行还会耗尽句柄。

推荐解决方案： 使用 using 声明包住 FileStream，或调用带路径的 XML API；在异常和取消路径也确保释放。

F-026 · Medium　配置直接覆盖写，崩溃可留下截断 JSON

位置： OverlayJsonSettingsProvider.cs:43-75

触发条件： 保存配置使用 File.WriteAllText 直接覆盖正式文件，进程崩溃、断电或磁盘写满发生在写入中途。

后果： config.json 可能变成半个 JSON；下次加载若根节点/分组类型异常，GetPropertyValues 还可能对 null 直接调用 TryGetPropertyValue，造成启动或设置页崩溃。

推荐解决方案： 同目录临时文件写入并 Flush 后 File.Replace，保留 .bak；加载损坏配置时恢复备份或空对象，并对节点类型做校验。

F-027 · Medium　IsPathWritable 的检查方式会误报可写

位置： Utils/FileHelper.cs:34-46

触发条件： 现有文件只用 FileAccess.Read 打开测试，目录/新文件则直接认为可写；ACL、只读属性或安装目录权限禁止写入时仍可能返回 true。

后果： 保存流程通过预检查后才在真正 File.Copy 时失败，用户得到延迟且不准确的错误；自动保存还可能反复失败。

推荐解决方案： 检查目标目录并以 FileAccess.Write/Append 做最小写入测试，处理只读属性和 ACL；不要把“能读”命名为“可写”。

F-028 · High　同一秒内 dmp 文件名会互相覆盖

位置： DumpFileHelper.cs:55-61

触发条件： 文件名只使用当前文化的 DateTime.Now.ToString()，精度到秒；多个托管异常或异常处理重入发生在同一秒。

后果： 后一次 FileMode.Create 覆盖先前 dmp，用户丢失第一个崩溃现场；路径还受当前区域设置影响。

推荐解决方案： 使用 UTC/InvariantCulture 的毫秒或 ticks 加 Guid，并以 CreateNew 原子占用文件名；异常处理闸门应同时避免重复写 dump。

F-029 · Medium　保存和标准化产生的临时文件长期不清理

位置： EditorProjectDataUtils.cs:86-131、TempFileHelper.cs:10-25、StandardizeFormat.cs:24-32

触发条件： 保存/转换成功或异常后只复制临时文件，不在 finally 删除；标准化还会先由 GetTempFileName 创建一个额外临时文件。

后果： 频繁 Ctrl+S、自动保存和转换会在临时目录积累项目/谱面副本，最终占满临时盘并拖慢扫描。

推荐解决方案： 使用 try/finally 删除临时文件；需要恢复时使用明确命名、带保留期限的备份清理策略，不要把所有临时副本永久保留。

F-030 · High　ACB 音频缓存会跨文件误复用

位置： Kernel/Audio/AcbConverter.cs:84-96

触发条件： 缓存路径只使用 ACB 的文件名，不含完整路径、文件大小、修改时间或内容哈希；不同目录有同名 ACB，或源文件更新。

后果： 编辑器可能播放另一目录的旧 WAV，用户看到/听到的内容与当前工程不一致且不易察觉。

推荐解决方案： 以规范化绝对路径和文件元数据/内容哈希生成缓存 key，并在命中时校验元数据，不匹配就重新解码。

F-031 · High　日志等待屏障存在入队竞态

位置： Utils/Log.cs:171-183、:77-99

触发条件： WaitForAllLogWriteDone 无锁读取 isRunning；它读到 false 后，另一个线程才在 drainLock 中入队并启动 drainer。

后果： 关闭/异常刷写可能在这条记录进入 file sink 前返回，导致仍有少量日志遗漏。

推荐解决方案： 用同一把锁检查队列和运行状态，并返回可等待的 completion TCS；关闭时设置停止标记，拒绝或同步接收新的日志，直到屏障完成。

F-032 · High　参数处理丢弃异步任务

位置： DefaultArgProcessManager.cs:34-69

触发条件： ProcessArgs 声明为 async Task，但内部通过 Dispatcher.Invoke(async ...) 和 NoWait 丢弃返回 Task。

后果： 打开文件/等待资源的异常无法回传，IPC 调用方会误以为处理完成；连续打开或退出时可能出现竞态和未观察异常。

推荐解决方案： 使用 Dispatcher.InvokeAsync 并 await/Unwrap 内部 Task，确保命令顺序、异常和取消由调用方掌握。

F-033 · High　更新检查窗口在 UI 线程同步 Wait 可能死锁

位置： DefaultProgramUpdater.cs:150-154

触发条件： UI 点击处理器调用 ShowWindowAsync(...).Wait()，而窗口创建通常需要 UI Dispatcher 继续泵消息。

后果： 更新对话框可能永远打不开，UI 线程被阻塞，后续关闭和日志刷写也无法执行。

推荐解决方案： 将点击处理器改为 async Task/async void 事件并 await ShowWindowAsync；捕获显示异常并恢复按钮状态。

F-034 · Medium　脚本保存和快捷键配置也会被半写覆盖

位置： EditorScriptDocumentViewModel.cs:191-205、DefaultKeyBindingManager.cs:49-54

触发条件： 两处都直接对正式文件调用 WriteAllTextAsync/WriteAllText。

后果： 崩溃、断电或磁盘满会留下空文件/截断 JSON，用户脚本或快捷键配置丢失。

推荐解决方案： 同目录临时文件写入并 Flush 后原子 Replace，保留 .bak；加载坏文件时自动恢复备份并提示用户。

F-035 · Medium　设置延迟保存在退出或异常时会丢值

位置： EditorSetting.cs:15-23

触发条件： setter 只启动 2 秒后的 async void 保存；用户在延迟结束前退出或进程异常，保存任务没有被等待。

后果： UI 中已经修改的编辑器设置只存在内存，重启后恢复旧值；Save 抛异常还会让 isRequestSave 永久保持 true，后续设置不再保存。

推荐解决方案： 用可取消/可等待的 debounce 任务，在 OnExit 强制 Flush；Save 放在 try/finally 中恢复状态并记录错误。

F-036 · High　命令行/更新器也会启动 GUI 更新检查并拖住退出

位置： AppBootstrapper.cs:243-260、DefaultProgramUpdater.cs:500-515

触发条件： CLI 启动 Scheduler 后，更新器调度任务仍按默认设置执行 HTTP 检查，并忽略 scheduler cancellationToken。

后果： 命令行任务或更新器退出时可能等待网络默认超时，无法按预期快速结束。

推荐解决方案： CLI/Updater 模式禁用 GUI-only scheduler；更新检查接受取消令牌并设置明确超时，Scheduler.Term 对未结束任务有界等待。

F-037 · Medium　异常转储回调可能因写盘问题自身失败

位置： DumpFileHelper.cs:122-126

触发条件： native 未处理异常过滤器直接调用 WriteMiniDump，没有 catch；路径无权限、磁盘满或日志刷写死锁时异常会从过滤器继续抛出。

后果： 本应生成的 dmp 可能完全没有，进程也可能停在异常过滤流程。

推荐解决方案： native 回调使用最小同步写 dmp 路径，所有日志操作限时并 catch；写盘失败只能写 Debug/事件日志，不能阻断过滤器返回。

F-038 · Medium　渲染事件未完整解除会持续泄漏资源
