位置： Utils/IPCHelper.cs:114-136

触发条件： 共享内存的消息槽仍有数据时，WriteLine 在已取得 Mutex 后直接 continue，没有 ReleaseMutex。

后果： 发送端永久持有命名 Mutex 并等待槽清空；接收端读取完成后再次等待同一 Mutex，第二实例/宿主通信和退出都可能永久卡死。

F-080 · High 播放按钮在 Prepare 期间可并发启动多条音频状态机

位置： AudioPlayerToolViewerViewModel.cs:221-246、DefaultFumenSoundPlayer.cs:159-181

触发条件： RequestPlayOrPause 是 async void，没有互斥标志；第一次点击 await Prepare 时 AudioPlayer.IsPlaying 仍为 false，连续点击会再次进入 Prepare。

后果： 多个 Prepare 交错 Abort 旧线程、重建事件并启动新线程，随后各 continuation 分别 Seek/Play，可能重复播放、状态回退或产生未观察异常。

推荐方案： 使用 SemaphoreSlim 或操作版本令牌串行化播放/暂停，立即设置 pending 状态禁用按钮；关闭时取消并等待当前操作。

F-081 · Medium 文件日志名称秒级忙等且多实例会互相追加

位置： FileLogOutput.cs:30-37

触发条件： Init 以当前文化的 DateTime.Now（精确到秒）拼文件名，使用 File.Exists 检查后在同一秒循环；两个实例之间没有原子占用。

后果： 快速重启命中旧文件时在当前秒内占满 CPU；并行实例可能选择同名路径并交错 AppendAllText，异常现场日志混合且顺序不可信。

推荐方案： 使用 UTC/InvariantCulture 的毫秒加 Guid，并用 FileMode.CreateNew 原子抢占文件名；冲突只做有限重试，不能在初始化阶段无限自旋。

F-082 · High OpenGL 兼容模式请求 3.3 却调用 4.5 DSA API

位置： DefaultOpenGLRenderManagerImpl.cs:166-208、DefaultOpenGLTexture.cs:23-67、DefaultInstancedLineDrawing.cs:108-143

触发条件： 用户启用 GraphicsCompatibility 后创建 OpenGL 3.3 compatibility profile，但纹理和绘制代码直接使用 GetTextureParameter、NamedBufferStorage、VertexArrayVertexBuffer 等 OpenGL 4.5/DSA API。

后果： 不支持 ARB_direct_state_access 的旧 GPU 会在首个纹理或绘制命令上报 GL_INVALID_OPERATION/入口不可用，编辑器无法渲染；设置名为“兼容”反而成为稳定崩溃入口。

推荐方案： 兼容路径绑定对象后使用传统 TexParameter/BufferData/VertexAttribPointer，或先探测扩展并明确降级；不要在 3.3 配置下无条件调用 4.5 API。

F-083 · High 公共谱面 Serialize API 会先截断正式 OGKR

位置： Parser/IFumenParserManager.cs:14-25

触发条件： 默认 Serialize 直接调用 File.WriteAllBytesAsync(saveFilePath, ...)；进程崩溃、磁盘已满或取消发生在写入中间时，目标文件已经被截断。

后果： 用户原有谱面可能变成 0 字节或半写文本，后续解析失败且没有备份；这条公共 API 也会影响未来绕过项目保存工具的调用方。

推荐方案： 同目录临时文件写完并 Flush(true)，重新加载校验后使用 File.Replace/Move 原子替换；失败保留原文件并清理临时文件。

F-084 · High 新版或第三方 bullet 枚举值会让整谱无法打开

位置： BulletCommandParser.cs:18-34、BulletPalleteCommandParser.cs:20-34

触发条件： 文件中出现更新游戏或第三方工具新增的 damage/shooter/target/size token，解析器的 switch 直接抛 NotImplementedException，没有未知值策略。

后果： 一条未来格式对象就能阻断整张 OGKR，用户无法查看或另存其他对象；兼容性问题在版本升级后会集中暴露。

推荐方案： 使用 TryParse 和明确的 fallback/ParseIssue，尽可能保留原始 token；主解析循环按行隔离异常，未知值应显示警告而不是让整个文件失败。

F-085 · Medium FumenConverter 批量转换会泄漏输入文件句柄

位置： FumenConverterWrapper.cs:25-35

触发条件： File.OpenRead(option.InputFumenFilePath) 直接传给 DeserializeAsync，没有 using/await using；默认 parser 不拥有调用方的 stream。

后果： 批量转换多文件时句柄要等 GC 才释放，Windows 上源文件会被锁住并最终耗尽句柄；取消和异常路径尤其容易留下锁。

推荐方案： 调用方使用 await using 明确管理输入流，约定 parser 不重复处置；转换结束、取消和异常都必须走 finally。

F-086 · High SVG 丢失后任何保存都会被绝对路径异常阻断

位置： DefaultOngekiFumenFormatter.cs:101-114、SvgPrefabCommand.cs:53-61

触发条件： SVG formatter 只写绝对 FullName，移机或删除外部 SVG 后 parser 保持 SvgFile=null；再次保存时 formatter 对空资源直接抛异常。

后果： 用户虽然还能打开并编辑其他对象，但 Ctrl+S/转换会整体失败；工程无法随目录迁移，外部资源丢失会扩大为整谱不可保存。

推荐方案： 保存工程相对路径或嵌入资源；缺失时保留原始 locator，允许原样写回并只提示预览不可用，不能阻断整谱保存。

F-087 · Medium SVG 自定义曲线插值器保存后恢复默认

位置： DefaultOngekiFumenFormatter.cs:101-114、SvgPrefabCommand.cs:24-40

触发条件： 属性面板可以选择非默认 CurveInterpolaterFactory，但 SVG formatter 没有写 factory 名称，parser 也不会恢复该属性。

后果： 保存重开或格式转换后插值器静默回到默认 XGridLimited，后续重新生成的 SVG 路径几何改变，用户看不到元数据丢失。

推荐方案： 写入稳定 factory 名并通过注册表解析；旧文件缺省使用默认，未知名称记录 ParseIssue，并为不同插值器做 round-trip 校验。

F-088 · High PROGJUDGE_BPM 未校验会污染长条判定计算

位置： ProgJudgeBpmCommandParsers.cs:7-15、HeaderCommand.cs:104-110、Hold.cs:130-160

触发条件： OGKR/Nyageki 可以把 0、负数、NaN 或解析失败的默认 0 直接写入 MetaInfo.ProgJudgeBpm，没有范围校验。

后果： Hold 判定步长计算用该值做除法、Log 和位移，可能得到错误步长、溢出或异常长的判定循环；坏元数据会影响整张谱面的判定和统计。

推荐方案： 在 parser 边界要求有限且大于 0 的 BPM，非法值记录 ParseIssue 并回退到明确默认值（例如 240）；计算函数也应对异常输入做防御。

F-089 · High 谱面标准化计算出的新 XGrid 没有写回对象

位置： Utils/Ogkr/StandardizeFormat.cs:153-193

触发条件： InterpolateAllLanes 为受影响对象计算了 afterLane 和 afterXGrid，循环末只赋值 obj.ReferenceLaneStart，没有将新坐标写回 obj.XGrid。

后果： 对弯曲或被替换车道上的 Tap/Hold/HoldEnd 执行标准化后，对象仍保留旧横向坐标；导出或再次渲染时出现视觉、判定位置错位。

推荐方案： 在 afterXGrid 非 null 时同步更新 obj.XGrid，并保留无法匹配对象的诊断；加入标准化前后车道和坐标一致性测试。

F-090 · High Music.xml 导入再生成会篡改作者和 MusicSource 元数据
